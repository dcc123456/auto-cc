# AGENTS.md — auto-cc 项目规范（对 AI 代理与人类同等生效）

本文件是**约束清单**，不是建议清单。每条规则后面标注它的**强制手段**：
`[机检]` = 有 hook / eslint / 测试自动拦截；`[验收]` = 写进对应 spec 的验收条目，逐项打分；
`[纪律]` = 只能靠执行者自觉，因此每次都必须在收尾自检里显式回答。

冲突时的优先级：**本文件 > docs/plans/\* > docs/specs/\* > 个人习惯**。
若某条规则与当前计划的既定决策不可调和，**先停下来提出冲突，不要自行打破规则继续写**。

---

## 0. 项目是什么（一句话，防止跑偏）

面向中国求职者的**桌面 app**（mac / windows / linux），用 **Cordis 插件框架**集成
浏览器自动化（搜 JD / 打招呼 / 投递）、简历知识库、简历 PDF 生成与编辑。
它**不是** web 项目、**不是**脚本集合、**不是** SaaS 后台。任何"先做成网页再说"的实现都是错的。

执行纪律：**一次只推进一个子计划**，且必须先有 plan、再写代码、最后逐项验收。
`docs/00-master-plan.md` §4 的计划树是当前唯一的路径依据。

## 1. 提交规范（Commit）

| #   | 规则                                                                                                                                                     | 强制                                                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 1.1 | 提交信息**必须用中文**书写描述部分。type / scope 是机器解析的枚举，保持小写英文。                                                                        | `[机检]` `.githooks/commit-msg` 要求描述含汉字                  |
| 1.2 | 格式：`<type>(<scope>): <中文subject>`，subject **必须说清"做了什么 + 为什么"**——是功能就写实现了什么功能，是缺陷就写修复了什么 bug / 什么场景下出问题。 | `[机检]` 正则 + `[验收]`                                        |
| 1.3 | 禁止 `update`、`fix bug`、`临时提交`、`wip`、`顺手改一下` 这类无信息量的 subject。                                                                       | `[纪律]`（无法机检全部，靠 review）                             |
| 1.4 | 一个提交只做一件事。功能与格式化改动**必须分开提交**，不许夹带无关重构。                                                                                 | `[纪律]`                                                        |
| 1.5 | subject ≤ 60 个汉字，正文可选、用 `-` 列点说明动机与影响面。                                                                                             | `[机检]` 长度上限 120 字符                                      |
| 1.6 | **每次修改完成后必须立即提交，并推送远端**，不允许代码在本地堆积。                                                                                       | `[机检]` 收尾自检脚本 `pnpm status:check`（无远端时降级为提示） |

**type 取值**：`feat` `fix` `chore` `docs` `refactor` `test` `perf` `build` `ci` `style`
**scope**：包名或功能区（`core` `ipc` `browser` `resume` `kb` `workflow` `ui` `docs`），kebab-case。

示例（正确）：

```
feat(browser): 增加 persist:<platform> 会话分区，重启后保留 BOSS 登录态

- 用户每次重启都要重新扫码是主流程断裂点
- session.fromPartition 按平台隔离，cookie/localStorage 落 userData
```

```
fix(ipc): 修复渲染层调用未白名单 service 时主进程崩溃而非返回错误

- 白名单校验异常未被捕获，穿透到 ipc handler 顶层导致进程退出
```

反例（禁止）：`chore: update`、`fix: 修 bug`、`feat: wip`。

> 1.6 的例外：**未跟踪的调查副本、临时 spike 不提交**（它们在工作区之外，见 §7）。
> 当前仓库**尚未配置远端**（`git remote -v` 为空）。在远端配好之前，1.6 执行为
> "必提交 + 明确报告未推送"，不得静默跳过。

## 2. 代码复用与简洁（本项目最重要的工程美德）

**以逻辑复用为荣，以堆积代码为耻。**

| #   | 规则                                                                                                                                                                                                | 强制                                                                             |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 2.1 | 写任何新函数之前，先在同包、`packages/shared`、`packages/core` 里**搜索是否已有实现**（按能力搜，不只按名字搜：`retry`/`throttle`/`parse`/`locate`/`render`）。已有就复用或扩展，不要复制改写一份。 | `[纪律]` + `[验收]`                                                              |
| 2.2 | 同一逻辑**出现第二次**就必须抽公共层；第三次还在复制视为缺陷，必须修掉才能通过验收。                                                                                                                | `[验收]`                                                                         |
| 2.3 | 优先**扩展现有模块的接口**，而不是新建一个平行模块。新增文件/新增 service 需要在 plan 里说明理由。                                                                                                  | `[验收]`                                                                         |
| 2.4 | 发现无用的代码（未被调用的导出、死分支、被替换的旧实现、注释掉的代码块）**及时删除**，不要"先留着"。                                                                                                | `[机检]` `eslint --max-warnings 0`（no-unused-vars / no-explicit-any）+ `[纪律]` |
| 2.5 | 发现功能重复的实现，**合并到一个入口**，另一个删除；不允许两个都能用。                                                                                                                              | `[纪律]`                                                                         |
| 2.6 | 代码尽可能简洁：不做超出需求的功能、不为假想的未来做抽象、不加不会发生的异常处理。边界校验只在系统边界做（用户输入、外部页面、LLM 输出）。                                                          | `[纪律]` + `[验收]`                                                              |
| 2.7 | 抽象门槛：三行相似代码好过一个过早的抽象。但同一逻辑出现第二次（见 2.2）就必须抽。两条规则冲突时，按"是否已经在做同一件事"判断，不按行数判断。                                                      | `[纪律]`                                                                         |

**禁止引入第二套同类基础设施**（本项目已判定，违反即退回）：
第二套日志、第二套配置读取、第二套状态存储、第二套并行的浏览器宿主（同一时刻只允许一套运行时在驱动页面；
外部内核可由 app 内置或自动下载，见 `docs/00-master-plan.md` §1.4 的 2026-09-30 更正——真实约束是"用户零手动下载"
与"功能完整"，不是"禁止第二套内核"）、第二个 LLM 客户端、
第二个 SQLite 连接池。所有跨模块能力必须经 `@auto-cc/core` 复导出，不得直接 `import 'cordis'`
`[机检]` eslint `no-restricted-imports`。

## 3. 注释与命名

| #   | 规则                                                                                                                                                                                                                       | 强制                                  |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 3.1 | **每个函数/方法都要有中文注释**，说明：作用、入参（含单位与边界含义）、返回值（含失败时的语义）。用 JSDoc 形式。                                                                                                           | `[验收]` + `[纪律]`                   |
| 3.2 | 注释写**为什么**和非直观约束，不复述代码字面。`// 返回 x` 这种废话注释视为违规。                                                                                                                                           | `[纪律]`                              |
| 3.3 | 复杂流程在函数头部写 1–3 行流程说明；一行注释只允许一行，禁止段落式大文档注释块。                                                                                                                                          | `[纪律]`                              |
| 3.4 | **变量命名必须有含义**：读名字就知道它装什么、属于哪个阶段。禁止 `data`、`res`、`temp`、`item`、`flag`、`obj2`、`a/b/c`、以及无语义缩写。循环内单字母仅允许在 ≤3 行的极短作用域。                                          | `[纪律]` + `[验收]`                   |
| 3.5 | 命名风格：`camelCase` 变量、`PascalCase` 类型与类、`kebab-case` 文件名与包名、常量 `UPPER_SNAKE_CASE`。布尔量用 `is/has/should/can` 前缀。                                                                                 | `[机检·1.2]` eslint naming-convention |
| 3.6 | 术语与 `docs/00-master-plan.md` 保持一致：JD / 打招呼 / 投递 / 站点知识包 / 工作流节点 / 额度闸门。代码里用英文名但概念表要能对上（`workflow.runner`、`entitlement.gate`、`usage.ledger`、`platform.boss`、`resume.kb`）。 | `[纪律]`                              |

注释示例：

```ts
/**
 * 在指定会话分区里解析平台登录态是否仍然有效。
 * @param platform 平台标识（'boss' | 'liepin'），决定探测页与判定选择器
 * @param nowMs 判定基准时间戳（毫秒），用于比对 cookie 过期时间
 * @returns 登录态快照；无会话或已过期时 status 为 'expired'，不抛异常
 */
```

## 4. 项目结构

| #   | 规则                                                                                                                                                                                         | 强制                                                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 4.1 | **结构必须清晰**：monorepo 分包见 `packages/*`，一个包只做一件事。层依赖方向只能是 上层依赖下层（L0 内核 → L1 壳 → L2 领域 → L3 流水线 → L4 界面），**禁止反向依赖、禁止同级横向内部引用**。 | `[机检]` eslint boundaries                                      |
| 4.2 | 包内固定分区：`src/index.ts`（唯一对外出口）、`src/internal/`（外部禁止深入 import）、`src/*.test.ts` 与被测文件同目录。                                                                     | `[机检]` eslint `no-restricted-imports`（`**/src/internal/**`） |
| 4.3 | 新功能先判断"属于哪个已有包"；只有确实跨不出时才新建包，且要在 plan 中记录理由与边界。                                                                                                       | `[验收]`                                                        |
| 4.4 | 目录不允许出现孤儿文件（不被任何入口引用）与"临时"目录长期存在。未完成的实现不进主干，或明确标记在 spec 的 `[ ]` 项里。                                                                      | `[纪律]`                                                        |
| 4.5 | 计划与验收文档必须成对：`docs/plans/<NN>-<area>/plan.md` + `docs/specs/<NN>-<area>/spec.md`。文档 ID（如 `2.3-05`）一经分配永不复用或改写。                                                  | `[纪律]`                                                        |

## 5. 前端（渲染层）硬性要求

| #    | 规则                                                                                                                                                                                                                                  | 强制                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 5.1  | **样式只用 Tailwind CSS**。禁止 `.css`/`.module.css` 里手写自定义规则（全局入口与极少数 `@layer` 例外），禁止内联 `style={}` 做视觉布局，禁止 CSS-in-JS。                                                                             | `[机检·1.2]` eslint（renderer 包禁止 import 非入口样式文件） |
| 5.2  | 需要自定义视觉时，组合 Tailwind utility；确实表达不了才允许一个 `@layer components` 类，并在 PR 里说明。                                                                                                                              | `[纪律]`                                                     |
| 5.3  | **图标只用 lucide-react 的现有图标**，禁止手写 SVG、自绘 path、引入其他图标库或 emoji 当图标。                                                                                                                                        | `[机检·1.2]` eslint（renderer 内拦 SVG 字面量）              |
| 5.4  | 找不到合适 lucide 图标时，**列出 2–3 个近似候选并询问**，不要自己造。                                                                                                                                                                 | `[纪律]`                                                     |
| 5.5  | **页面上出现的每一条文案都必须走 i18n**。禁止裸中文字符串出现在 JSX 里。语言包放渲染层本地 JSON，不依赖网络；当前必须至少提供 `zh-CN`（默认）与 `en`。                                                                                | `[机检·1.2]` eslint 裸文案检测 + 缺翻译校验                  |
| 5.6  | i18n key 按功能区层级命名（`workflow.panel.start`、`jd.card.salary`），禁止用文案本身当 key。新增文案必须同时补齐所有 locale，缺失即 lint 失败。                                                                                      | `[机检·1.2]`                                                 |
| 5.7  | 文案里的动态值用插值参数，禁止字符串拼接组句（不同语言语序不同）。平台专名（BOSS 直聘）作为参数不进翻译主句。                                                                                                                         | `[纪律]`                                                     |
| 5.8  | 渲染层**不碰 Node 能力**：只经 `window.autoCC`（`cordis:call` / `cordis:event` 白名单）访问主进程 service。`contextIsolation` / `sandbox` / 无 `nodeIntegration` 是不可动摇的底线。                                                   | `[机检]` 1.2-04 类断言 + `[验收]`                            |
| 5.9  | 首页第一入口是**对话式 Agent（chat）**，工作流面板是第二视图；两者共用同一个 `workflow.runner`，禁止各长一套业务逻辑。新增功能页必须既能被工作流节点调用，也能被 agent 当作工具调用，不允许做出"只有工程师知道怎么串起来"的孤岛页面。 | `[验收]`                                                     |
| 5.10 | 会话消息流、工具卡片、自治档位指示都必须属于**独立组件 + 独立 i18n 命名空间**（`chat.*`、`agent.tool.*`、`agent.autonomy.*`），文案不得硬编码在组件里；浏览器真实页面截图是 agent 能力的验收手段，不是用户的唯一反馈渠道。            | `[机检·1.2]`                                                 |

## 6. 方案先行：新能力必须先研究

**实现项目里没有的功能之前，必须先做外部取证（GitHub / 官方文档 / 网页检索），确认方案可行且采用当前主流做法，再写代码。**

| #   | 规则                                                                                                                                                                                | 强制                |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| 6.1 | 研究产出写在对应 `docs/plans/*/plan.md` 的"选型与证据"小节：候选方案、**否决理由**、被验证的一手来源（官方文档 URL 或仓库路径）、以及**本机实测的 spike 结论**。                    | `[验收]`            |
| 6.2 | **文档转述不可信，必须以实测为准**（本项目已两次因照抄博客里的框架 API 而构建失败）。涉及框架/第三方库 API 形态时，先读它的 `.d.ts` 或编译产物，或跑最小 spike 验证，再写调用代码。 | `[纪律]` + `[验收]` |
| 6.3 | 前沿性判断：优先当前维护活跃、与 Electron/ESM 兼容、无原生编译依赖的方案。引入新依赖前先回答"现有依赖能否覆盖"。                                                                    | `[纪律]`            |
| 6.4 | spike 代码放工作区外的 `.research-repos/`，**不进 auto-cc 仓库**；结论进文档，代码不进主干。                                                                                        | `[纪律]`            |
| 6.5 | 被否决的技术路线，spec 里必须留一条**反向验证**条目（例：确认"不引入 Playwright"没有造成不可补齐的能力缺口）。                                                                      | `[验收]`            |

## 7. 测试与收尾自检（每个子计划收口必须做完）

**禁止"脚本绿了就宣称做完"。** 本项目的测试标准是**能看到页面**：

| #   | 规则                                                                                                                                                                                                                                                                               | 强制                                         |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 7.1 | 任何标 `V`（可视）的验收项**必须有截图/DOM 断言证据**，通过 CDP harness（`pnpm harness`）驱动真实窗口，不允许用单测替代。CDP 端口按项目约定用 **10222**（`pnpm dev` 与 harness 默认值），不使用 Chrome/Electron 默认的 9222。                                                      | `[验收]`                                     |
| 7.2 | 自动化测试**不得访问真实招聘平台**。登录态、抓取、打招呼、投递一律先打本地 fixture 站点；真实平台只在用户在场时手动验证。                                                                                                                                                          | `[机检·1.6]`（测试 URL allowlist）+ `[纪律]` |
| 7.3 | 所有外发动作（打招呼、发送简历、投递）必须经 `entitlement.gate`；绕过 gate 的调用必须有测试使其失败。                                                                                                                                                                              | `[机检·1.9]` 骨架测试                        |
| 7.5 | **测试过程中产生的图片/临时文件一律不得进入 git 仓库**。探针输出、中间态截图、一次性素材只能写到被忽略的 `tmp/` 目录；入库的图片只允许两种路径：`docs/acceptance/<子计划>/<验收条目ID>-*.png`（正式验收证据，文件名必须对应 spec 条目）与 `resources/**`（应用素材，非测试产物）。 | `[机检]` `.githooks/pre-commit`              |
| 7.4 | **收尾自检清单**（每次改完必须逐条回答，任一不过不得提交/不得声称完成）：                                                                                                                                                                                                          |                                              |
|     | ① `pnpm typecheck` / `pnpm lint` / `pnpm format:check` / `pnpm test` 全绿，贴实际命令与输出                                                                                                                                                                                        | `[机检]`                                     |
|     | ② V 类条目附截图路径或 DOM 断言输出，逐条对应 spec ID                                                                                                                                                                                                                              | `[验收]`                                     |
|     | ③ spec 状态位更新（`[x]` 通过 / `[!]` 受阻并写原因 / `[ ]` 未做），不留下"看起来过了"的模糊项                                                                                                                                                                                      | `[验收]`                                     |
|     | ④ 复用检查：新写的逻辑搜过同能力实现吗？出现第二处复制了吗？（对应 §2）                                                                                                                                                                                                            | `[纪律]`                                     |
|     | ⑤ 死代码检查：有没有未被调用的导出、被替换的旧实现、注释掉的代码块（对应 §2.4）                                                                                                                                                                                                    | `[纪律]`                                     |
|     | ⑥ 前端改动：Tailwind、lucide、i18n 三项是否都满足（§5）                                                                                                                                                                                                                            | `[机检]`                                     |
|     | ⑦ 提交与推送是否完成（§1.6），commit message 是否符合 §1                                                                                                                                                                                                                           | `[机检]`                                     |
|     | ⑧ 暂存区里有没有测试临时产物（截图、探针输出、一次性素材）？只允许 §7.5 的两类路径                                                                                                                                                                                                 | `[机检]`                                     |

`[!]` 是合法状态——环境不具备（例如本机为 Windows、无法验证 macOS 运行期）时**如实标 BLOCKED**，
禁止用推测写成 `[x]`。诚实的空项比虚假的全绿有用。

## 8. 安全与合规红线（不可为赶进度让步）

1. 渲染层 `contextIsolation: true` + `sandbox: true` + `nodeIntegration: false`；`window.open`/外链默认拒绝。
2. IPC 只走 `cordis:call` / `cordis:event` 白名单，禁止万能 `invoke` 透传。
3. **不绕过平台风控**：检测到验证码/风控即暂停并通知用户，不做识别与规避。频控、日上限、人类化节流是必需项而非可选项。
4. 简历内容**事实锁定**：LLM 不得编造公司/职位/时间/数字，必须过事实校验（见 `docs/research/source-repos-analysis.md` §2.3 的 `factCheckService` 借鉴）。
5. 会话 cookie、日志、截图中的个人数据**默认脱敏**；日志不落原始 cookie。
6. 不把密钥写进仓库；LLM key 走系统安全存储或本地配置文件，且配置文件已在 `.gitignore`。
7. 抽取来源的许可证必须记账（AGPL 依赖附 NOTICE；PolyForm 非商用来源只能 clean-room 重写）。

## 9. 环境事实（已实测，勿重复试错）

- 本机 **Windows**，Git Bash。**macOS / Linux 的运行期验证在本机无法完成**，相关条目一律标 BLOCKED，不做推测。
- 网络对 GitHub 直连与 `git clone` 不稳定；npm 走镜像；Electron 二进制镜像走 `.npmrc` 的
  `electron_mirror`。**实测更正（1.2）**：Electron 44 起包内**没有 install 脚本**，只暴露
  `install-electron` bin，`pnpm-workspace.yaml` 的 `onlyBuiltDependencies` 对它空转；
  二进制由根 `package.json` 的 `postinstall` 显式调用 `install.js` 拉取。
- npm 生命周期脚本在本环境**可能被禁用**：不要依赖 husky/commitlint 安装期钩子，钩子用
  `core.hooksPath` + 纯 shell 实现（已在 `.githooks/`）。根 `prepare` 在非 git 目录里会失败，
  临时目录装依赖时要先 `git init`。
- **实测（2.5-d）单实例锁按 userData 目录算**：装机版 app 在跑（默认 userData
  `%APPDATA%\auto-cc`）时，`pnpm dev` 会**静默退出 0**、CDP 端口根本不监听——不是崩溃，别按报错找。
  正确做法是给 dev 换一份 userData（`AUTO_CC_USER_DATA_DIR="$PWD/tmp/dev-userdata" pnpm dev`，
  `scripts/dev.ts` 已支持），**不要为了跑测试去杀用户正在用的 app**。
- **实测（2.5-d）fixture 服务是长驻进程且模板内联在代码里**：`/chat/frame` 的 HTML 写在
  `scripts/fixture-server.ts` 里（父页 `chat-lab.html` 每次请求读磁盘），改了帧模板不重启
  `pnpm fixture` 会得到"半新半旧"的页面，表现为帧绑定到写死的默认 jobId 而不是 URL 参数。
- Node 24 内置 `node:sqlite` 可用 → **禁止 `better-sqlite3`**（原生编译会破坏"用户只装一个 app"）。
  **实测（1.3）**：Electron 44 主进程内 `node:sqlite` 直接可用（sqlite 3.53.4 / WAL /
  `PRAGMA user_version`），见 `docs/acceptance/1.3/1.3-06-node-sqlite-in-electron.txt`。
- Cordis 是 `4.0.0-rc.*`，**API 未稳定**：只在 `packages/core` 一处 `import 'cordis'`，
  其余包经复导出使用。已知坑：`FiberState` 是 const enum，在 `verbatimModuleSyntax` 下不可再导出
  （用 `fiberState(state: number)` 映射函数代替）；`Context` 上没有 `start()/stop()`。
- **实测（1.3）插件配置一律走构造器第二个参数**：cordis 用 `static Config` 校验后把结果作为
  第二个实参传入（`Plugin.Constructor<T>` 即 `new (ctx, config: T)`），而 `ctx.plugin()` 调用点的
  配置类型正是从该参数**反推**的（`GetPluginConfig`）。写成单参数构造器 + 读 `ctx.fiber.config`
  会让调用方传任何配置都被判成 `undefined` 而报 TS2345。参数类型取 schema 的**输出**，所以带
  `.default()` 的键在直接调用点必须显式给出（`cordis.yml` 里可以省略，由 schema 补）。
  内核按 `Registry` 挂载时配置是运行期合并结果，因此 `PluginConstructor` 的该参数只能是 `any`。
- **实测（1.3）`ctx.effect(fn)` 会立刻执行 `fn` 取回收器**：`fn` 必须「返回一个函数」，
  单层箭头就是刚挂载就执行清理（store 的连接因此在 init 之前被 close，表现为「尚未完成挂载」）。
- **实测（2.4 spike）spike 的入口不能是 `.mjs` 直接交给 `electron.exe`**：那样走 `default_app`，它在
  「加载应用包」期间不发出 `ready`，模块顶层 `await app.whenReady()` 永不 resolve（静默卡死、不产子进程）。
  入口写 CJS：`app.whenReady().then(() => import('./spike.mjs'))`。
  同一运行时里 `ELECTRON_RUN_AS_NODE=1` 起的是纯 Node（本机实测 node 24.21.0 / sqlite 3.53.4），
  要验数据库行为（WAL 崩溃恢复等）用这条路，不需要 GUI。
- **实测（2.5）热改配置会连带重建下游插件**：`plugins.saveConfig('A', …)` 之后，凡是 `inject` 了 A 的
  服务都会被重新实例化并重跑 `[Service.init]`。因此"由别的包在 init 时推给我、我存进内存 Map"的
  注册表会在改配置后静默变空（本项目在 2.5-e 撞上过：打招呼渠道表被清空，从此 `OUTBOUND_CHANNEL_MISSING`
  到重启为止）。跨包能力一律改成**用的时候按名字现问**，不要在本地存第二份事实（§2.7）。
- **实测（5.1-c）`cordis.yml` 的清单顺序就是挂载顺序**：kernel 按列表从上往下逐个 `await` 挂载，所以
  "在自己的 init 里往别的服务登记东西"的一方，**必须排在被登记的那一行之后**。给一只已存在的服务加上
  `agentTool` 登记时，如果它在清单里排在 `agent` 前面，`registerAgentTools` 软问不到注册表、返回 0，
  真 app 的工具清单就静默少一只（本项目 5.1-c 撞上过一次：四道门禁全绿、活体清单 15 只而非 16 只）。
  **单测看不见这一类缺陷**——用例都把注册表替身挂在被测服务前面。这条顺序从此由
  `scripts/check-tool-contract.ts`（`pnpm lint` 链内）机检，别再依赖注释。
- **实测（5.3-a）给已有服务加新表必须另起迁移号段，改老迁移的 `up` 不会重跑**：`runMigrations` 的判据是
  `schema_migrations` 台账里"这一版记过账没有"，不是 DDL 幂等——`CREATE TABLE IF NOT EXISTS` 塞进已应用的
  版本号里，在老库（含本机开发实例）上根本执行不到，运行期才以 `no such table` 失败。
  **单测同样看不见**：每个用例都从空库起，所有迁移都是头一回跑。加表前先 `SELECT version FROM schema_migrations`
  看台账最高值，取下一号段（本项目当前到 17）。
- **实测（2.5）harness 的三条使用约束**：① eval 脚本不支持顶层 `await`，整段包进
  `(async () => { … })()`；② 默认 CDP target 可能是内嵌内核视图（那里没有 `window.autoCC`），
  打应用页必须显式 `--url 5173`；③ `shot --reveal <css>` 只在顶层文档里找元素，同源 iframe
  （fixture 聊天页）里的内容要在帧内 `eval --url 10233` 调 `scrollIntoView` 后再 `shot`。
- **实测（2.5）页面上的浏览器动作前必须先 `sessions.open`**：内核视图未打开时页面操作以
  `NO_KERNEL_SESSION` 失败，而改一次配置就会关掉已打开的会话视图（与上面第一条同源），
  顺序必须是「改配置 → 重开会话 → 跑」。
- 仓库**已有 git 远端**（`origin` → `dcc123456/auto-cc`），§1.6 的"提交 + 推送"按原文执行。
