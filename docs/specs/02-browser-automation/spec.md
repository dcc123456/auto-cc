- **2.1-11**：**计数口径换成 CDP 的 page target 表**（对端读数），而不是 `process._getActiveHandles`：
  只 `forceUnload()` 不 `close()` 的 webContents 会一直挂在 target 表上，所以这张表数得比自述可信。
  10 轮 `open('boss') → close()`（每轮回读 `activePlatform`，10/10 都是 boss→null）之后
  表里仍是 2 个 target，与挂载前基线逐字相同；UI 点击路径另跑 10 轮，每轮取样也都是 2。
  证据：`2.1-11-target-count.txt`。
- **2.1-12**：BLOCKED——本机 Windows，mac/Linux 运行期无法验证，随 1.7 产物装机验证补。

这不是 app 的缺陷（`did-fail-load` 与 404 页都如实反映在视图里），但会让 2.1-01 拍到假证据，

`pnpm fixture`，这条写进 2.2 的验收前置。

**过程中发现并就地修掉的偏差**：
① `locator` 与 `relocated` 事件的 `because` 字段原本回显**自愈之后**的得分，
而契约要的是「声明候选为什么落空」的原因，已改回并补了回归断言；
② 实验台的提示行原本在「调用成功但没命中」时也写「成功」（transport 成功被当成结局成功），
已改为转述真实结局（走 `useBridgeAction` 既有的 `describe` 挂钩，没有新造机制）。
两处都是看截图才发现的——单测拦不住一行说谎的文案。

**与 spec 字面写法不同的三处（不是漏做，是就地决定）**：
① 「本次目标条数」是新增的界面输入框（`jd-limit`），走的是契约里已有的 `criteria.limit`，
没有改 `cordis.yml` 再重启进程去演示停止条件；② 抓取没有单独的「重新读快照」按钮，
`browser.page.snapshot` 已在实验台 2.2 那侧暴露，重复放一个入口就是第二套实现（AGENTS.md §2.5）；
③ 仿站的哨兵 `div` 必须有可见高度——零面积的哨兵即使滚进视口也不会被 `IntersectionObserver` 判为 intersecting。

**自测通道的一条硬前置（本轮踩实）**：dev 窗口被最小化时 `document.visibilityState === 'hidden'`，
Chromium 不再产帧，于是 `IntersectionObserver` 回调与 `scroll` 事件**一个都不发**（实测：`window.scrollTo`
把 scrollY 从 0 推到 653，事件计数仍为 0，第二屏永远长不出来），抓取会在第一轮就以「页面无新增」停下——
读数看着像"这站就 5 条"，其实是通道假死。`--disable-features=CalculateNativeWinOcclusion` 只解决"被别的窗口盖住"，
不解决"最小化"。**跑 2.x 的可视验收前先确认 dev 窗口没被最小化**（`harness eval --url 5173` 读 `visibilityState`）。
后台渲染（用户把 app 收进托盘/最小化后仍要能跑完搜索）是产品能力，另计条目，见下方遗留项。

**遗留（不假装过）**：

- 2.3-10 真实平台判据待用户在场；
- 「窗口不可见时抓取仍能推进」未做（需要 `backgroundThrottling: false` + 不依赖渲染帧的加载触发，属 2.4 之后的加固项）；
- 进度行在目标条数小于屏宽时显示「已入库 5/3 条」，读起来别扭但说的是事实（一屏一次），暂未粉饰。
