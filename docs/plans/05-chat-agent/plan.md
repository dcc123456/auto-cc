## 1. 立项依据与证据基线

P1~P4 结束后，系统里已经存在全部**业务能力**（搜索、建档、话术、定制简历、打招呼、投递），
但没有**总控**。P5 不新增业务能力，只做三件事：

1. 把自然语言变成一次可执行、可见、可确认的**计划**；
2. 按计划逐步调用已登记的工具，把过程如实回报到对话流；
3. 把跑通的一轮对话**沉淀**为可复用的工作流，并接上调度、看板与发布。

因此 P5 的判据不是"能力有没有"，而是"**主控面是否可信**"：会不会谎报、会不会越权、
会不会在别人接管后仍按旧页面瞎点。

## 4. 边界规则

1. **工具面即能力面**：注册表里没有的，agent 看不见也调不动；调用未知 id 必须报错而非"试试看"。
2. **计划先于执行**：多步任务必须先产出可见计划（步、预期副作用、预计额度消耗），确认后才动。
3. **外发三闸门**：档位允许 + 用户确认（除非显式处于全自动白名单）+ `entitlement.gate` 放行，三者缺一即不外发。
4. **观察先于假设**：任何一步执行前，若目标页面可能被人工改过（发生过接管、或距上次快照超过阈值），必须重读 DOM。
5. **回报忠于证据**：对话里的"完成"必须能指向 run 步记录与证据文件；无证据只能说"未验证"。

## 5. 核心设计要点

### 5.1 工具契约（对齐 P2 的 SPI）

```ts
ToolSideEffect = 'read' | 'localWrite' | 'outbound';
AgentTool = {
  id: string;              // 'browser.navigate' | 'boss.greet' | 'resume.generateForJd' ...
  titleKey: string;        // i18n key，不进注册表的是文案本身
  params: ZodType;         // 入参校验，失败即拒绝执行
  sideEffect: ToolSideEffect;
  requiresApproval: (p: Params) => ApprovalDecision;  // 依档位+副作用+额度算，默认最保守
  run: (p: Params, ctx: ToolRunCtx) => Promise<ToolResult>;
}
```

`ApprovalDecision` 三态：`auto` / `askApproval` / `askElicitation`（需补信息）。注册表是**唯一**能决定
"这一步会不会暂停"的地方，UI 与循环都不各自判断。

### 5.2 循环与状态

一次任务的持久状态：`AgentRun = { runId, sessionId, planStepIndex, status, autonomyTier, pendingApprovals[], snapshotRefs[] }`。
循环每一步只做四件事：**取当前步 → 判闸门 → 调工具 → 写观察**。LLM 只用于两处（生成计划草案、把观察摘要成回报文案），
"这一步能不能执行"由 `agent.policy` 用代码判定，**不交给模型自由裁量**（与 P4 事实核查同一立场：不做 prompt 式"让模型判断是否可信"）。

### 5.3 档位与确认

三档语义写死（主计划 §1.7-3）：`建议模式`只出计划；`半自动`每个写操作与外发都问；
`全自动`放行「这只手自己没声明要批准」的一切，**再加上用户显式加进免确认白名单的那些**（外发级也在可加白之列——
2026-10-03 用户裁定：主线动作要能自动出去，否则「全自动」永远自动化不了打招呼与投递）。
白名单的三条边界跟着一起写死：**默认为空**、**加白是一次显式用户操作并留审计**、**免确认不豁免 `entitlement.gate` /
频控 / 日上限**（AGENTS.md §7.3、§8.3 仍在链上）。白名单只在 `auto` 档生效，`semi` 仍逐条问。
当前档位需常驻显示在界面（截图可读，1.11-07 已在 P1 立此验收），界面上还要能读出「哪些动作已免确认」。
档位提升动作本身要留审计记录。

### 5.4 沉淀为工作流

导出规则：只允许沉淀"已成功执行且每步都有 run 记录"的连续段；沉淀时把具体入参
**参数化**（城市、关键词、日期区间提取为变量），未参数化的残留具体值要在面板里显式标出，避免"沉淀下来的工作流只能复现上一次那一条"。

### 5.5 接管与恢复

接管 = 循环挂起 + 标记 `humanTookOver`；恢复时**强制重读**目标元素指纹（复用 2.2 的定位与自愈），
指纹不匹配则重新规划该步而不是硬点。待决审批随检查点保存，重启后重新发出（§1.1 取证结论）。

### 5.6 压缩与脱敏

压缩保留清单是**白名单**（已投目标 id、被否决做法、剩余额度、当前档位、最近失败原因），
其余按摘要处理；简历/聊天文本里的手机号、邮箱、身份证在落库前脱敏（对齐 4.x 的 PII 条目）。

### 5.7 调度

调度器只触发**已保存的工作流**，不触发自由对话任务（无人值守下不允许临场规划外发动作）。
触发结果一律记账，且受同一 `entitlement.gate` 约束。

#### 5.10.2 数据模型：graph 与 plan 分两层

```ts
// 视图层：只有画布关心，不参与指纹计算
WorkflowNodeView = { nodeId: string; position: { x: number; y: number } };
// 语义层：扩现有 workflowNodeSpecSchema，加出口声明
WorkflowNodeSpec = { ...现有字段, outputs: Array<'default' | string> };  // 条件节点才有第二、三出口
WorkflowEdge = { id: string; source: string; sourceHandle: string; target: string };
WorkflowGraph = { id, revision, nodes: WorkflowNodeSpec[], edges: WorkflowEdge[], views: WorkflowNodeView[] };
```

`fingerprint` 只覆盖 `nodes + edges`（键有序的 canonicalJson 已有实现），**views 不进指纹**。
线性计划是「每条边都是 `default` 出口、且每个节点至多一个入边」的特例，
现有 `BOSS_BASIC_PLAN` 必须能原样升级成 graph 而不需要重写（5.10-02 的验收点）。

#### 5.10.3 DAG 语义解锁到哪一步

- **做**：条件分支（一个节点多个命名出口，runner 按出口选边）、并行扇出 + 汇聚（join 等所有入边到达）、
  失败专用边（`onError: fallback` 指向的边）。
- **不做**：循环与回边。理由：`workflow_nodes.attempts` 现在既是重试计数又是 2.4-10 统计的原料，
  循环会让「第几次执行」二义；且 loop 需要 `MAX_STEPS` 一类失控护栏，属新基础设施（§2.6 不做未来抽象）。
  这条以反向验证条目（5.10-14）留在 spec，不许 silently 变成"以后再说"。
- `runner.advance()` 从「数组顺序 +1」改为「按当前节点出口查边」；`node_index` 不再能定位 DAG 位置，
  改为按 `(run_id, node_id)` 定位——**这是对 2.4 已验收面的改动**，于是 2.4-05（断点续跑）与
  2.4-06（幂等不重放）必须在 DAG 下重跑一遍并留新证据（5.10-13），不得沿用旧结论。

#### 5.10.4 算子（operator）是唯一登记处

`OperatorDescriptor = { kind, category, titleKey, effect, params: ZodType, outputs[], icon }`。
画布左侧调色板按 `category` 分组列出、节点卡片渲染、右侧参数表单、runner 的 `registry.register`
分派四处**都从这一张表派生**；`kind` 与 2.4 的执行器名、5.1 的 `AgentTool.id` 对齐
（同一能力在对话里是工具、在画布上是算子，不接受两套名字，见 AGENTS.md §2.5/§5.9）。
`titleKey`/表单标签/校验文案全部走 `workflow.operator.*` 与 `workflow.canvas.*`，zh-CN 与 en 齐备才有 lint 通过。

#### 5.10.5 运行态与编辑态是同一张图

编辑态可拖可连线可改参数；点「运行」后画布切只读并叠加状态色（pending/running/done/failed/skipped），
状态来源就是 `workflow/progress` 事件，不轮询；点节点弹出该节点的参数、attempts、耗时与 2.4 的证据文件。
接管点（`requiresHuman` / 外发未观察完成）在图上必须显眼——这是 2.4 遗留的「接管点只在工作流视图可见」
的正面回应，画布成为该真相的唯一渲染面之一，而不是再造一条横幅。

#### 5.10.6 持久化与校验

自定义计划落 SQLite 新表 `workflow_plans(id, revision, graph_json, fingerprint, updated_at)`，
经 `@auto-cc/core` 的既有单一连接（不新建第二套存储，§2.7）；内置 `boss-basic` 仍来自代码。
保存前在**系统边界**校验（§2.6）：未知 kind、必填参数缺失、边指向不存在的节点或句柄、
有环、多个源点、外发节点缺 target 或未登记 gate 策略——逐条报「第几个节点为什么不行」，
不得只回"图不合法"。撤销重做是画布级命令栈（react-flow 不提供，自建）。

#### 5.10.7 与前端规范的三处硬约束

1. **样式**：`@xyflow/react/dist/style.css` 必须整体引入，否则画布不渲染。这是 AGENTS.md §5.2 的
   第三方库样式例外，需在全局入口引一次并在 spec 记录；节点内部样式一律 Tailwind utility，
   禁止再写 `.css`。
2. **图标**：算子图标只从 lucide-react 选（§5.3）；选不到合适图标时按 §5.4 列 2–3 个候选并询问，
   不自绘 SVG。
3. **不碰 Node**：画布在渲染层，只经 `window.autoCC` 白名单读写计划与订阅事件（§5.8），
   新增的 `workflow.graph.*` service 方法必须进 `shared/bridge.ts` 白名单，不开万能透传。

#### 5.10.8 本片明确不做

不做录制→自动生成工作流；不做子工作流/嵌套图；不做循环与回边；不做云端共享与多人协同编辑；
不做画布上的拖拽数据映射（变量插值 `{{node.output}}` 属 P5 之后的独立决策，理由同 5.10.3 的
「不建第二套字符串基础设施」）。

**裁定一（命名对账，与 4.6-11 同口径：锁形状与语义，不为名字动已跑通的接线面）**：
spec 5.1-01 写的六个名字里有四个与实现同义不同名——`params`=`input`、`sideEffect`=`effect`、

**裁定二（`description` → `titleKey` 是真缺口，而且是"两份事实"那种）**：读数是这样的——
注册表带的是中文字面量 `description`，它经 `agent.tools.list()` 变成 `ToolDescriptorView.description` 过了 IPC，

于是一只工具"叫什么"有两份事实：主进程一份（没人显示）、渲染层一份（不在注册表里）。
这撞 §2.7（跨包能力不许存第二份）与 §5.10（工具卡片文案不得硬编码在组件里），
还有一个已经发生过的后果：5.1-c 要新增工具时，改完登记处**还必须记得改渲染层那张表**，
忘了就显示成「未登记的工具」——那张表就是这类失效的现场。
本片把它合成一份：声明里放 `titleKey`（`agent.tool.labels.<短码>`，id 带点而语言包按点分层，所以仍用短码），
`ToolDescriptorView` 带它过 IPC，渲染层查语言包并**删掉硬表**；未登记 id 的兜底键保留。
**机检跟着落地**：新增一条检查——注册表里出现的每个 `titleKey` 必须在 `zh-CN` 与 `en` 都存在

**裁定三（`requiresApproval` 三态放哪）**：plan §5.1 要求"注册表是唯一能决定这一步会不会暂停的地方"，
而现在的 `requiresConfirmation: boolean` 表达不出"需要补充信息"（`askElicitation`）。

**5.3-b 的落点与理由（写这片之前定的形状，含一条对原计划的更正）**：

- **"显式配置项"落成服务侧的持久设置，而不是 `cordis.yml` 里的一个键**（这是对切片表原句的更正，两条实测理由）：

  `semi` 档不看白名单：那是"每个写操作都问"的档，能让白名单在这里生效就等于把档位语义合并成一档。
- **加白的手不是 agent 的手**：`setExempt` / `clearExempt` 不登记为工具，`loop.ts` 里也不出现这两个名字与表名，
  判法沿用 5.3-04 的静态口径并进同一个脚本（新增第 ⑥ 条），因为它是"agent 自己给自己放宽"的第二种形态。
- **界面**：新组件 `AgentPolicyPanel.tsx`（独立 i18n 命名空间 `agent.policy.*`，§5.10），挂在对话面板档位那一行下面——
  白名单只在全自动档生效，把"当前档位"与"哪些动作已免确认"画在同一屏，5.3-03 要的"任一截图可读出档位与生效范围"
  与 07 要的列表截图因此共用同一次捕获，不必为一个数截两次图。审计流水这一片先给服务与用例，不画进界面。

**5.3-c 的落点与理由（写这片之前定的形状，含一条"先抽公共再新增"的顺序约定）**：

- **等人应答这台状态机在 2.6-c 已经落过一次**，5.3-c 是它的第二个用户，所以**先抽通道、再写 agent**：
  `packages/outbound/src/deliver.ts` 里那套「`randomUUID()` 单号 → 内存 Map 登记 → 发事件提醒 →
  超时按拒绝 → 让出即中止 → 服务销毁收单 → 查无此单 fail-closed」的五性质机器，与 5.3-08 / 09 / 10 要的是
  同一台机器（§2.2 同一逻辑出现第二次必须抽公共层）。抽出去的只有**机制**，落在 L0 的
  `packages/core/src/pending-channel.ts`；留在各自服务里的是**领域**：view 长什么样、发哪个事件名、
  定局映射成哪个错误码。把机制留两份的真实代价不是重复行数，而是"超时＝未确认＝不执行"这条安全性质
  会有一处漏掉——那正是 5.3-10 要钉的东西。
- **通道只认三样东西**：单号、等人给的那个值、时刻。它的定局是三个可判别的结果
  （`answered` / `timed-out` / `cancelled`），**不猜调用方要哪种错误**——同一个"超时"在投递侧是
  `OUTBOUND_APPROVAL_DENIED` 的原话，在循环侧是一条 `refused` 步行与 `stopReason`，映射权在调用方。
  重复与迟到的应答在通道里就是 no-op（`answer()` 返回"没有落到任何在等的单上"），
  这一条同时满足 5.3-09 的"重复 id 被忽略"和投递侧既有的"后到的表态不算数"（同一条性质，一处实现）。
- **agent 侧不新建表、因此不占号段**：待决暂停是**等待状态**而不是事实记录，与 `deliver.ts` 头注释里
  那条判断同源（做成表就要回答"进程死了谁收 in-flight 的单子"，而超时按未确认本来就把所有悬挂兜住了）；
  真正的经过落在既有的 `agent_step`（那一行的 `status` 与 `code`）与 `agent_run.stop_reason` 上。
  "待决审批随检查点保存、重启后重发"明确不在本片（见下面的"5.3 不做的事"，plan §5.5）。
- **两类暂停各自的触发点都是当下真存在的事实**，不是为了截图造的：
  ① `approval`（是/否）——`policy.decide()` 交回 `CONFIRMATION_REQUIRED` 的那一步。今天这条分支直接落一行
  `refused` 就结束了，5.3-c 把它改成"先开单等人"：批准就照原样执行这一步，拒绝/超时/叫停才是今天的结局。
  5.3-b 写进人读文案的那句「逐条批准的卡片在 5.3-c 接」到这片才算数。
  ② `elicitation`（补充信息，可多轮）——模型给这一步拟的入参过不了**工具自己声明**的 strict schema。
  这条不是假想场景：确定性桩不产出合法入参，5.3-b 的活体证据里那只加白后的手正是停在
  `TOOL_INPUT_INVALID`（"桩没给出合法入参"）。LLM 输出是系统边界（§2.6），在动手之前按工具的契约问一句人，
  比把一句 `TOOL_INPUT_INVALID` 摔回对话里更接近"能替人干活"。**多轮的落法**：人补进来的那段还要过同一次
  schema 校验，还不合格就**再开一单**（新 `requestId`、卡片上写着第几轮与还缺哪些字段），
  而不是在一单里做分页状态——单号路由、超时、收单这些性质因此一条都不用特化。
- **`agent.tools` 多露一只 `validateInput(toolId, raw)`**（§2.3 扩展现有接口，不新建平行模块）：
  校验逻辑本来就在 `call()` 里（那次 `safeParse`），抽成一只可单独问的口，`call()` 改走它——
  于是"合法才动手"这条判辞仍然只有一处实现，循环只是提前问了同一个问题。
- **界面两张卡形状不同**（5.3-08 的 V 半边）：`approval` 是一只工具名 + 副作用级 + 原话 + 「批准 / 拒绝」
  两个按钮；`elicitation` 是同一份抬头 + 缺字段的原话 + 一个填输入的文本域 + 「提交 / 放弃」+ 轮次读数。
  两者都从 `agent.pause.pending()` 现读而不是只订阅事件——投递侧 2.6-01 定下的那条口径（事件负责"此刻提醒"，
  读数负责"错过了也还在"）在这里一字不改地复用。i18n 用独立命名空间 `agent.pause.*`（§5.10）。
- **一处必须提前认的副作用**：`agent.pause` 的超时时长是配置键，而 `agent.loop` inject 这只服务——
  改一次这一格就会重建整条循环（§9 的 2.5 实测）。可接受的前提是销毁时必须收单：
  `ctx.effect` 里走通道的 `cancelAll()`，在等的卡全部定成"未获批准"，那条 run 停在安全点并写下原因，
  而不是留一个没人应答的 `await` 悬在事件循环里。这条性质由用例钉，不靠注释。

**5.3-d 的落点与理由（写这片之前定的形状，含一处与 1.9 已验收原话的冲突调和）**：

- **5.3-11 判的是"串起来"，所以它必须住在装配层**（`packages/main/src/three-gate-link.test.ts`，与 4.4-09 的
  `gap-quota-link.test.ts`、3.7-02 的 `delivery-snapshot-link.test.ts` 同一个理由）：`agent` 包 import 不到
  `outbound` 与 `entitlement`（§4.1 的依赖方向，领域包之间也不许横向引用），在它自己包里只能用替身演一遍
  "闸门会拒"，而替身既不拒绝也不落账，那条断言是空的。装配层是唯一能把**真的循环 + 真的判定口 + 真的暂停通道 +
  真的 `outbound.greet` + 真的闸门与账本**放进同一个 `Context` 的入口，台架照 `greet.test.ts` 的 `boot()` 组，
  平台层与 sessions 沿用它已有的两个替身（§7.2：不碰真实招聘平台，发送由假渠道记调用次数）。
- **三维各关掉一次，每维断言两件事：没出手、没占额度**。① 档位那一维不给（`suggest` 档 → 判定口交回
  `TIER_SUGGEST_READ_ONLY`，连确认单都不该开）；② 档位给了但确认没过（`auto` 档 + 未加白 → 开确认单 → 人按拒绝
  → `PAUSE_DENIED`）；③ 前两维都放行而闸门不给（`auto` 档 + 那只手加白 → 工具真被调 → `mode:'daily'` 且
  `greet` 上限用尽 → `QUOTA_EXCEEDED`）。
  三次的判据都是**假渠道的调用记录为空** + `usage_ledger` 的用量行数不变，而拒因各不相同
  （三种 code 各指一格）——三条一起看才叫"缺一即不外发"，单看任何一条都只能证明那一格自己会拦。
  ③ 走加白那条路而不是"批准之后被闸门拦下"，是因为它不依赖应答的时序，用例不必等一张卡片。
- **第四格是正向对照，缺了它前三条全是空的**：同一份装配里把三维都放行（`auto` + 加白 + 额度还剩一条），
  确实发出去一次、确实多落一行账。这一条照 `gap-quota-link.test.ts` 第 3 条的写法立——
  没有它，"没出手"也可能只是台架坏了。
- **5.3-12 的形状选择（本片唯一需要论证的一处）**：被闸门拦下的动作记成**同域的第二张表**
  （`usage_denials`，号段 19：`action` / `target_id` / `workflow_run_id` / `ts` / `code` / `reason`，只追加），
  而不是给 `usage_ledger` 加一列 `status`。理由不是"加列麻烦"，而是**加列把安全性质变成了纪律**：
  `usage_ledger` 现在被三处计数读着——`countToday`（日上限）、`countFor`（同目标重复发送防护，spec 2.5-13）、
  `latestActionTs`（频控的钟，spec 2.5-04）。掺进被拒行之后，这三条查询每一次都必须记得带 `status` 过滤，
  漏掉任何一条的后果不是显示错误而是**被拒开始消耗额度 / 被拒之后那个目标再也发不出去 / 被拒之后白等一个频控间隔**，
  三种失效都往用户身上加惩罚。做成第二张表，"被拒不占额度"就是结构性质（它根本不在被数的那张表里）。
  写入口只有一处：`gate.perform` 在判定拒绝、抛 `QUOTA_EXCEEDED` **之前**写一行——它是唯一必经口，
  所以"被拦下必留痕"在结构上写不出绕过的代码（与 1.9-05 同一立场）。读出口并进已有的 `summary()`
  （多一个 `recentDenials`），不新开一只服务、不新开一条 IPC 白名单外的路径。
- **不认识的动作名不记被拒**：`requireLimit` 抛的 `INVALID_ARGUMENT` 是"有人问了个不存在的东西"，
  不是"拦下了一个动作"，硬记就把垃圾写进审计表；这条只在注释里认，不写成用例（§2.6：不加不会发生的处理）。
- **一处必须调的冲突（按本文件前言"先提出、不要自行打破"）**：5.3-12 与 1.9 已验收的原话
  「被拒既不花钱也不落账」（`docs/specs/01-framework/spec.md` 的 1.9-03 证据）以及
  `docs/plans/01-framework/plan.md` §8.4 决策 1「落账只在 task 成功之后，被拒的动作不记账」读起来直接相反。
  调和的依据是那句话的**理由**本身——"它没消耗平台侧任何东西，记进账本就是假用量"——它约束的是**用量**那一侧，
  而 5.3-12 要的是**审计**那一侧（人回头能看出这只手今天被闸门拦下过几次、为什么）。
  两者在"用量表一行也不许多"这个前提下同时成立：本片 `usage_ledger` 的每一列语义都不动，
  只在同域加一张只追加的拒绝流水。1.9 那句验收原话因此**仍然为真**，并新增一条用例把它钉住
  （三维各拒一次之后 `count()` 与 `countToday()` 都不变），防止后来者把两件事又搅回一张表。
- **与 5.3-c"不建表"的口径不矛盾**：那里不建的是**等待状态**（进程一死就无意义，做成表就要回答谁收 in-flight 的单子），
  这里建的是**已经发生的拒绝**（审计事实，必须跨重启成立）；两种东西的存储判据本来就不同。
  号段 19 也不构成 §2.7 禁的第二套存储——同属账本域、同一个连接、同一份 `store.migrations`、
  同一个 `usage.ledger` 服务持有，与 5.3-a/b 已确立的号段口径一致（号段只是台账里的版本号）。
- **另两闸不抄进 `usage_denials`**：档位拒绝与确认拒绝的经过已经落在 `agent_step.code / message` 与
  `agent_run.stop_reason` 上（5.2-c / 5.3-c 已验收），账本这边再存一份就是 §2.5 禁的第二处事实。
  本项目术语表里"额度闸门"专指 `entitlement.gate`（AGENTS.md §3.6），所以 5.3-12 的记账口只在这一条上；
  另两维由 5.3-11 的同一条链用例断言"不外发"。
- **本片不做界面**：5.3-11 / 12 两条都是 U 类，回看口先给服务与用例（与 5.3-a"本片不做界面"同一口径），
  用量面板要显示被拒流水是后面的事，等它成为验收条目再画，不提前堆代码（§2.6）。
- **收口照 5.2-d 的口径**：把 5.3 的 12 条状态位逐条对着**当前代码**复跑一遍判据（不是复读前四片的记录），
  过不了的如实标 `[ ]` / `[!]` 并写原因；落地记录里注明哪些是这片新验、哪些是复跑确认。
  真模型仍不在 5.3 范围内（§6 的出网授权未解除）。

**5.3 不做的事**：不接真模型（同 5.2，出网须用户单独授权）；不做检查点里保存待决审批与重启重发（5.5，
plan §5.5 明写"待决审批随检查点保存"）；不做"档位变更后重算已起草计划"（改档只影响后续步的判定，
已确认的计划不追溯——追溯就是§2.6 禁的假设性未来）；不做第四档（plan §5.3 沿用主计划三档）。

## 8. 明确不做

- 不在 agent 层写任何业务动作（抓取/发送/生成），发现缺口回 P2/P4 补。
- 不做多 agent 协作、群组编排、自主招募子 agent。
- 不做无人值守下的自由对话任务（调度只跑已保存工作流）。
- 不做自动登录、验证码识别、指纹/UA 伪装、多账号池（主计划 §8 一贯立场）。
- 不做对外 MCP server / 开放 API。
- 不引入外部编排框架与重型图表库（D3/ECharts/AntV 一类）。**已按 5.10 开这一条例外**：
  `@xyflow/react`（MIT，纯画布交互层，非数据可视化图表库）因用户明确要求算子图编辑器而引入，
  除此之外不引第二个图库。
- 不做云端会话同步 / 多设备续聊（SaaS 化时另立计划）。
