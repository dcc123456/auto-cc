# 计划十 · 求职主链体验与闭环（Job Journey）

> 立项：2026-11-19。目标是把「简历 → 意向搜岗 → 匹配解释 → 定制简历/招呼 → 确认外发 → 约面 → 面试准备」收成一条可追踪的求职主链，而不是继续增加孤立页面。
> 执行顺序：一次只推进一片。M1 由礼部交付 plan/spec 与**本地样例原型**；后续实现、验收和发布各有唯一责任部门与前置门禁。

## 0. 本片边界与裁定

1. **M1 只做体验与契约原型**：不新增生产 service、数据库表、迁移号、LLM 客户端或第二套工作流；不调用 `jd.capture.run`、`outbound.greet.perform`、`outbound.deliver.perform`，不访问真实招聘平台。
2. 原型从现有**对话首页**进入，在现有桌面壳内展示；可跳回岗位、简历、运行记录三个既有工作台。对话仍是控制面，原型不是第八个顶级菜单。
3. 原型使用明确标识的 `fixture.*` 本地样例。样例岗位、简历事实、约面草稿、操作记录和面试材料均不得写成真实平台结果或正式账本。
4. **外发计数在 M1 永远为 0**。确认卡只演示审批信息架构，按钮文案必须写明「仅演示，不外发」；即使完成演示确认，也不得调用任何外发桥接方法。
5. 事实锁定在 M1 只验证「生成内容引用的证据 ID 属于选定 JD 与样例简历」。正式生成与事实校验由 M2-B 复用 `resume.customize` / 知识库 / 既有事实校验完成，不用原型替代真实验收。
6. 沿用 React、Tailwind、lucide-react、i18next、`DeskButton` / `DeskSelect` / `Banner` / `Tag` 和 `viewTrail`。不引入依赖，不新增样式表，不手写 SVG，不在 JSX 中写裸文案；可逆的原型不新增遮罩弹窗。

### 1.1 选型与证据

本片是既有桌面应用的信息架构与交互原型，不引入新技术能力，因此不做新的框架选型。依据均为仓库内一手实现与已验收设计：

- `docs/design/ui-drafts/01-chat.html`：对话第一入口与计划/批准卡。
- `docs/design/ui-drafts/02-jobs.html`：六步闭环是界面脊柱，而不是新的功能页目录。
- `docs/design/ui-drafts/06-states.html`：空态、失败、风控、暂停等状态必须有明确恢复路径。
- `docs/design/ui-drafts/07-controls.html`、`09-dialogs.html`：五态控件、原因码、浮层与确认纪律。
- `docs/plans/09-workbench-ia/plan.md`：菜单边界、跨视图 `viewTrail` 与真实平台阻断记录。
- `packages/agent/src/metrics/funnel.ts`：约面无来源时 `count=null`，禁止伪造为 0。

否决项：①新增顶级「求职」菜单——会再长一个孤岛；②静态 HTML 评审稿——无法验证同一上下文在主链中的流转；③直接接真实服务做原型——会把 9.2 的阻断与真实外发风险带进 M1；④另建面试/约面数据表——属于 M2/M3 的正式实现范围。

## 2. 信息架构与关键屏

### 2.1 唯一入口与返回

- 对话顶栏新增「求职主链」按钮，在对话工作区内联显示原型；消息流与原型都只改 `display`，不卸载、不新增浮层。
- 原型标题旁常驻「本地样例 · 不外发」标识；关闭后回到原对话，原消息、滚动位置与输入草稿不变。
- 原型的岗位、简历、运行记录出口复用 `advanceViewTrail`，关闭原型后进入既有工作台并显示来源面包屑。

### 2.2 六步关键屏

| 步骤    | 用户动作                               | 画面必须回答                                 | 上下文写读                                      |
| ------- | -------------------------------------- | -------------------------------------------- | ----------------------------------------------- |
| 01 简历 | 载入样例简历、查看由事实生成的求职意向 | 用哪份母版、哪些事实可用、意向从何而来       | 写入 `fixture.resume.v1`；下游尚未生成          |
| 02 搜岗 | 按意向列出三个本地样例岗位并选一岗     | 为什么匹配、选中哪份 JD                      | 保留母版；写入 `jobId + jdVersion`              |
| 03 定制 | 生成样例变体与招呼语                   | 内容引用了哪些简历事实和 JD 要求、事实越界数 | 同时绑定母版与 JD；换岗必须作废旧产物           |
| 04 确认 | 请求确认、取消或完成「仅演示」确认     | 发什么、发到哪里、用哪版简历、是否真发       | M1 外发计数恒 0；记录原型操作而非正式账本       |
| 05 约面 | 登记一条样例约面草稿                   | 属于哪个岗位、是否只是草稿                   | 保留同一岗位与变体；不写正式约面来源            |
| 06 准备 | 生成自我介绍、八条问答与准备清单       | 每段内容依据哪条事实/JD 要求                 | 所有材料带来源 ID；可进入既有岗位/简历/运行记录 |

### 2.3 持续可见的版本条与操作记录

- 顶部三格：`resumeVersion`、`jdVersion`、`tailoredResumeVersion`；未产生时显示「尚未生成」，不拿上一岗位的版本冒充。
- 侧栏为「原型操作记录（非正式账本）」，只记录本地动作类型与上下文 ID，不记录 cookie、姓名、手机、邮箱、绝对路径。
- 换岗位时清空该岗位的变体、招呼、确认、约面草稿与准备材料，保留母版与新的 JD；这是防止上下文串线的关键负对照。

## 3. 统一上下文契约（M1 原型 → 后续正式实现）

```ts
interface JourneyContext {
  resumeVersion: string | null;
  selectedJobId: string | null;
  jdVersion: string | null;
  tailoredResumeVersion: string | null;
  confirmation: 'idle' | 'pending' | 'confirmed-demo';
  outboundAttempts: number; // M1 恒为 0
}
```

正式实现时上下文归 L3 主链服务/既有 `workflow.runner` 所有，对话与面板只消费同一快照。不得在 `ChatPanel`、`JobLabPanel`、`ResumeDesk` 各存一份可独立修改的生产真相。M1 的 `useReducer` 仅是样例状态机，文件与命名均带 `prototype`，后续不得被当成生产 service 直接复制。

### 3.1 来源与事实锁定

- 样例简历事实使用稳定 ID：`experience` / `performance` / `testing`。
- 每份样例 JD 使用稳定要求 ID，例如 `JD-A.R1`。
- 每份定制材料、自我介绍与问答均携带 `resumeFactId + requirementId`；不允许出现无来源的公司、职位、时间或数字。
- 正式生成必须复用既有事实校验并在事实违规时阻断外发；M1 画面中的 0 只代表样例引用检查，不代表正式模型已验收。

## 4. 状态、风控与恢复

原型提供可切换的七类**演示状态**，与业务样例数据分开，避免为了截图篡改正式库：

| 状态 | 必须表现                                    | 恢复/阻断口径                               |
| ---- | ------------------------------------------- | ------------------------------------------- |
| 空载 | 未载入简历时说明第一步，不显示 0 个真实岗位 | 载入本地样例后开始                          |
| 加载 | 显示进行中，已有上下文版本条仍可读          | 不重复提交，不以加载结束冒充动作成功        |
| 失败 | 显示结构化失败语义与重试入口                | 重试前先重读上下文，不生成成功回执          |
| 风控 | 明确暂停、外发不可用、需要人工接管          | 不识别/绕过验证码；恢复前必须重读页面与账本 |
| 暂停 | 保留当前版本与操作记录，停止后续动作        | 只能由显式恢复继续                          |
| 恢复 | 显示已对账、恢复点与未盲目重发              | 只恢复未完成动作，成功动作不重放            |
| 正常 | 回到当前步骤，无虚假成功徽标                | 样例与正式结果始终分标                      |

### 4.1 后续正式安全判据

1. **备份与隔离恢复**：迁移前备份；在隔离副本恢复后逐表核对行数、主键与关键字段一致，再允许迁移。不得在用户库上边修边验。
2. **去重**：至少按 `platform + target + action + resumeVersion` 判定；同一目标同一动作同一简历版本不得重复消耗额度或重发。
3. **一键停用**：停用后新增 greet/deliver 外发与账本成功行均为 0；已成功的历史记录保留，不能删除后假装没发生。
4. **失败对账**：页面回执、适配器状态、`usage.ledger`、`delivery_records` 与去重记录先对齐，再决定续跑；任何未知结局都按「可能已发生」处理，禁止盲目重发。
5. **隐私**：日志、截图、诊断与原型样例不含真实个人数据；正式材料只显示脱敏摘要与来源 ID。

## 7. 操作与验证

### 7.1 原型操作

1. `pnpm dev`，打开应用首页；如隐私声明出现，先阅读并确认。
2. 对话顶栏点「求职主链」→「载入样例简历」→「按意向搜样例岗位」。
3. 在三个样例岗位中选一个，生成事实锁定样例；检查母版、JD、变体三个版本读数。
4. 点「请求确认」：未确认外发为 0；再点「确认（仅演示，不外发）」：仍为 0，且无 `outbound.*` 调用。
5. 登记样例约面草稿并生成面试准备；核对自我介绍、八条问答、准备清单及来源 ID。
6. 通过「状态演示」切换空载/加载/失败/风控/暂停/恢复；从操作记录进入既有运行记录，或跳回岗位/简历。

### 7.2 验收方法

- U：原型 reducer 负对照与全链单测；不访问网络、不写数据库。
- V：CDP harness 固定 `--url 5173`，按条目截关键屏并保存 DOM 读数；同批图片 `md5 -q | sort | uniq -c` 去重。
- C：`pnpm typecheck` / `pnpm lint` / `pnpm format:check` / `pnpm test`，日志写文件后读取真实退出码，禁止用管道尾段充当门禁结果。
- 外发负对照：原型源码不出现外发桥接调用；活体 `data-outbound-attempts=0`，操作记录明确「非正式账本」。
- 真实平台、真实模型生成、正式约面入库、Windows/Linux 安装均不在 M1 验收中冒充完成。

## 8. 反向验证

- 不新增顶级菜单：原七项导航与既有 `data-action` 不变；入口只在对话顶栏。
- 不新增第二套业务链：原型零桥接调用，正式切片必须接既有 runner/service，不得把样例 reducer 提升为第二套生产状态。
- 不用样例伪造真实结果：所有样例标题、约面和操作记录均有原型标识；真实外发阻断继续引用 9.2-05/06/08。
- 不用 V 截图替代逻辑负对照：换岗作废、非法确认、八条问答来源由 U 兜底，V 只证明画面与一轮操作。
- 不用「无真实个人数据」代替脱敏测试：M1 只用虚构样例；正式隐私脱敏由 M4-A 单独攻击验证。

## 9. 回滚与风险

- M1 回滚只需移除对话入口、原型三文件、双语 key 与 P10 文档；无数据库迁移、无配置变更、无用户数据恢复动作。
- 若原型影响既有对话布局或验收锚点，先撤入口保留 plan/spec，不修改旧 `data-action` 来迁就新画面。
- 共享工作树只按 pathspec 提交本片文件；提交后逐行核对 `git show --stat --name-only HEAD`，不得吞入其他部门改动。
- 当前最大风险是把「样例可走通」误读为「真实闭环已通」。因此 M1 的完成口径只覆盖体验契约，M2～M4 未验项必须持续可见。

### 12.2 无人值守投递的授权模型

**原则**：授权把"逐笔点头"换成"范围授权"，代价是范围必须写死、可核对、可立刻收回；范围内视为已确认，范围外一律 0。

#### 12.2.1 授权单三要素

| 要素     | 取值口径                                                                                          | 默认               | 缺失/越界后果                                                            |
| -------- | ------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------ |
| 日限额   | 本轮无人值守每天允许推进的**岗位数**，整数 1–10；与 `entitlement.gate` 的日限额**取小**，绝不放大 | 5 岗/天            | 未设不启动；用尽即停并在界面写明「今日额度已用尽」，不静默继续           |
| 岗位范围 | 从本次意向搜岗返回的岗位里**显式勾选**，最多等于日限额；不接受「全部岗位」或按关键词模糊扩展      | 空（必须用户勾选） | 未勾选不启动；集合外岗位不放行，拒绝原因可读                             |
| 简历版本 | 必须是本轮已生成并通过事实校验的 `tailoredResumeVersion`，并与母版 `resumeVersion` 一并绑定       | 无                 | 未定制或未过校验的岗位不得进授权范围；外发前版本不符即拒，不换旧版本顶替 |

**名额口径**：日限额按**岗位**计，不按动作计。同一岗位一次授权内最多 1 次打招呼 + 1 次投递，两者共享同一个名额；三类动作的既有日上限（搜索/打招呼/投递）仍然是另一道闸，两者取小。

**2026-11-20 PMO 裁定（逐岗变体的准入护栏；表内「简历版本」一行按此执行）**：授权单绑定**母版**；批量执行器为每岗
生成定制变体时，该变体必须同时满足三条——①同一授权母版血缘（`parentDocId` = 授权母版）②JD 归因命中本岗
（变体的 `jdId` = 本笔 target）③事实校验通过（变体只能经 `resume.generate.accept` 产生，违规时不产生变体）。
缺任一条按越权拒绝（`OUTBOUND_RESUME_VERSION_NOT_AUTHORIZED`）。原文「简历版本必须是本轮已生成并通过事实校验的
`tailoredResumeVersion`」不改写：本裁定说明的是「一轮多岗各自定制的变体」如何满足它，而不是把版本维放开成任意值。

#### 12.2.2 生效、失效与停点

1. 授权单与「本自然日 + 本次无人值守运行」绑定；运行结束、用户停用、应用退出即失效。
2. **应用重启后不自动续跑**：未完成岗位转成待办，界面给出「继续需要你确认一次」；用户确认后从断点继续，额度按账本现算，不重复扣。
3. **跨日不自动续跑**：本地自然日切换后，前一天未完成的岗位不自动继续，需重新授权或确认。
4. 暂停（风控、停用、额度用尽）保留断点与已成功记录；已成功的动作不重放，未知结局按「可能已发生」处理。

#### 12.2.3 频控与人类化节流

- 两笔外发之间取 `outbound.throttle` 的随机区间（默认 45–150 秒），页面动作（滚动、逐条读详情）走另一档（默认 300–900 毫秒）；**不得配置为 0，也不得 min>max**（配置面挂载即拒）。
- 判据不是「够慢」而是「不像节拍器」：一轮内实际间隔不得全部相同。
- 每笔外发前先问额度闸门，被拒的这一次不消耗额度、不留成功账。
- 无人值守不因「反正没人看」缩短间隔；用户不在场不是放宽节奏的理由。

#### 12.2.4 风控与验证码

- 命中验证码/风控即**整轮暂停**：不跳过该岗继续，不再发起任何外发；已成功的记录保留。
- 不识别、不规避、不重试同一动作；不自动恢复。
- 通知：回到应用必须看到常驻横幅（原因原文 + 「需要你来」+ 恢复入口）；托盘可见提示。系统通知能发则发，但系统通知不可用不构成静默放行的理由。
- 恢复必须由用户在场确认，且**先对账再续跑**：页面回执、账本、投递记录、去重记录先对齐；未知结局不盲目重发。
- 机检靶页是本地仿站的风控开关（200 验证页/403 限流页两类）；真实平台风控**不主动构造**，自然遇到才在用户在场时取证。

#### 12.2.5 一键停用

- 停用入口在无人值守运行可见处常驻，不藏在二级菜单。
- 点击后 ≤1 秒不再发起新的外发；正在飞的那一笔按未知结局处理（先对账，不重发）。
- 停用不删历史、不补写成功账；停用期间对账只读，不把「事后查到成功」写成新的一笔。
- 恢复要用户显式确认，并从断点续跑。

#### 12.2.6 外发落账与可审计

- 每笔成功外发在**同一事务**里写 `usage.ledger` 与 `delivery_records`；失败一侧不写成功账。
- 任一笔外发都要能回答五个问题：发了什么（正文/附件版本）、发到哪（平台 + 岗位/会话坐标）、用哪版简历、平台回执是什么、由哪次运行发起。
- 审计只读：按账行可反查到对应页面回执；查不到回执的账行视为对账异常，冻结后续外发。

#### 12.2.7 去重与越权

- 四元组 `platform + target + action + resumeVersion` 永不重发、不重复扣额，跨入口、跨运行、跨重启一致。
- 在四元组之上再加一条**同岗 24 小时上限**：同一岗位 24 小时内最多 1 次打招呼 + 1 次投递，换简历版本也不叠加。
- 越权外发为 0，五种情形逐一判：①岗位不在授权集合；②超出授权日限额；③简历版本未授权或未绑定；④授权窗口外（跨日、运行已结束）；⑤应用重启后未重新确认。每次拒绝留原因，失败一侧不落成功账。

#### 12.3.4 失败与阻断标注

- 任何一步失败当场标 `[!]`，写清三件事：**缺什么**（定位未取证 / 风控 / 账号状态 / 环境）、**谁解除**、**解除条件**。
- 不得用仿站结果替代真实平台结论；不得把半程写成通过；失败一侧不落成功账。
- 同一动作重试最多一次，且必须换了原因才重试；重试前先对账。

#### 12.3.5 对账口径

页面回执 ↔ `usage_ledger` 行 ↔ `delivery_records` 行 ↔ 四元组记录，四条**逐笔**对齐（含 1 笔失败样本）；不一致即停后续外发并标 `[!]`。失败笔的四方一致结论是「未发生」，不是补一条成功账。

#### 12.3.6 时间盒

本轮真实链路必须在**同一次在场窗口**内完成；两次窗口之间不得把半程累加成通过。窗口结束仍未走完的步骤，按 12.3.4 标 `[!]` 并写明下一次窗口要补哪一步。

### 12.4 追踪与统计口径

#### 12.4.1 岗位状态机（八态）

| 态            | 进入事件（唯一来源）                    | 允许后继                             |
| ------------- | --------------------------------------- | ------------------------------------ |
| `captured`    | 抓取入库（jobs 表，带抓取时刻）         | `matched`、`closed`                  |
| `matched`     | 产生匹配读数（含逐条理由）              | `tailored`、`closed`                 |
| `tailored`    | 定制简历与招呼生成且事实校验通过        | `greeted`、`delivered`、`closed`     |
| `greeted`     | 打招呼成功（页面回执 + 账本）           | `replied`、`closed`                  |
| `replied`     | 收到对方入站消息                        | `delivered`、`interviewed`、`closed` |
| `delivered`   | 投递成功（页面回执 + 投递记录）         | `replied`、`interviewed`、`closed`   |
| `interviewed` | 用户登记一条约面（见 12.4.3）           | `closed`                             |
| `closed`      | 用户标结束，或系统判定岗位下架/无法继续 | 可重开一次，回到结束前的态           |

- **按事件推进，不按时间推断**：没有对应事件就不推进；同一事件重复到达不重复推进。
- **允许跳过，但跳跃必须有回执证据**：站点上可以不经打招呼直接投递，所以 `tailored → delivered` 合法；没有回执的跳跃一律拒绝。
- **只进不退**：唯一例外是 `closed` 重开一次，重开要留痕（原结束态、原因、时间）。
- 每次迁移记 `jobId + from + to + 时刻 + 来源引用`（消息 id / 账本行 id / 投递记录 id / 用户登记 id）。

#### 12.4.2 结束与重开

`closed` 必须带原因：对方拒绝 / 无回音 / 我放弃 / 岗位下架。结束不删历史、不影响已发生的账；重开回到结束前的态并保留两次结束记录。

#### 12.4.3 约面唯一来源

- 约面的唯一来源是**用户登记的一份约面记录**：岗位 + 约面时间 + 方式（电话/视频/现场）+ 来源引用（平台消息 id，或用户口述并记录登记时间）。
- 招聘方在平台上直接给的约面通知也算，但必须由用户登记时引用那条消息；不引用就不计入。
- 一岗多条约面按**岗位**计 1；未约面的岗位不计入、也不补 0。
- 没有登记来源时，漏斗该级显示「无来源」；登记服务未挂载时显示不可用——两者都不是 0（沿用决策十五的口径）。

#### 12.4.4 漏斗五级口径

| 级          | 口径                                     | 来源                | 无源显示      |
| ----------- | ---------------------------------------- | ------------------- | ------------- |
| `search`    | 区间内抓取入库的岗位数                   | jobs 表（抓取时刻） | 不可用 + 原因 |
| `greet`     | 区间内成功打招呼数                       | 账本（成功行）      | 不可用 + 原因 |
| `reply`     | 区间内收到对方回复的岗位数（按岗位去重） | 会话消息            | 不可用 + 原因 |
| `deliver`   | 区间内成功投递数                         | 投递记录            | 不可用 + 原因 |
| `interview` | 区间内已登记约面的岗位数（按岗位去重）   | 约面登记            | 不可用 + 原因 |

- 五级必须来自**一次** `funnel.query` 读数，界面不各自拼数。
- 区间含头不含尾，按**本地自然日**切；日界由发起方按本地时区算。
- 缺服务给原话原因，不降级成 0（0 读起来是「一条都没发生」，与「没有这个数据源」是两件事）。

#### 12.4.5 趋势

- 按日聚合上述五级，加外发成功数与失败原因 Top3；区间 7 天 / 30 天两档。
- 与漏斗**同源、同区间口径**，不允许渲染层自算第二套统计。
- 无源不画线（给不可用文案）；区间内某天没有数据就是 0，不是缺测。

#### 12.4.6 逐条一致与抽样

同一区间内，漏斗各级与趋势的日均值必须等于按同口径逐条数出来的数，**差异为 0**；每片至少抽 3 笔（含 1 笔失败）逐笔对账，抽样结果进证据。差异 ≠0 阻断发布。

### 12.8 待验证假设（不编数据，写明怎么验）

1. **5 岗/天是否合适**：产品判断取保守值，无任何使用数据支撑。→ 用首轮用户在场试用与 7 天趋势回看调整；调整只改授权默认值，不改四元组与频控。
2. **10 分钟门槛**：单用户首轮计时只证明路径无阻断，不构成分布结论。→ 需要 ≥5 名真实用户样本才能写成指标结论；样本不足时文档只写「待验证」。
3. **重启后不自动续跑**：安全优先的取舍，可能牺牲「关掉电脑第二天继续」的期待。→ 首轮用户测试问一句「你上次没跑完会怎么办」，按回答决定是否做「第二天一次性确认」。
4. **同岗 24 小时上限**：防连发，可能挡住「对方回了、想当天补发简历」的合理场景。→ 用回复事件作为例外条件做一次用户测试，未验证前不放宽。
5. **约面登记负担**：登记是约面唯一来源，用户可能不愿手填。→ 首轮观察登记率与放弃原因；若负担过高，再评估从会话消息一键带入（仍须用户确认，不自动判定）。

### 13.1 产品判断（先定方向，再拆条目）

1. 三个 P0 都是**「新手看不到路」**，不是功能没做：第一入口要签全自动才能打字、导入成功后别处读不到简历、缺口用 `expectRole` 这类键名。
   要修的是**指路与一致性**，不加新功能。
2. 后半程没走**不等于后半程没问题**——它连读数都没有。所以本轮既不许拿 fixture 结果当「新手已走完」的证据，
   也不许因为没读数就把它当通过：改造后按 13.5 补走，证据必须写明 fixture。
3. 走查人自报的「最想先改 3 条」（K3/K2/K1）与本判据的 P0 集合一致，**采纳**；P1/P2 不按吐槽音量排序，按「挡不挡下一步」排。
4. 易用判据必须**可测**：每屏下一步、四态出口、禁用原因可见、双语无裸 key、窄窗不溢出。不接受「体验更好」这类不可验收的表述。

### 13.2 2026-11-21 dated 裁定（默认档位口径，原判据与旧文案保留不改写）

**裁定**：新用户默认档位是**「只建议」（最保守）**；**授权单生效后**底栏才显示「**无人值守：已授权 N 岗**」；
撤销授权或一键停用后立即回到「只建议」。隐私声明、底栏、对话页三处措辞必须一致。
**依据**：走查实测干净实例 `autonomy="auto"`，而首屏隐私声明写「默认档位是最保守的『只建议』，外发动作一个都不会自己出手」——
两处直接打架，且是涉及外发的风险表态，必须由产品定口径而不是让两段文案各自为真。判据落 10.10-04。

### 13.3 可测的易用标准

1. **首屏三入口**：导入简历 / 看匹配岗位 / 授权投递，各一个按钮，点了就到对应页。
2. **关键链每屏三问**：我在哪（当前位置）、下一步是什么（可点）、从哪退出（回上一步或去别的页）。
3. **四态必有原因与恢复**：空、加载、失败、风控；风控另有「需要你来」、一键停用、不自动恢复（与 10.6-04 同一口径）。
4. **禁用必给原因**：可见文字，不能只挂 `title`；旁边给可点的下一步（例如「先去登录 BOSS」）。
5. **文案全双语、无裸 key、无内部术语**：`JD` 这类平台通用词保留但首现处给白话注解；键名、枚举、cron 不得直接出现在界面上。
6. **窄窗不溢出**：620px 与 486px 两档，`document` / `root` 宽度不超窗。
7. **≤10 分钟**：定义沿用 10.9-01（首屏可交互 → 第一笔真实外发成功落账），本轮只补测量方法（10.10-21）。

## 14. 新壳：Home 总览 + 全局助手（2026-11-21 用户裁定；spec 10.11 判据区）

**裁定来源**：用户 2026-11-21 定方向——「对话页面没什么实用性，改成全局智能助手悬浮组件，任何页面都能呼出、点击就能对话、能帮用户干活；原对话页做成 Home，展示趋势数据、summary、关键节点入口」。
三份提案（产品 `docs/design/proposals/2026-11-21-home-assistant-product.md`、视觉 `…-visual.md`、技术实测）合并后，PMO 按推荐定稿、用户未反对即执行：
**C 停靠让位**、**Home 显示最近 5 笔外发**、**角标只在「需要你」时亮**；页首**单一动态主行动**、summary 拆 **4 数字 + 2 状态行**、站点全屏呼出**先退全屏 + toast**。

**效力与边界**：本节只新增口径，不改既有判据原文；实施落第 11 片；新壳判据区 = spec **10.11**（编号续用未占用段，不是新切片）。旧对话页的信息不是删除，是按 §14.5 逐项安置。

### 14.1 三条不变式

1. **不新增顶级菜单**：左轨仍是 7 项，第一项仍是同一位置、同一 key（`chat`），只把标签改成「首页」。改 key 等于拆掉 harness 与冒烟脚本的既有凭据，收益为零；新壳的判断一律用 `data-testid` 区分 Home 与助手。
2. **不新增第二套基础设施**：不新开窗口、不新增 IPC、不自建统计与状态存储。助手是既有 `ChatPanel` 的停靠变体；Home 的数字只读既有服务。
3. **不新增第二执行通道**：助手的每个动作仍走 `agent.loop` 的「计划 → 人确认 → `entitlement.gate` / `outbound.authorization`」。悬浮层只负责入口与展示。

### 14.2 形态（C：停靠让位，不做浮动覆盖）

| 项       | 规格                                                                                | 理由                                                                                                        |
| -------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |

| 面板     | 主区 `main` 内右沿，`inset-y-3 right-3`，宽 `min(420px, 100%-24)`                   | 父级是 `main` 就天然不伸进站点那一栏；不靠 z-index 赌覆盖                                                   |
| 三态     | 展开 / 最小化（48px 状态条：一行状态 + 展开 + 关闭）/ 收起（只改 `display`）        | 收起不丢草稿、run 订阅不断；最小化保留"助手在干什么"的一句话                                                |

| 键盘     | `Ctrl/⌘+J` 全局呼出并聚焦输入卡；`Esc` 关闭、焦点回胶囊；面板不锁 Tab               | 非模态：背后页面必须还能用                                                                                  |

### 14.4 助手口径

#### 14.4.1 职责六类

| 类别         | 具体                                         | 落到哪                              |
| ------------ | -------------------------------------------- | ----------------------------------- |
| 解释与指路   | 解释 JD / 母版 / 授权 / 回执，说清下一步点哪 | 读同一份服务读数，纯文本            |
| 带去处的跳转 | 「带我去看这个岗位 / 这份简历」              | `viewTrail` 跨视图推进              |
| 只读汇总     | 「今天投了几份、谁回了、还剩多少额度」       | 只读 `funnel` / 账本 / 追踪 / 授权  |
| 起草计划     | 「按这 3 个岗位准备一轮投递」→ 出计划卡      | `agent.loop.propose`；人确认才执行  |
| 执行既有动作 | 搜岗、入库、定制简历、生成招呼、准备投递     | 既有 agent 工具；外发经闸门与授权单 |
| 值守提醒     | 风控暂停、待办未跑、审批待确认、额度用尽     | 读执行器与授权读数，角标提示        |

#### 14.4.2 七条红线（逐条可判）

1. **不绕闸门外发**：助手没有第二套外发通道，任何外发都经 agent loop → 闸门 → 账本。
2. **不代签**：计划确认、逐步批准、授权单开启与恢复只能人点；「上次点过」不构成本次许可。
3. **不自开/自改授权单**：日限额、岗位范围、简历版本只能人设；助手只能把建议写进计划卡。
4. **不编读数**：服务没挂载就说不可用，不显示 0、不给估计值。
5. **不存第二份状态**：会话、run、审批、执行进度都归既有服务；收起重开读同一份。
6. **不做第二套会话/第二套 agent 循环**：复用同一个 chat session 与 agent run，不做多助手并发。
7. **不访问真实平台**：自动化仍只打本地仿站，真实平台只由用户在场手验（AGENTS.md §7.2）。

#### 14.4.3 档位与审批（助手永远比人低一档）

| 档位                 | 助手能做                             | 外发                                                | 备注                      |
| -------------------- | ------------------------------------ | --------------------------------------------------- | ------------------------- |
| 只建议（新用户默认） | 解释、跳转、只读汇总、起草计划       | 无；计划卡只给人看                                  | 10.10-04 口径             |
| 半自动               | 计划 → 人确认 → 执行；外发前逐步批准 | 人点批准才发                                        | 助手不代点确认            |

#### 14.4.4 上下文与状态归属

- 呼出即当前会话；Home 的「问助手」与顶栏胶囊打开的是**同一份会话**（同一个 chat session，不是两个）。
