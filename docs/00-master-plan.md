## 1. 项目定位

### 1.1 形态

auto-cc 是一个**桌面端 Application**，不是网页、不是 CLI、不是浏览器扩展宿主。

| 维度               | 结论                                                             | 依据                                                         |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| 运行时外壳         | Electron                                                         | 必须在用户本机持有 Chromium 渲染层与 Node 主进程；见 §6 选型 |
| 平台               | Windows / macOS / Linux **三端都要出安装包**                     | 硬性需求                                                     |
| 后端               | Node.js 主进程，内嵌 **Cordis** 插件框架                         | 硬性需求（功能以插件挂载）                                   |
| 前端               | React 渲染进程                                                   | 硬性需求                                                     |
| 分发               | electron-builder 产出 `nsis`/`dmg`/`AppImage`+`deb`              | 见 §6.5                                                      |
| **自带浏览器内核** | app 内嵌 Chromium，不依赖用户系统的 Chrome/Edge                  | 硬性需求，见 §1.4                                            |
| **登录态持久化**   | 招聘站登录一次长期复用，不必每次重登                             | 硬性需求，见 §1.4                                            |
| **零前置依赖**     | 用户只装这一个 app，**不需要**装 Node / Chrome / Python / Docker | 硬性需求，见 §1.4                                            |

### 1.2 产品目标

为中国求职者提供一个**自动化求职助理**，把「找工作」从重复劳动变成一条可托管的流水线：

```
   ①搜索 JD        ②读 JD + 建档      ③生成话术         ④打招呼/沟通        ⑤按 JD 优化简历      ⑥择机投递
  BOSS/猎聘/拉勾  →  结构化 JD 库   →  开场白/追问/回绝  →  自动发送+回复监听  →  命中缺口的简历内容  →  自动发简历
```

**闭环判据**：一条 JD 从被发现到简历送达，用户不需要手动操作浏览器；用户只做两件事 ——
设定画像与筛选条件（前置）、审批高风险动作（可选的 human-in-the-loop 开关）。

### 1.3 主界面 = 对话式 Agent；主流程 = 工作流（两者是一体两面）

**产品主界面是一个聊天窗口**（对齐当前主流 agent app 形态：Qoder / WorkBuddy 一类），
不是功能页目录，也不是表单堆叠。用户在对话里用自然语言表达意图，agent 生成工作流、
或直接驱动内嵌浏览器执行，全过程在对话流里可见、可中断、可接管。

两条驱动路径，**共用同一套 service 与同一套护栏**：

| 路径        | 用户做什么                                                    | 系统做什么                                         | 落到哪                                                |
| ----------- | ------------------------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------- |
| A. 对话驱动 | 「帮我找上海 3 年内前端岗，打招呼并投我那份带 Golang 的简历」 | agent 规划 → 生成/选用工作流 → 逐步执行 → 回报结果 | L4 `plugin-chat` → L3 `workflow.runner` → L2 services |
| B. 面板驱动 | 直接在工作流面板点运行/暂停/重试预制流程                      | runner 按声明执行，进度回显                        | L4 workflow 面板 → 同一 `workflow.runner`             |

要点（硬性）：

- **工作流仍是一等公民**：对话的价值不只是「一次一次地聊」，而是把可复用的做法**沉淀为工作流**
  （生成 → 命名 → 保存 → 再运行）。agent 每次多步执行都应可一键转为工作流。
- 对话是**控制面**，不是新的业务逻辑容器：agent 只能调用已注册的 tool（= service 方法），
  **禁止**在对话链路里长出第二套抓取/发送/投递实现。
- 搜索、话术生成、打招呼、简历优化、投递都只是**工作流节点 / agent 工具**，
  界面不提供绕过主流程的捷径入口（调试面板除外）。
- 每个节点必须可观测（状态、耗时、失败原因、可重试）且可停靠（人工审批节点）。
- 技术上由 L3 `workflow.runner` 承载，**跨 P2~P5 复用**，不是某个页面的私有逻辑。
- 「绕过工作流与 agent 工具面直接调 service」视为设计缺陷。

### 1.4 分发与浏览器内核约束（硬性，直接约束技术选型）

**用户只下载这一个 app，并且不需要自己动手装/下任何东西。** 由此推出四条不可违反的规则：

1. **同一时刻只有一套「被驱动的浏览器运行时」当自动化宿主，默认是内置内核**：驱动招聘站的浏览器默认就是
   **Electron 自带的 Chromium**，通过 `WebContentsView` 嵌在 app 窗口内 ——
   用户能亲眼看到自动化正在做什么，也可随时接管手动登录，且零额外下载。
   **2026-09-30 需求方更正**：本条**不是**「禁止引入第二套浏览器内核」。真实约束是
   「用户不用额外手动下载其他软件」，因此 app **可以**自行集成/自动下载它需要的插件与依赖
   （含 Playwright/Puppeteer 的 Chromium 这类独立宿主运行时），只要满足：
   ①下载由 app 完成（构建期内置，或首启动/使用时自动拉取 + 校验 + 可回滚 + 失败有显式降级），
   用户全程零手动操作；②**功能完整性优先**——内置内核补不上的能力缺口可以靠它补齐；
   ③换宿主后仍然只有一个宿主在驱动页面（不许两个内核并行各跑一半）。
   默认仍用内置内核：它已经满足可见 + 可接管 + 零下载，而 §9.7 的对账显示已登记的两条缺口
   （网络空闲等待 → 2.3-06、文件上传 → 2.6-04）都能在 Electron 通道内补上，
   **一旦出现补不上的缺口，自动下载宿主内核就是许可方案，而不是禁区**。
2. **用户零手动下载**：安装完成后，运行期不得要求用户自己去装任何东西（内核、字体、模型、词典、依赖、驱动）。
   需要外部产物时由 **app 自动获取并管理**：构建期下载并打进包是首选（离线可用、启动零等待），
   运行期自动下载是许可的备选，且必须带完整性校验、失败重试与「不下载也能降级运行」的明确路径。
   CI 构建期允许下载，最终用户不允许自己动手。中文字体子集、embedding 模型等一律打进包，或降级为可选插件并显式标注。
3. **禁止用户机现场编译原生模块**：用户没有 Node 也没有 VS Build Tools。
   含原生模块的依赖必须①提供覆盖三端 Electron ABI 的预编译产物，或②纯 JS，或③用 Node/Electron 内置能力。
   → 持久层定为 **`node:sqlite`**（Electron 44 内嵌 Node 24 已内置，实测可 `require('node:sqlite')`），
   放弃 `better-sqlite3`（需 `electron-rebuild`，构建期可解但风险与复杂度更高）。
   同理，P4 的向量检索必须选纯 JS 或内置方案，不引入需编译的原生扩展。
4. **登录态持久化**：自动化流量走独立会话 `session.fromPartition('persist:<platform>')`（每个平台一个 partition），
   cookie / localStorage / IndexedDB 落在 app 的 userData 目录，随重启保留；
   用户在内嵌视图里手动登录一次即可长期复用，工作流跑完不清登录态。
   - 自动化会话与主 app UI 会话**必须隔离**（互不共享 cookie）。
   - 界面提供「当前登录状态」指示与「重新登录 / 退出登录」入口；退出登录不清业务数据。
   - 登录失效必须被检测并显式提示，禁止静默失败或假装成功。
   - 凭证属敏感数据：日志、诊断包、截图中一律脱敏（§8）。

### 1.5 商业化预留（本阶段不实现，但不许堵死）

现阶段完全本地、免费、无账号；架构必须能长出这个付费模型：
**「有限次自动投递」→ 超出后付费解锁额度**。因此 P1 就固化以下接线面，之后不返工：

1. **所有外发动作必须经过 quota gate service**（`entitlement.gate`），
   即使当前实现是"无限额度直通"。禁止任何代码绕过 gate 直接调 send。
   该约束**可机检**：P2 起 `browser.greet` / `resume.deliver` 的调用点必须位于 gate 之后。
2. **本地用量账本**（`usage.ledger`）：每次消耗记录 `(action, jobId, workflowRunId, ts)`。
   计费口径先落盘，将来上云只是把账本同步出去，而不是重新埋点。
3. **`entitlement` service 抽象**：`check(action, ctx) -> { allowed, remaining, reason }`。
   本地实现返回无限；将来 SaaS 实现返回配额。
   **上层业务代码不允许出现任何"是否付费"的 if 分支**，只看 gate 结果。
4. 反推要求：可生成稳定的本地安装/设备标识（将来绑定授权用），但**不上传任何个人信息**；
   一切联网校验必须**可选**且失败可降级为本地模式 —— 断网不能让已购能力失效。
5. 数据模型预留 `source`（local / saas）与 `remoteRef` 可空字段，避免未来加同步时改表语义。

> SaaS 服务端本身、支付、账号体系均在 P1~P5 之外，本计划只保证 §1.5 这五个接线面存在且被测试覆盖。

### 1.6 明确的非目标（防止范围漂移）

- 不做需要用户自行安装 Node / Chrome / Python 的「开发者式」部署路径。
- 不做需要用户自己去找、自己去装的外部依赖（app 自行内置或自动下载，见 §1.4）。
- 不做 SaaS / 多用户服务端 / 支付（本阶段只留 §1.5 接线面）；单机单用户，数据全在本地。
- 不做「代刷简历」「批量海投绕过平台风控」的对抗能力；反检测不是设计目标（见 §8）。
- 不自研浏览器内核；不自研 PDF 排版引擎；不训练模型 —— 三源项目的能力**按功能内核抽取复用**。
- 不做移动端。

### 1.7 对话式 Agent 的约束（形态新，风险也新，前置写清）

1. **工具面 = service 白名单**。agent 只能用注册的 tool（每个 tool 是一个 service 方法的声明式契约：
   名称、参数 schema、副作用等级、是否需要确认）。没有 tool 声明的能力，agent 不可见也不可调用。
2. **副作用分级 + 确认策略**：只读（搜索/读 JD/查库）可自动执行；写本地（建档/生成内容）可自动执行；
   **外发（打招呼/投递/发送消息）必须逐级确认**，且一律经 `entitlement.gate`（§1.5）与 human-in-the-loop（§8）。
   确认策略是配置项，但默认值永远是「最保守」。
3. **自治档位**（显式、可切换、界面上常驻可见）：
   `建议模式`（只给计划不执行）→ `半自动`（逐步确认）→ `全自动`（仅白名单动作 + 频控 + 可随时叫停）。
   不存在「隐性全自动」：档位状态必须能在截图里读出来。
4. **计划先于执行**：多步任务先生成可见的执行计划（步骤 + 预期副作用 + 预计额度消耗），
   用户确认后才开始跑；执行中每步在对话流留下可折叠的工具卡片（入参摘要、结果、耗时、证据链接）。
5. **可中断、可接管、可回滚解释**：任何时刻用户能暂停并手动接管浏览器；agent 恢复时必读用户手改后的页面状态，
   不假设自己上次离开时的 DOM 仍然成立。
6. **上下文与成本可控**：页面快照采用「引用 + 摘要」而非全量 HTML 灌进 prompt；
   会话历史可压缩但保留关键事实（已投目标、额度消耗、用户否决过的做法）。
7. **对话内容不得写入敏感数据明文**（§8 脱敏同样适用于会话持久化）。
8. **失败不谎报**：tool 失败必须原样回报给用户（附证据），禁止 agent 用「已完成」的措辞掩盖部分失败。

## 2. 三大成熟功能源项目的分析结论

用户明确：**这三个项目不适合直接嵌入**，需要判断后按需抽取。分析结论如下（详细逐仓库分析见
`docs/research/source-repos-analysis.md`）。

| 源项目            | 原形态                                     | 可抽取的「功能内核」                                                                               | 必须丢弃的宿主耦合                                                                   |
| ----------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `browser-copilot` | 浏览器扩展（WXT/Manifest V3）+ 配套 server | ①工作流引擎（步骤序列 + 断点续跑）②DOM 定位与语义选择策略 ③站点适配器（招聘站）④抓取的 JD 数据结构 | popup/options/background 生命周期、扩展消息通道、MV3 service worker 约束、扩展打包链 |
| `canva-pdf`       | 独立 Web 应用                              | ①简历模板模型（区块 + 数据绑定）②PDF 渲染与导出管线 ③版面度量（分页/字号/边距）                    | 其前端路由与状态管理、画布编辑器的独立宿主、其构建配置                               |
| `ai-resume`       | 独立应用                                   | ①简历 → 个人知识库的抽取建模 ②检索（JD 查询 → 个人经历命中）③缺口识别与内容生成提示词              | 其 Web 宿主、其独立的存储层与鉴权                                                    |

**抽取原则（对全部三个项目生效）**：

1. 只搬**纯逻辑与数据契约**，不搬宿主。凡是 import 了原项目 UI 框架、扩展 API、或原项目配置的，重写而非移植。
2. 搬过来的代码必须落进一个 Cordis 插件边界内，通过 Service 对外暴露，不得跨插件直接 import 内部文件。
3. 保留来源可追溯性：每个抽取模块在文件头注明源项目 + 源路径 + **许可证判定**，便于后续 diff 上游。
4. 站点选择器（招聘平台 DOM）**不硬编码进逻辑**，集中在 `platforms/boss` 这类适配器包里，因为它是腐化最快的部分。
5. **许可证门禁（取证后新增，优先级高于以上所有便利）**：
   `browser-copilot` 是 **PolyForm Noncommercial 1.0.0** `[实测 LICENSE + package.json]`，
   在商用前提下**只能 clean-room 重写其结构与协议，不得复制代码、prompt 文本与 UI 资产**；
   `canva-pdf` README 自述 MIT 但**仓库无 LICENSE 文件**，且依赖 `pdfjs-dist` / `mupdf` 为 **AGPL-3.0**
   → 抽取前须补授权文件，分发时附 NOTICE；`ai-resume` 同（README MIT、无 LICENSE 文件）。
   详见 `docs/research/source-repos-analysis.md` §1。
6. **三个源项目都不含招聘平台知识**：`zhipin|boss|直聘|猎聘|打招呼` 全部零命中 `[实测 grep]`。
   BOSS 直聘的选择器、字段顺序、打招呼话术、投递时机判定**必须自建**，不要假设可抽取。

## 3. Cordis 集成基线（已实测）

Cordis = `cordis@4.0.0-rc.10`（`cordiverse/cordis`，"Meta-Framework for Modern Applications"）。
以下语义已在 `.research-repos/cordis-spike/spi.mjs` 实测通过，**不是文档转述**：

```js
class JobService extends Service { static provide = 'jobs'; list() { ... } }

const kernel = (ctx) => { new JobService(ctx); };   // ctx.jobs 立即可见
kernel.provide = 'jobs';

const consumer = (ctx) => { ctx.jobs.list(); ctx.effect(() => () => cleanup()); };
consumer.inject = ['jobs'];
```

已验证的框架行为（构成后续架构的硬约束）：

- **A. 服务发布**：`new XxxService(ctx)` 即以 `static provide` 的名字挂到 `ctx`，作用域为当前 fiber。
- **B. 显式依赖**：插件用 `inject: ['name']` 声明依赖，未声明的 service 取不到（隔离是默认的，不是共享全局的）。
- **C. 资源回收**：`ctx.effect(() => () => teardown)` 随 fiber 卸载自动逆序执行 —— 浏览器实例、DB 连接、定时器都走这条路径，禁止手写 cleanup 钩子。
- **D. 依赖联动**：提供方被 dispose 时，依赖方自动卸载（实测 `f2.state` 回到 PENDING），service 恢复后自动重建 —— 这是**热插拔/热重载**的基础，P1 必须把它做成可运维能力（改插件不重启 app）。
- **E. 可观测**：`ctx.registry.size`、`fiber.state`、`ctx.logger` 提供运行时自省能力，P1 的调试面板据此实现。
- **F. API 不稳定**：官方 README 明示 API 未稳定。因此**所有插件只依赖本项目 `packages/core` 复导出的 cordis 类型**，升级 cordis 只改一处。

### 3.1 插件分层规范

```
L0 kernel      配置/存储/日志/事件总线            无 inject
L1 platform    浏览器驱动、站点适配器              inject: kernel
L2 domain      jd-store, resume-kb, copywriting   inject: kernel (+ platform 或彼此)
L3 pipeline    job-pipeline（串联 2 的业务流）     inject: L1+L2
L4 surface     ipc-gateway, devtools              inject: L2/L3
```

规则：只允许下层被上层 inject；同层禁止互相 inject（避免环）；跨层禁止跳级访问内部实现。

## 4. 主体计划拆分

四大主体计划。**执行顺序为串行**，因为 P2/P3/P4 都依赖 P1 提供的插件骨架与 IPC 契约，
P4 的产出是 P2 中「按 JD 优化简历」步骤的内容来源。

```
P1 搭建主体框架 ─┬─> P2 集成浏览器自动化 ──> P5(后续) 端到端流水线与打包发布
                 ├─> P3 PDF 编辑 / 简历生成
                 └─> P4 简历 → 个人知识库
                      （P3、P4 可在 P1 完成后并行；P2 与 P4 会合于 P5）
```

> **执行纪律（用户明确要求）**：一次只推进一个计划。当前计划未通过其 spec 的逐项验收之前，
> 不得开始下一个计划。禁止把 P1~P4 混在一次改动里实现。

### P1 · 搭建主体框架

目标：跑起来一个三端可安装、功能以 cordis 插件挂载、React 界面可见、且 **agent 能自己开页面看并直接操作测试** 的骨架。

| 子计划 | 内容                                                                                                                                  | 产出                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| 1.1    | 仓库与工程基线：pnpm workspace、TS 配置、ESLint/Prettier、提交规范、目录结构定稿                                                      | 可 `pnpm i && pnpm dev` 的空壳          |

## 6. 技术选型与理由

1. **Electron 而非 Tauri**：核心诉求是「驱动真实浏览器抓 JD + 复用 browser-copilot 的 DOM 逻辑」。
   Tauri 主进程是 Rust，Node 侧 cordis 插件体系与 CDP 生态无处安放。Electron 让 cordis
   直接跑在主进程 Node 里，且渲染层与自动化目标同为 Chromium。代价是包体大，可接受。
2. **自动化宿主默认为 Electron 自带 Chromium（`WebContentsView`）；Playwright/Puppeteer 不是禁区，但要按 §1.4 更正后的口径由 app 自己取**：
   选内置 Chromium 的**正面理由**是「用户看到的窗口就是被驱动的窗口」——可观测、可随时人工接管登录，
   且这一套内核已经在包里。外部宿主（Playwright 自带的 Chromium 等）过去被当成红线否掉，
   **2026-09-30 需求方更正**：真实约束是「用户不额外手动下载软件」，不是「不许有第二套内核」，
   所以只要 app 自行内置（构建期拉取，离线可用）或自动下载（校验 + 回滚 + 失败降级）外部内核，
   并且**同一时刻仍只有一个宿主在驱动页面**，就是许可方案。
   仍然否决的只有 `puppeteer-core` + 系统 Chrome：那要求用户自己装 Chrome。
   代价对比：放弃内置宿主换来 Playwright 的选择器引擎/自动等待等便利，
   但外部浏览器是**独立 OS 窗口**，不能再嵌在 app 面板里被用户直接看到与接管——
   因此切换宿主只应发生在 §9.7 对账出现「内置通道补不上的能力缺口」时，且要显式记录换来的可见性损失。
   默认路线不变：**自建 locator 层**（P2.2）补齐自动等待与选择器引擎。
3. **TypeScript（strict）+ ESM**：cordis v4 是 `"type": "module"`；全仓统一 ESM 避免双轨。
4. **pnpm workspace monorepo**：插件必须各自成包才能 enforce 分层 inject 规则（靠 lint + 显式依赖）。
5. **React + Vite + Tailwind CSS + lucide-react + i18next**：渲染层纯 UI，不做业务决策；构建快、HMR 好，利于 P1.2。
   三者是**硬性规范**（`AGENTS.md` §5）：样式只用 Tailwind utility（禁手写 CSS / CSS-in-JS），
   图标只用 lucide-react 现有图标（禁自造 SVG / emoji 当图标），页面文案一律走 i18n
   （`zh-CN` 默认 + `en`，语言包本地 JSON，不走网络）。i18n 从第一屏就做，避免后期返工抽文案。
6. **electron-builder**：一套配置出 nsis / dmg / AppImage / deb，含 Linux 多格式，是三端需求的最低成本解。
   打包必须自包含（含 Node 运行时与 Chromium），产物装机后**不得**再拉取任何依赖。
7. **SQLite = `node:sqlite`（Electron 内置，实测可 require）+ 文件迁移**：JD、简历、知识库、投递记录全本地关系型。
   放弃 `better-sqlite3`：它要求 `electron-rebuild` 对齐 Electron ABI，违反 §1.4 第 3 条的风险取向。
   向量检索在 P4.3 决策，约束同样是不引入需用户机编译的原生扩展。
8. **zustand + typed IPC client**：渲染层轻量状态，服务端状态一律从 service 事件流派生，不做二次真相源。
9. **不引入 HTTP 服务层**：主/渲染通信用 Electron IPC（preload 白名单方法），不额外开端口，减少攻击面。
   （P1.6 的 dev harness 例外，仅 dev 模式启用，且不得进入生产产物。）
10. **额度/计费以 service 边界预埋，不以 UI 或 if 分支预埋**：见 §1.5，只暴露 `entitlement.gate`，
    将来换实现不改调用方。
11. **PDF 编辑轨 = 降级为轻编辑（2026-10-04 需求方裁定，2026-10-05 落地，P3 plan §0.1 有全文）**：
    放弃「在用户既有 PDF 上真编辑」——即 `mupdf` 的字节级真涂黑与为它服务的三引擎路由 / WASM 随包内嵌 / CSP 放开，
    `canva-pdf` 的代码一行都不搬。保留的轻编辑 = **文本覆盖（白底矩形 + 新文字，不改写原内容流）+ 页面增删 + 撤销重做 + 另存新文件**，
    引擎只留 `pdf-lib`（MIT、纯 JS、无原生依赖，与 §1.4 零首启动下载一致）。
    理由：真编辑的唯一硬依赖 `mupdf` 是 AGPL-3.0，再叠 `canva-pdf` 缺 LICENSE 文件那份须由需求方署名的书面豁免；
    而轻编辑的全部能力落在 MIT 依赖上，零许可风险，且"只追加不改写"让「其余版式一点不动」从需要断言变成结构上必然。
    失去的产品能力如实登记：改动后的 PDF 不再与原文件逐字节同构（替代路径 4.1 解析 → 4.5 定制 → 3.3 重生成，版式由模板决定），
    且"旧文字提取不出来"的涂黑语义不再提供；反向验证（否决这条路线没有打断任何已验收能力）落在 spec 的 `3.4-11`。

## 7. 项目规范（摘要，**权威全文见仓库根 `AGENTS.md`**，P1 工具落地细节见 `docs/plans/01-framework/spec-conventions.md`）

- 提交：Conventional Commits + **描述必须中文且写清实现了什么功能 / 修复了什么 bug**；
  **每次修改完成即提交并推送，禁止本地堆积**（`commit-msg` 钩子 + `pnpm status:check` 机检）。
- 代码：**以逻辑复用为荣，以堆积代码为耻** —— 新函数先搜同能力实现，同一逻辑第二次出现必须抽公共层，
  发现死代码/重复实现即时删除；不做超需求功能，不加不会发生的异常处理。
- 注释：**每个函数中文 JSDoc**（作用 / 入参含单位与边界 / 返回含失败语义）；行内注释只写「为什么」。
- 命名：变量名必须有含义（禁 `data/res/temp/flag/obj2`）；cordis service 名用 `域.能力`
  （如 `browser.session`、`jd.store`）；插件目录 `plugin-<name>`。
- 结构：monorepo 分层依赖只能自上而下，禁止反向与同级横向内部引用；包内 `src/index.ts` 为唯一出口。
- 边界：插件间只经 service 通信；`packages/*/src/internal/**` 不得被外部包 import；只经 `@auto-cc/core` 用 cordis。
- 前端：**样式只用 Tailwind CSS；图标只用 lucide-react（不自造）；页面文案一律走 i18n（`zh-CN` + `en`）**。
- 方案先行：实现项目里没有的功能之前，**必须先做 GitHub / 官方文档取证并写进 plan 的选型证据**；
  文档转述不可信，涉及 API 形态必须先本机实测。
- 收尾自检：lint/typecheck/test 全绿 + V 类条目附截图证据 + spec 状态位更新 + 复用/死代码/前端三规
  - 提交推送，逐条回答后方可声称完成（`AGENTS.md` §7.4）。
- 文档：每个子计划必须有 plan + spec + 验收记录三件套，spec 条目 ID 稳定不复用。

## 8. 合规与风险立场（前置约定，非事后补丁）

自动化操作招聘平台存在账号封禁与违反平台 ToS 的现实风险。项目立场：

- 默认开启 **人工审批**（发送打招呼/投递简历前确认），自动化频度受限；
- 提供「仅辅助」模式（只搜索/只生成内容，不自动发送），供不愿承担风险的用户；
- 不做验证码绕过、不做指纹伪装、不做多账号池 —— 这类需求一律拒绝实现；
- 所有外发动作留完整审计日志，界面可回看。

## 9. 测试策略：agent 可视化自测（用户硬性要求）

不以「测试用例脚本覆盖率」为主验收手段。定义 **Dev Harness**：

1. app 在 dev 模式下开启 `--remote-debugging-port`，由 `plugin-devtools`（P1.6）暴露控制面。
2. agent（我）通过 CDP 连接：读取实际渲染 DOM、截图、真实点击/输入、读取主进程日志与 service 状态。
3. 验收 = agent 亲自操作 app 完成 spec 场景，并**基于看到的界面**给出结论；截图与 DOM 快照作为证据归档在
   `docs/acceptance/<spec-id>/`。
4. 单元/集成测试脚本仍保留，但只用于纯逻辑（选择器解析、分页、schema 校验），不作为功能验收的唯一依据。
