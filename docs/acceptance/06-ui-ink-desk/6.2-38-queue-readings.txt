① 发送键在流式期间不再是"拒发"
--------------------------------------------------------------------------------
基线（没有草稿）
  sendAriaDisabled = "true"    sendDisabledReason = "INPUT_EMPTY"    键面「发送」

第一句点出去、流式起来之后（草稿已清空）
  sendAriaDisabled = "true"    sendDisabledReason = "INPUT_EMPTY"    键面「排进队列」
  chat-running 条目存在

  **判据在 reason 码上**：流式期间 reason 仍然是 `INPUT_EMPTY`（草稿空），**不是 `STREAMING`**。
  旧实现里 `STREAMING` 是独立一支；本片把那支删掉了，于是"按不动"只剩草稿空这一个原因。
  键面文案从「发送」切成「排进队列」，也是同一处 `isStreaming` 分支在起作用。

③ 自动出队，且落库顺序 = 排入顺序（FIFO）
--------------------------------------------------------------------------------
等甲那条流走完，再读库末尾
  2026-10-19 05:39:53.425  user       53b3c2f8-1  排队取证甲：这一句会流式很久。
  2026-10-19 05:39:53.426  assistant  08bf4f6a-c  已收到：「排队取证甲：这一句会流式很久。」…
  2026-10-19 05:39:53.530  user       cb9cc282-e  排队取证乙：这一句应当排在甲后面，等甲说完才发出去。
                                 ↑ 乙的 user 行落在甲的 assistant 行**之后**，不是入队那一刻的时间戳。

出队后界面
  chat-queued 读数消失（data-queued-count 不再出现）
  最后一条助手正文 = 「已收到：「排队取证乙：这一句应当排在甲后面，等甲说完才发出去。」

  **出队点选在 `done` 事件之后**是有讲究的：渲染层收到 `done` 会 `setLiveStream(undefined)` 并重读快照，
  若出队排在 `done` 之前，紧接着起来的新流会被那一次重读擦掉。代码里 `finalize()` 的顺序是
  「落库 → 摘 live → 发 done → drainPending()」，本条读数就是这一顺序的活体兑现。
