三条要点：
- 第 4/5/6 行是**同一只按钮在三种界面态下的三次现读**，用来证明 `createReason` 的优先级链
  （busy → 名字 → 计划 → 表达式）真的按书写顺序命中：填名字后跳到 `PLAN_MISSING`，
  名字留着再清空表达式仍是 `PLAN_MISSING`（计划那一档先命中），名字清空后回到 `NAME_EMPTY`。
- 第 1/2/3 行的 `bg` 与 `color` 与「未禁用」的 amber 完全不同（收敛到 ink-850 + slate-500），
  即禁用态**不靠 opacity 蒙一层**，而是整档换成中性色——效果色只留给「能按下去会发生什么」。
- 第 7 行的底色与 1～6 不同（`oklab(0.1986…)` = amber 档自己的 disabled 底），
  因为它嵌在计划行内的紧凑档（`compact`）里，容器底色不同、令牌同一套。

原生 `disabled` 全为 `false` 是刻意的（`ui/controls.tsx:126`）：原生禁用会让 tooltip 不派发，
人只会看到"按不动"而看不到为什么按不动。挡下的是 `onClick`（`isDead` 时根本不挂）。

② 归属色档位（24 只 `DeskButton`，按「这个动作动到谁」分）
--------------------------------------------------------------------------------
`grep -c '<DeskButton'` 逐文件：`WorkflowPanel` 7 + `WorkflowPlans` 7 + `SchedulePanel` 7 + `ConsentCard` 2 + `WorkflowEvidence` 1 = **24 只**。
按 variant 汇总：seal 6 / amber 6 / line 5 / ghost 4 / solid 3（合计 24，与逐文件计数对得上）。

一句规则（写在 `WorkflowPanel.tsx` 的 `busyReason` 上方注释里，整屏共用）：
动到平台的是 `start` / `retry` / `schedule-trigger-now` / `consent-grant` / `*-remove-confirm` / `plan-remove-confirm`
→ `seal`；只改本机那份 run 的状态或只写本机的表（`pause` / `resume` / `abort` / 建任务 / 启停 / 落计划名）→ `amber`；
什么都不写（`refresh` / `schedule-refresh` / 删除的**入口** / 证据展开）→ `line`；
开合画布这种"同一批数据的另一种画法"→ `solid`；取消 → `ghost`。

- `plan-rename-save` / `plan-duplicate-save` 旧写 emerald（= jade 族「已经核过」），改 `amber`：

  且签完紧接着就重放那一次外发。`consent-deny` 从 rose 退成 `ghost`——拒绝不该被涂成危险色。
