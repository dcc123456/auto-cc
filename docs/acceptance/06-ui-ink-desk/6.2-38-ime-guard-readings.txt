① 中文输入法守卫（spec 1.11-02 的补齐）
--------------------------------------------------------------------------------
守卫本体两个判据（`ChatPanel.tsx` 的 `onKeyDown`）：
  `event.nativeEvent.isComposing || composingRef.current`
后者兜的是"compositionend 晚于 keydown 到达"那种次序——部分平台上的中文输入法正是这个次序。

  探针一：合成进行中（已派 `compositionstart`）敲回车
    draft            = 「输入法守卫：正在选词时敲回车」   ← **没被清空**
    draftCleared      = false
    userMessagesDelta = 0                            ← **一条都没发出去**
    queueCount        = null                          ← 也不是排进了队列

    守卫前的样子是：半句拼音连着候选框一起被发出去，草稿当场清空。
    现在两件事都没发生。

  探针二：派 `compositionend` 之后同一颗回车
    draft             = ""                            ← 清空了，说明这一发真走了
    userMessagesDelta = 1
    助手回复首句      = 「已收到：「输入法守卫：正在选词时敲回车」。这是对话骨架的本地确定性回复…

    守卫没有把回车永久焊死：合成一结束就恢复原来的行为。

  探针三（负对照）：非合成态 Shift+回车
    userMessagesDelta = 0                            ← 只换行，不发送
    draft 开头        = 「Shift 回车只换行，」        ← 内容还在

  本条不需要扩 `DeskTextarea` 的 prop：`onKeyDown` / `onCompositionStart` / `onCompositionEnd`
  早已在 `...rest` 里透传（`ui/controls.tsx`），原件层零改动。

② 可拖拽高度：五档吸附，缺省 140
--------------------------------------------------------------------------------
档位表（`COMPOSER_HEIGHT_CLASS` 与 `COMPOSER_HEIGHT_PX` 逐档对齐）
  第 1 档   72px    h-[72px]
  第 2 档  140px    h-[140px]      ← 缺省
  第 3 档  220px    h-[220px]
  第 4 档  320px    h-[320px]
  第 5 档  520px    h-[520px]

拖拽手柄的活体读数（`[data-action="chat-composer-resize"]` 的 aria-label + 输入框实测高度）
  initial                    h: 72    输入框高度：第 1 档（72 像素）     stored "0"
  drag-up-3steps             h: 320   输入框高度：第 4 档（320 像素）    stored "3"
  drag-down-5steps-clamped   h: 72    输入框高度：第 1 档（72 像素）     stored "0"   ← 到底不越界
  drag-up-1step              h: 140   输入框高度：第 2 档（140 像素）    stored "1"
  drag-up-10steps-clamped    h: 520   输入框高度：第 5 档（520 像素）    stored "4"   ← 封顶
  手柄 title = 「拖动改输入框高度」

--------------------------------------------------------------------------------
③ 取证期间抓到一个真缺陷并修掉（已复测）
--------------------------------------------------------------------------------
上面 `initial` 那一行原本是 `h: 72 / stored "0"`——**新装的用户落在最矮那一档，不是声明的 140**。
根因是 `readComposerStep()` 里的 `Number(localStorage.getItem(...))`：
`Number(null) === 0`，"没存过"被静默读成了第 0 档。

修法：判空走在 `Number()` 前面。
  const stored = localStorage.getItem(COMPOSER_HEIGHT_KEY);
  if (stored === null) return COMPOSER_DEFAULT_STEP;

复测（清掉 `auto-cc.composerHeight` 后 reload）：
  stored        = "1"        ← 挂载时写回的是缺省档下标
  heightClass   = ["h-[140px]"]
  实测高度       = 140
  手柄 aria-label = 「输入框高度：第 2 档（140 像素）」

  这条正是"首次挂载 + 本地无偏好"这一格：单测默认从有值的 localStorage 起步，看不见它。

--------------------------------------------------------------------------------
④ 为什么是吸附档而不是参考那边的连续拖拽（主动降级，理由入档）
--------------------------------------------------------------------------------
参考实现直接连续改高度。本片做不到同形：§5.1 禁内联 `style` 做视觉，而 Tailwind 只认源码里
出现过的字面量类名——连续高度只能写运行期拼出来的 `h-[${n}px]`，扫不到就一条 CSS 都不生成。
于是改成"按位移折算档位 + class 从枚举表取字面量"，每档 40 像素换一格
（档位落差本来就大：72→140→220，按像素逐格算会一直停在同一档）。
