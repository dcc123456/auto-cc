反向验证：观测层是唯一让它停下来的东西（spec 2.7-01 的另一半）
  plugins.stop('browser-risk') → 靶页仍是 captcha → 点「续跑」→ run 3f573127… 跑到「已完成」，
    渲染层监听器整段零新信号（__riskSignals 停在 1 条）→ 归还槽位后确实不再有任何回调
  plugins.start('browser-risk') → tree 读数 browser-risk=active → 点「开始」→ 新 run 79716061… 又停在 jd-capture，
    渲染层收到第 2 条 page-text 信号 → 重新挂载确实重新拿到那个唯一的 webRequest 槽位
  收尾：靶页 DELETE 归零 + 点「续跑」→ 79716061… 已完成，app 回到无接管点状态

收尾自检后的复读（主进程侧只做格式化改动 → esbuild watch 自动重启 Electron 之后）
  kernel.tree() → browser-risk=active、30 个节点全 active、notActive 为空
  workflow.runner.current() → {status:"idle", requiresHuman:null}（无遗留接管点）
  GET /api/risk-mode → {"mode":"off"}

结论：两类判据（HTTP 状态码 / 页面文案）都在真实窗口里把整条工作流停在当前步并给出可续跑的接管横幅；
     摘掉观测服务则同样的风控页不再产生任何暂停——因果链只经过 `browser/risk-signal` 这一个事件。
