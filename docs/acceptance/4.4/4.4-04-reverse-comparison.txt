4.4-04 验收证据 · 反向比对：库内具备但 JD 未提的相关能力（2026-10-02，切片 4.4-c）
==============================================================================

条目原文：反向比对：库内具备但 JD 未提的相关能力，作为差异化亮点候选输出（U 类，判据"单测"）。

结论：`[x]`。亮点候选必须同时过**两道闸**，只看第一道会把「C1 驾照」推成差异化优势。


【0】两道闸的口径（plan §4.4-c 判据三，写代码前定稿）
------------------------------------------------------------------------------
一个库内实体要成为亮点候选，四个条件全成立：

1. `kind` 属于 `skill` / `achievement`。经历、项目类不当候选——它们的技能面已由 skill / achievement
   实体代表，再进来就是同一件事在界面上出现两遍。
2. **第一道闸**：`coverageOf(实体, 全部 JD 要求) < evidencePartialMinScore(0.3)`。
   也就是这个能力 JD 根本没提——JD 提过的东西是"要求"，不是"差异化"。
3. **第二道闸**：`coverageOf(实体, JD 全文) ≥ highlightMinScore(0.12)`。
   这一条反过来用同一个尺子：它判的是"这条实体与这个岗位到底有没有关系"。
   只判第一道闸时，「英语六级」「C1 驾照」都满足"JD 没提"，会被当成亮点推给用户，
   而它在投后端工程师时是噪音——产品上比"没有亮点"更糟。
4. 与截断上限（`maxHighlights`）无关，只是排序后只留前 N 条，被截掉的条数**随报告一起返回**
   （`highlightsDropped`），不静默丢（4.4-06 的"计数可见"同一条口径）。

输出形状 `{ id, origin, label, score, matchedTokens }`，`score` 是对 JD 全文的覆盖率（第二道闸的读数），
`matchedTokens` 就是"相关在哪几个词"——界面要能回答"凭什么叫亮点"，靠的不是再问一次模型。

------------------------------------------------------------------------------
$ npx vitest run --reporter=verbose src/requirements-compare.test.ts
（工作目录 packages/resume-kb，Node 24 / vitest 3.2.7）

 ✓ 反向比对的两道闸（spec 4.4-04） > JD 提过的能力不当亮点（第一道闸）
 ✓ 反向比对的两道闸（spec 4.4-04） > 与这个岗位无关的实体不当亮点（第二道闸）：驾照、六级不是差异化优势
 ✓ 反向比对的两道闸（spec 4.4-04） > 库里具备、JD 没提、且与岗位相关时进候选，并给「相关在哪几个词」
 ✓ 反向比对的两道闸（spec 4.4-04） > 经历/项目不当亮点候选：它们的技能面已由 skill / achievement 代表
 ✓ 反向比对的两道闸（spec 4.4-04） > 条数上限来自配置，被截掉的条数如实报出

四条用例里第三、第四条是"过闸"的正反两向：第二条单独把 `highlightMinScore` 抬高时驾照那条就该出局。
另外 `maxHighlights: 0` 时 `highlights` 为空、`highlightsDropped` 等于不封顶时的条数——
截断与"一条都没有"在报告里是两个不同形状，界面要能分开播报。


【2】真实装配读数
------------------------------------------------------------------------------
同一份 demo（复跑步骤见 `4.4-03-three-state-comparison.txt` 第【2】节抬头）的第【3】节：

【3】亮点 kb-819fb3991e58f894[achievement] 0.1429  相关词：服务 / 订单
     亮点 kb-a560a1714d8177e6[achievement] 0.125   相关词：推荐 / 负责
     截掉 0 条

读数说明两件事：

- 两条候选的 `score` 分别是 0.1429 与 0.125，都只比 `highlightMinScore(0.12)` 高一点点。
  这不是巧合而是这条闸的设计意图：**门槛设在"沾一点边"的量级**，因为对立面（JD 没提的任何实体）
  数量大且大多与岗位无关。也正因为余量这么小，阈值未标定的风险集中在这里——
  4.4-e 标定时的主要对象就是这一项（其余四项在三态分界上有余量）。
- 语料里的「C1 驾照」「英语六级」两条实体**没有**出现在候选里，是第二道闸挡下的；
  它们过得了第一道闸（JD 全文确实没提）。这就是"只判 JD 没提"会出错的具体例子。

服务层的对应用例（`gap-service.test.ts`，真库 + 真切片）：

 ✓ kb.gap.report 的三态比对与反向比对（spec 4.4-03 / 4.4-04 / 4.4-07） > 亮点候选受配置上限约束，被截掉的条数随报告一起返回

demo 第【4】节还给了一个跨界读数：把 filter 收到只剩技能类实体（`kb_entities` 10 → 6 条）时，
参与比对的实体变少、`entityCount` 随报告变成 6，而**越界证据 0 条**——
也就是说 filter 是真的递到库查询那一层，不是比完再在前端删掉；亮点候选同样只从过滤后的集合里出。


【3】这条判据没覆盖什么
------------------------------------------------------------------------------
- 亮点候选的**排序质量**没有验收。判据只说"作为差异化亮点候选输出"，
  所以钉住的是"该出的出、不该出的不出、条数封顶且丢弃可见"，
  不是"排第一的那个真的是最亮的"。后者要评测集，归 4.4-e 的标定动作。
- 界面上怎么呈现"亮点"是 4.4-05（V 类），归 4.4-d。
- `highlightMinScore` 与 JD 全文比较用的是**同一个 `coverageOf`**，没有新增第二种相似度
  （§2.1/§2.2：本片的打分一律复用 4.2-c 的覆盖率，新写的只有区间合并、档位比较、两道闸的编排）。
