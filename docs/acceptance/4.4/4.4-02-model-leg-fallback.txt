【3】4.4-02 的两句判据分别怎么落
------------------------------------------------------------------------------
- 「功能不中断」：五种结局里有四种（unavailable / rejected / failed / disabled）交回的 `items`
  指纹与"完全不问模型的词面基线"**逐字相同**（d668f55a7d54d3f7），第五种是 merged，它只增不减。
  也就是说本方法在模型任何形态下都不抛、不清空、不截断词面结果。唯一的例外是 `INVALID_ARGUMENT`
  （我们拼错了请求），那条照旧上抛——回落不该掩盖自己的 bug（`outbound.script` 的同一判据）。
- 「回落要能被看见」：`modelStatus` + `modelReason` + `modelAdded` + `modelDropped` 四个字段随结果返回，
  且非 merged 的那一路日志级别是 **WARN**（merged 是 INFO）。界面 4.4-d 直接按这五态出五句文案，
  不需要自己再推断"是没配还是失败了"——`missing` 的具体项已经写在 `modelReason` 里。

与 2.5-01（话术生成回落模板）的形状差异，是这条链后续可复用的结论：
话术那侧的回落是**换产出者**（模型不行就本地模板出文案），拆解这侧的回落是**减少产出**
（模型不行就只交词面基线）。所以这里必须区分五态而话术只需两态——少了哪一类，界面说的话就不同。

【6】诚实边界（本片没证的、以及为什么）
------------------------------------------------------------------------------
- **真模型没跑过**：本机 `AUTO_CC_LLM_API_KEY` 未设置（`env | grep AUTO_CC` 为空），
  所以 ② 那一路用的是本地 fixture 端点。它证明的是**形状与接线**（请求体参数、OpenAI 信封解析、
  契约校验、定位、合并、五态播报）全链路穿通，**不证明**真实模型的召回质量与 JSON 合规率。
  真 key 到位后的复跑步骤：`cordis.yml` 的 `llm` 段补 baseUrl/model 两行 + 导出 key →
  `pnpm dev` → 缺口报告界面（4.4-d）拆一份真实样例 JD → 看 `modelStatus` 是否 merged、
  `modelDropped` 里"引文对不上原文"占多少——那个比例就是提示词 jdreq-v1 的合规率，要记进 4.4-d 的记录。
- **V 半边（界面提示）未做**：条目是 U+V，本片只到服务与结果层，界面上那句"没用上模型，
  以下是关键词拆解"要等 4.4-d 的缺口报告界面（§5.9 双入口同批接）。
- **`rejection` 的分布未知**：模型在真实 JD 上到底会给出多少定位不回的引文，只有真端点跑过才知道；
  现在能说的只有"引文对不上就一定不收，且这条计数看得见"。
- 迁移号段本片**没有新增**（仍停在 14，15 空着）：4.4 的拆解不落库，见 plan §4.4 口径 3。
