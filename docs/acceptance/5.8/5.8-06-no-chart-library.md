# 5.8-06 依赖树无图表库（C 类机检证据）

**判据原文**（spec 5.8-06）：看板不得引入图表库；比例呈现由渲染层的十分位宽度条与精确数字承担。
**验证方式**：C（结构/静态）——把这条否决落成常驻机检，进 `pnpm lint` 链，每次提交都跑。

## 为什么落在 `check-dependency-floor.ts` 而不是新写一台机检

这台机检的既有语义就是「某次顺手 `pnpm add`」的防线（spec 4.3-05 无外部向量服务 / 4.3-06 无本机编译扩展）。
5.8-06 是同一个失效模式的第三种写法：某天有人把看板的宽度条"升级"成 chart.js，
变化的是运行期依赖变重，不是多一个服务。同一条逻辑只留一个入口（AGENTS.md §2.2 / §2.5），
所以并入同一份三层扫描，新增 `VISUALIZATION_BANS` 与它参与的 `TREE_BANS`（= 能力类 + 图表类，三层都判）。
`NATIVE_BANS` 的语义保持原样：声明层禁止、传递链路只提示、是否落到用户机上由搬运层判。

## 禁令清单（按家族，不逐个版本号）

| 家族 | 覆盖写法 |
| --- | --- |
| Chart.js | `chart.js` / `chartjs-*` / `@chartjs/*` |
| ECharts / AntV | `echarts` / `@antv/*` / `antv` |
| React 图表组件 | `recharts` / `victory` / `@victory*/*` / `semiotic` / `@nivo/*` / `@vx/*` / `visx` |
| D3 与传统图表 | `d3` / `d3-*` / `@types/d3*` / `highcharts` / `apexcharts` / `plotly.js` / `c3` / `morris` |
| Canvas / WebGL 引擎 | `konva` / `react-konva` / `pixi.js` / `@pixi/*` / `fabric` / `three` / `@react-three/*` / `babylonjs` |
| 图与流程图渲染 | `mermaid` / `dagre` / `@dagrejs/*` / `elkjs` / `gojs` / `jointjs` / `cytoscape` / `vis-network` / `vis-data` |

后两类的理由写在源码注释里：`§5.3` 的 lucide-only 不允许"为了画图引入 SVG 手绘链路"；
画布类需求属 5.10，真要引入须先按 §6 取证再改这条禁令。

## 实测二：反向验证（禁令确实会拦，不是摆着好看）

方法：把 `chart.js` 暂时写进根 `package.json` 的 `devDependencies`（同时放一个 `better-sqlite3` 作既有禁令的对照），
并在 `pnpm-lock.yaml` 的 `packages:` 段暂时插入一条 `'chart.js@4.4.1':` 键，跑一次机检后**原样撤掉两处改动**。
撤后 `git diff --stat` 只显示 `package.json` 一行变化（即 lint 链接线那行），锁文件无残留。

```
$ npx tsx scripts/check-dependency-floor.ts
✖ 离线依赖门槛机检未通过（spec 4.3-05 无外部向量服务 / 4.3-06 无本机编译扩展 / 5.8-06 无图表库）：
  - package.json 的 devDependencies 里声明了 better-sqlite3：非内置的 SQLite 绑定或向量扩展（AGENTS.md §9 已实测 `node:sqlite` 在 Electron 44 主进程直接可用，禁止原生编译依赖）
  - package.json 的 devDependencies 里声明了 chart.js：图表库（spec 5.8-06：看板用十分位宽度条，界面不引图表库；决策十九）
  - pnpm-lock.yaml 的依赖树里解析出 chart.js：图表库（spec 5.8-06：看板用十分位宽度条，界面不引图表库；决策十九）
exit=1
```

三条结论：**声明层**拦得住主动引入（且它比锁文件更早报错，指向具体的那份 package.json 与字段）；
**解析层**即使没人显式声明、只是某个包的传递依赖带进锁文件，同样的名单也拦得住（这一层不依赖本机装没装）；
既有禁令未被新名单挤掉（`better-sqlite3` 仍在前两条里报错）。

## 机检没覆盖到什么（如实标注）

- **搬运层的反向验证未实测**：判据是 `resolveRuntimeDeps()` 的闭包（mammoth / pdfjs-dist 的依赖树），
  要让它命中图表库得往真实 `node_modules` 里塞包，属于污染用户机环境，按 §9 的纪律没做。
  代码形状上那一层与另两层共用同一个 `TREE_BANS`（`banOf(dep.name, [...TREE_BANS, ...NATIVE_BANS])`），
  所以"图表库进了 esbuild 外置闭包"会被判失败这条是**读代码得出的结论，不是跑出来的**。
- 名单按**包名**判，不看别名或 fork 后的改名（如把 chart.js 改名发布）。这类绕过不是一次 lint 能防的，
  留给 §7.4 的人工自检与 review。
- 真机 macOS/Linux 的依赖闭包差异无法在本机验证（§9），本条判据本身是结构检查，与平台无关。
