## 灌进去的是什么

一万行按四腿铺开，行时刻在 30 天的格子上轮转（`index % 30` 天前，`AS_OF_MS` 取本机中午十二点，日界不漂）：

| 归属服务           | 表                      | 灌入行数 | 近 7 天窗口内 |
| ------------------ | ----------------------- | -------- | ------------- |
| `jd.store`         | `jobs`                  | 4 000    | 1 072         |
| `usage.ledger`     | `usage_ledger`          | 3 000    | 800           |
| `conversation.store` | `conversation_messages` | 2 000  | 536           |
| `outbound.deliveries` | `delivery_records`     | 1 000    | 272           |
| **合计**           |                         | **10 000** | 2 680       |

写全部经各服务的**公开写入口**（`upsert` / `record`），不手搓 SQL——手搓会把"服务真认得这一行"判成假。
只有事务边界在外面套了一层 `BEGIN` / `COMMIT`：一万条逐条自动提交会把时间全花在 fsync 上，测不到聚合。
表行数由 `SELECT COUNT(*)` 逐张核对，等于上表——**少了这一条，"计时很快"就只是"表是空的"**。

## 计时读数（`FunnelView.tookMs`，本服务自己的 `performance.now()` 差值）

```
5.8-05 万级计时实测（10000 行）：近 7 天 tookMs=1/1/1/1/1（中位 1）· 整段 31 天 tookMs=2/2/2/2/2（最差 2）
```

- 近 7 天窗口：五次各 **1ms**
- 覆盖全部一万行、跨 31 天的窗口：五次各 **2ms**
- 用例里的预算上限是 **200ms**（实测的两百倍余量）。这条判据要拦的是"全表扫在数据涨上去之后变成秒级卡顿"，
  不是把毫秒级读数钉死；阈值写紧只会让一台慢机器把一条成立的判据跑成假红。真正的护栏是下面的查询计划。
- 界面显示的就是这个数（`metrics.took`，5.8-b 已上屏），不含 IPC 往返与渲染绘制。

## 查询计划（`EXPLAIN QUERY PLAN`，四条计数 SQL 各一条）

```
jd.store.countCaptured: SEARCH jobs USING COVERING INDEX jobs_captured_at (captured_at>? AND captured_at<?)
usage.ledger.countAction: SEARCH usage_ledger USING COVERING INDEX usage_ledger_action_ts (action=? AND ts>? AND ts<?)
conversation.store.repliedJobCount: USE TEMP B-TREE FOR count(DISTINCT) / SEARCH conversation_messages USING INDEX conversation_read_at (read_at>? AND read_at<?)
outbound.deliveries.count: SEARCH delivery_records USING COVERING INDEX idx_delivery_records_ts (ts>? AND ts<?)
```

逐条读法：

1. 四条都是 `SEARCH`（按索引定位），**没有一条是 `SCAN`**（逐行过表）——"不做无界全表扫描"的正面证据。
   用例里 `expect(detail).not.toContain('SCAN')` 就是钉这一件。
2. 三条是 `USING COVERING INDEX`：`COUNT(*)` 只需要索引本身、不回表，这是最省的一种。
3. `conversation.store` 那条多一行 `USE TEMP B-TREE FOR count(DISTINCT)`：这是 `COUNT(DISTINCT platform||'|'||job_id)`
   的**去重**步骤，建在已经由 `conversation_read_at` 区间筛出来的行上（近 7 天是 536 行，不是全表 2 000 行）。
   去重键是决策十六定的（数岗位不数消息），删掉它就变成把同一个岗位重复计进分子，所以这一行是**要求的代价**，
   不是漏网的全表扫；如实记在这里。
4. 索引名与号段对得上 5.8-a 落地记录：`jobs_captured_at`（既有）、`usage_ledger_action_ts`（既有）、
   `conversation_read_at`（号段 26 补）、`idx_delivery_records_ts`（号段 27 补）。
5. SQL 文本在本文件里是一份副本，所以用例同时比对生产源码（`assertSourceStillUses`，空白折叠后包含）：
   服务把形状改了（加列、换索引、退化成全表）时，这条判据会失败而不是继续测一条"已经没人走的查询很快"。

## 区间口径顺带被万级库验了一次

基准时刻取中午、行铺在整天格子上，于是"正好 7 天前"那一档压在 `fromMs` 边界上。用例里期望值由灌数循环
按 `ts >= fromMs && ts < toMs` 逐行累加（与 SQL 无关的第二条路），SQL 数出来的五级读数是

```
[1072, 800, 536, 272, null]
```

与逐行点数逐格一致；覆盖 31 天那一档数到 `[4000, 3000, 2000, 1000, null]`，即灌入的每一行都被数到。
5.8-a 的 `metrics-link.test.ts` 在替身上测的是半开区间的形状，这里是它在真库、万级行下的复验
（含头这一件在真数据上成立）。第五级仍是 `null` + 无源原话（决策十五），没有因为库大了就长出数字来。

## 边界与未覆盖

- 一万行是**灌出来的**，不是真实使用攒出来的：行内容全是虚构中文、来源地址用保留的不可解析域，
  全程零出网、不碰真实招聘平台（AGENTS.md §7.2）。
- 计时在临时库（`mkdtemp`）上，用完即删，**没有**动开发库 `tmp/dev-userdata`，
  因此 5.8-b 那六张活体截图对应的读数不受影响。
- 这条判据测的是四腿相加一万行；单表十万行、以及磁盘上真有一堆别的表（`kb_*`、`resume_*`）时的表现未测。
  计划形状由索引决定，与同库其他表无关，所以这一格留白不构成"看板会卡"的漏检，但如实记为未覆盖。
