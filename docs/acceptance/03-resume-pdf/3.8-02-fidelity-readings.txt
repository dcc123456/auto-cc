## 0. 这一道门在裁什么

plan 03 §12 与批准的计划里写死了顺序：**片 5 达标才开族三（3.8-03…06 的落地），不达标就停在片 5**，
族一（3.5-14/15/16 的覆盖去痕）成为本轮 PDF 编辑轨的终态。所以这份读数的用途不是"报告进度"，
而是**裁一条路线要不要继续花钱**。四条判据按裁定的保真口径（未改动区像素级一致）逐条量，
本轮没有任何编辑动作，整页都算未改动区。

## 1. 口径（先钉死怎么量的，否则数字没有意义）

- 出件：重建 HTML 经 `webContents.printToPDF({printBackground:true, preferCSSPageSize:true, margins:0})`，
  与产品打印口同一引擎；`@page{size:595pt 842pt;margin:0}`。
- 栅格化：原件与重建件都按 **150dpi** 用**同一版 pdf.js（6.3.289）**渲染；两张纸都缩进同一个
  1240×1754 的像素框（重建件的页框实测是 594.96×841.92pt，1px 的取整差不该算进"未改动区差异"）。
- 差异像素：单像素三通道最大差 **>8/255** 记为一个差异像素（另附 >16 的档，两档都报，不挑好看的）。
- 每通道平均色差：全页每像素三通道绝对差的均值。
- 行基线漂移 / 单 run 宽度误差：两份件各跑一次 `extractPdfDocument`，按"同基线 + 同字体 id + 同旋转"
  聚成行，再按行文本配对（重建件被逐字拆开，见 §4 第 2 条）。**旋转那一行单列成已知丢失项**，
  不进聚合（3.8-01 同一条口径）。

## 2. 两个变体（把"可修的那一格"与"物理补不齐的那一格"分开）

- **A `aSpan`**：每格 run 一个绝对定位 `<span>`，行盒高按 pdf.js 报的 ascent/descent 算；
  字族只取模型里现有的 `fontFamilyHint`（`serif` / `sans-serif`）。
- **B `bSvg`**：整页一个 `<svg viewBox="0 0 595 842">`，`<text y>` **直接落在基线上**（消掉行盒口径），
  并按夹具声明补回字重（`Helvetica-Bold` 那一族）。

## 5. 本轮新撞到的四条形状实测（都写进了 plan 03 §12.5，族三若不立项也是这一份记录在替后人省时间）

1. **Chromium 打印件的算子流坐标是各向异性的混合空间**：x / 字号 / 宽度按 CSS px 写（= pt × 4/3），
   Y 则是"以 pt 页高为原点、按 px 向下推进"再取负。归一公式（实测反推，逐位对得上）：
   `xPt = x×0.75`，`fontSizePt = size×0.75`，`fromTopPt = (pageHpt + y)×0.75`。
   不归一时"Jane Doe"的字号会读成 24pt、基线差 1584pt——**看起来像抽取器坏了，其实是两份件的坐标空间不同源**。
2. **Chromium 按字距把每一格文字拆成逐字 `Tj`**：夹具 7 行 → 重建件 105 格。所以"run"这一层身份
   在重建件里根本不存在，任何按 run 配对的判据都必须先按基线聚行（3.8-01 的判据本来就是这么写的，
   这一条是它反过来救了保真测量）。
3. **描边被写成填充**：夹具那条 `0.8 w … S` 的细线在重建件里是 `kind:'fill'` 的 1pt 高矩形，
   stroke/fill 这一轴不同源；而且它在像素判据里是**整条线全红**（0.2pt 之差就把 1px 的线整个挪掉）。
4. **重建件多出一整页满幅白矩形**（793×1123 的 `fill`）——Chromium 自己画的页底，不是内容。
   判据若按"形状条数"比会白多一条，按像素比则无影响（色值一致）。

另外两条与判据直接相关：
- **字重根本不在模型里**：`ExtractedRun` 只有 `fontFamilyHint`（`serif`/`sans-serif`），
  两行 `Helvetica-Bold` 在 A 版里整行掉成常规体——这是本轮**最大的一处肉眼可见差异**，
  但它是"模型缺一格"而不是"重建补不齐"，所以另开 B 版按夹具声明补上后重量。
- **字族名差一格，advance 误差差一个量级**：B 版衬线行原先写 `"Times New Roman", Times, serif`，
  宽度误差 +14.5%；换成与源 BaseFont 同名的 `Times` 优先之后仍 +14.5%（本机 Chromium 解析到的字面没变），
  而同一版里 Helvetica 那几行是 −1.3% ~ −3.6%。**这一格误差完全由"这台机器的字体解析"决定，不在我们手里。**

## 6. 差异集中在哪几类元素（按 `3.8-02-pixel-diff.png` 逐类读，红=差 >16/255）

- **页面底色、色带（495×34pt 的米白块）**：diff 图里整块纯蓝，**逐像素一致**，颜色值在抽取里也逐位对得上。
- **每一条文字行的字形**：全红，且呈" doubling/重影"状——起点准（Δx≈0）、基线准（B 版 Δy≈0.07pt），
  差在**每个字形的推进宽度与轮廓**（源字体是标准 14 型非嵌入字体，重建件由 Chromium 换字并嵌子集）。
- **那条 0.8pt 细线**：整条红（描边→填充 + 0.2pt 厚度差）。
- **旋转水印**：红，且重心的读数在斜排下不可比（隔出）。

**结论：差异不是"摆错了位置"，而是"同一句话换了一只字"**——正是计划里预先列出的物理补不齐第 ② 条
（`Tc`/`Tw` 字距与 advance 不复现）与第 ① 条（源字体不可得）的合成结果。位置类判据（Δx、B 版 Δy）
已经做到 0.01~0.08pt 的量级，说明**该路线的几何腿是成立的，字形腿按定义不成立**。

## 7. 门的裁定（按批准计划的原文执行，不自行放宽）

**片 5 不达标 → 族三（3.8-03…3.8-06）不开工；族一（3.5-14/15/16 的覆盖去痕）就是本轮 PDF 编辑轨的终态。**
判据不许"先做出来再说"，因此 3.8-02 标 `[!]`（跑完了、数字如实、结论是不过），3.8-03…06 保持 `[ ]` 并注明被这道门停在门外。

**顺带捞回来的两条正面结论**（不需要族三也成立，建议后续单独取号做）：
1. **按基线落字的 SVG 口径**把行基线误差从 1.33pt 压到 0.076pt——覆盖轨（3.5-15）替换字现在用的是
   `textBaseline='bottom'` + 行盒，同一格误差就在 0.5~1.3pt 这一档；把 B 版的口径搬过去是纯收益。
2. **字重这一格该进抽取模型**（`ExtractedRun` 缺 BaseFont/weight）——覆盖轨的替换字今天也丢这一格，
   粗体行会被替换成常规体。这一格补在 `page-extract.ts` 与 3.5-15 是同一件事。

## 8. 本机证不了的

- 以上四个数只在 **macOS arm64 + 本机字体集**下成立。Windows/Linux 上 `Helvetica`/`Times` 会落到别的字面，
  advance 误差只会不同、不会更准（这条不影响裁定：门已经在最好的一侧过了线外）。
- 打印出件（真纸）与屏上 pdf.js 栅格是两条腿，本轮只量了栅格；装机版打印不在本机可验范围。
- 「人眼看不出是覆盖」那一条仍按裁定要用户在场看一眼才算 `[x]`，这份读数不替代它。
