## 一、这一发是怎么停下的（fail-closed 的正面读数）

  `outbound.deliver.pending()` 随后回空数组 ⇒ 闸门与人工确认这一段的顺序是对的。
- 结局（`deliver.perform` 的信封，`ok:false`）：

  ```
  code    LOCATE_FAILED
  message 定位未过线，上传没有执行：最优候选 10 分低于最低可用分 30
  path    browser.act
  details.status  below-score
  details.spec    {cardinality:'single', effect:'inject', requireActionable:false,
                   candidates:[css 'a.btn-file input[type=file]']}
  ```

- **这一发没有注文件、没有点任何键、没有落账**：抛点在 `channel.send` 之内、`gate.perform` 之前
  （`packages/outbound/src/deliver.ts` 的 commit 顺序是 consent → 择机 → gate.enforce → 节流 →
  等人表态 → `channel.send` → 记账/落记录），所以 `usage_ledger` 与 `delivery_records` 都不增行。
  页面侧同一条自证：三枚 `input[type=file]` 的 `files.length` **全是 0**，
  会话末尾那一条仍是 8.4-01 那发的 11:53「送达 您好，我对贵司这个岗位很感兴趣，方便聊聊吗？」，
  没有长出任何附件消息。

## 二、真会话页上 `input[type=file]` 的实测形状（**把 8.0-06 那句"全页唯一一枚"作废**）

`document.querySelectorAll('input[type=file]')` 现读 **3 枚**：

| # | 父节点 | `accept` | 收 PDF？ | 可见性 |
| - | ------ | -------- | -------- | ------ |
| 1 | `div.toolbar-btn-content.icon.btn-sendimg`（会话工具条「发简历」那一格自己带的一枚） | `image/gif,image/jpeg,image/jpg,image/png` | **否** | 可见 |
| 2 | `a.btn.btn-primary.btn-file`（文本「上传附件简历」） | 含 `application/pdf`、`.doc/.docx`、ppt | 是 | **藏在关着的弹层里** |
| 3 | 同上，逐字相同 | 同上 | 是 | 同上 |

⇒ **能收 PDF 的那一枚不在工具条上**：工具条那格「发简历」走的是**图片简历**（只收 image/\*），
附件简历（PDF）必须先让 `upload-resume-dialog` 那个弹层打开。

## 三、那两枚为什么区分不了（本轮的定位挡路石）

两枚的父链逐字相同，都是同一份对话框的两份 **teleport 副本**，且都直接挂在 `<body>` 下：

```
a.btn.btn-primary.btn-file            文本「上传附件简历」，rect 0×0，offsetParent=null
  < div.btns
  < div.upload-resume__old            [data-v-46c9e5e1=""] class="upload-resume__old"
  < div.dialog-body
  < div.dialog-container              style="display: none"
  < div.dialog-wrap.upload-resume-dialog.v-trans   [data-v-46c9e5e1] [data-v-c18800fc] [data-transfer="true"] style="display: none"
  < body
```

两份副本的内部文案也逐字相同：「拖拽文件到这里 / 简历建议使用 PDF 文件，也支持DOC、DOCX、JPG、PNG 格式 /
文件大小不超过20M / 上传附件简历 / 没有附件简历 / 在线填写」。

⇒ 结论三条，都是这一格真正的形状：
1. `a.btn-file input[type=file]` 这条候选在**弹层关闭**的状态下必然命中 **2** 枚 ⇒ 歧义罚分把它从 35 分打到 **10 分**，
   注入档 30 分（裁定㉑）过不了线 —— 这就是本轮 `LOCATE_FAILED` 的全部原因，不是选择器写错，是**页面状态没到位**。
2. 因此 `cardinality:'single'` 这句声明只在"弹层已打开"的前提下成立；**打开弹层是投递链路的前置动作**，
   而它此前没有被登记（`deliver` 段没有入口键，理由写在定位描述里："入口键本身没登记：它的 role 计算值需要实测而本次不点"）。
3. 区分"哪一枚能用"的唯一实测依据是**可见性**（`display:none` 在祖先 `div.dialog-container` 上），
   不是内容、不是顺序。任何"取第一枚 / 取最后一个"的写法都没有证据支持，不许进包。

## 四、顺带抄到的两格（与投递无关但会咬人）

  文案「我觉得你很适合我们的岗位，你可以直接跟我互换电话联系我 / 电话联系TA」；
  `message-controls` 那一块里还预置了「换电话 / 换微信 / 确认与对方交换电话吗？取消 确定」等节点。
  它们是**遮挡候选**：中心点命中测试会打到这些节点上（本轮 `发送` 键仍是 `button.btn-v2.btn-sure-v2.btn-send.disabled` @ (1112,602,62,28)）。
- `document.querySelectorAll('div.dialog-wrap.upload-resume-dialog')` 有两份这件事本身说明：
  真页面的组件副本数会随会话切换/路由变化增长。**"全页唯一一枚"这类断言必须每次现读**，
  知识包里的 `hits` 只能代表取证那一刻的形状（8.1-02 的 `hits` 可选正是为此）。

## 六、界面侧同轮的一格（**结论经过一次自我作废，以这一节为准**）

第一张确认单 `be6c7f03-…` 超时被按拒绝处理（回执 `OUTBOUND_APPROVAL_DENIED`，前后账本不增行）。

我先据此写过一句"确认单只长在岗位屏、默认视图里看不见"，**那句按实测作废**：对话屏的「等人表态」带
（`AgentPauseCards.tsx` 的 `data-testid=agent-pause-band`）**本来就把投递单画出来**——`origin==='deliver'`
的那些行走 `DeliverApprovalCard`，而它用的按钮 `data-action` 与岗位屏那张**逐字同名**（`approve-<approvalId>`）。
直接证据是同屏那格的文案「批准这一步 失败：确认单 be6c7…」——用户确实在对话屏点过，只是落在 120 秒到期之后。
所以第一发空转的根因是**表态窗口太短 + 我把按钮位置说成了一个不存在的位置**，不是可见性。

仍然成立的是另外两条独立测量：
1. 岗位屏那张卡在用户停在对话屏时 `[data-approval-id]` 量出 **宽度 0**（祖先 `section` 是 `display:none`，
   与 6.2-25 的"负腿读数"同一形态）。它不影响人点对话屏那一只，但**程序化按 `data-action` 找卡会打错**：
   同一时刻 DOM 里有**两只同名按钮**，一只有尺寸、一只宽度 0（§9 实测 5.4-b 的⑦ 同一条）。
2. 卡片即使在自己那一屏里也可能被**吸顶 header 压住中心点**：本轮岗位屏那一只实测 `y 34`，中心点命中测试打到
   `header`；`scrollIntoView({block:'center'})` 之后 `y 405`、`isSelf:true` 才点得到
   ⇒ 该区块缺 `scroll-margin-top`（或带偏移的滚动），属于渲染层那一片。

待裁的一格（不在本片里自行改）：`approveTimeoutMs` 出厂 120000（`cordis.yml` 的 `outbound-deliver`）
对"发单 → 人读到 → 点下去"这一串够不够——本轮从发单到超时只有整整两分钟，而我一次读数往返就要几十秒。
这一格要的是人的表态，不是代码默认值。
