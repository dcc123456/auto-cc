8.4-02 · 该笔在 usage_ledger 有行；再发同一目标被幂等挡住
执行时间：2026-10-09 11:56（紧接 8.4-01 同一现场，视图宽度与登录态未变，窗口仍未最大化）

────────────────────────────────────────────────────────────────────────
第一节 · 库读数：这一笔落成了一行，且只有一行
────────────────────────────────────────────────────────────────────────
发出前后各读一次 `usage.ledger.summary(6)`：

    发出前  { total:4, byAction:[{action:'search',count:4}] }                    ← greet 零行
    发出后  { total:5, byAction:[{action:'search',count:4},{action:'greet',count:1}] }

那一行原样（`recent` 里的第 5 行）：

    { id:5, action:'greet', targetId:'上海肯德基有限公司', workflowRunId:null,
      ts:1791517931936, source:'manual:上海肯德基有限公司', remoteRef:null }

三条对得上的口径：
- `targetId` 装的是**会话坐标那一维**（`greetTargetLabel` 的读数：给了 `conversationTarget` 就用它），
  与回执里的 `conversationTarget`、页面回读到的那一家公司是同一个字符串，不是岗位 id、不是拼接出来的。
- `source` 是 `manual:<目标>` 那条链的首段如实写法：本次正文是调用方给的现成文案，没有过一次 LLM，
  所以没有 `script-v1:` 段——这不是缺字段，是 `ledgerSource()` 的 manual 分支（spec 4.6-02）。
- 这一行是 `entitlement.gate.perform` 在 task 成功之后落的：第一次尝试（`WAIT_TIMEOUT` 那一发）
  前后 total 都是 4，**失败的一侧没有留下流水**，这正是 §7.3 要的性质。

────────────────────────────────────────────────────────────────────────
第二节 · 幂等：同一目标第二次 8 毫秒被挡，且第二次什么都没发
────────────────────────────────────────────────────────────────────────
同一条请求（同 platform、同 conversationTarget、同文案）再打一次：

    { ok:false, code:'OUTBOUND_ALREADY_SENT', ms:8,
      message:'目标 上海肯德基有限公司 在此前那些未挂工作流的发送里已经打过招呼，不再重复发送',
      details:{ targetId:'上海肯德基有限公司', workflowRunId:null } }

- **8ms** 这一量本身就是证据：这一条拒绝发生在 `greet.ts` 的幂等判据上（渠道问到了、账本数过了），
  排在页面动作之前，所以第二次**一个页面都没碰、一个字都没往输入框里写**。
  复述一遍代价：幂等键如果错，代价是同一位招聘方收到两句一模一样的开场白。
- 判据的键是 `(action='greet', target=上海肯德基有限公司, runId=null)`。`workflowRunId:null` 走的是
  "未挂工作流的发送"那一路（`alreadySentScope` 的对应措辞），跨重启成立——它数的是账本行，不是内存集合。
- 挡住之后账本没有变成 6：`total` 仍是 5、`greet` 仍只 1 行。即"换第二遍仍只算一笔"。

────────────────────────────────────────────────────────────────────────
第三节 · 额度那一侧的如实读数（这一格没说谎的地方）
────────────────────────────────────────────────────────────────────────
`entitlement.gate.check('greet')` 在这一发之后仍是 `{allowed:true, remaining:null, reason:null}`。
`remaining:null` 不是"无限"，是**当前 `entitlement.mode` 下这一档没有可报的剩余额度**这一件事
（口径记在 8.7 那两格与用量屏），所以这里不能写成"还剩很多"。
真正确定的读数只有两条：闸门放行过一次（`gate.perform` 落了第 5 行），幂等挡住了第二次。

────────────────────────────────────────────────────────────────────────
第四节 · 「界面读数」这一半到底取到了什么
────────────────────────────────────────────────────────────────────────
spec 这一格原本写的是"库读数 + 界面读数"。库读数在第一节，界面读数这一半**只能如实写成缺**：
渲染层射程内没有任何一只按钮带 `conversationTarget`（`grep -rn 'conversationTarget' packages/renderer/src` 零命中），
`JobLabPanel` 的「打招呼」与 `ScriptPanel` 的「选中候选→打招呼」传的都是 `jobId`。
所以这一轮的"界面"证据是同一条白名单 bridge 调用的返回值 + 账本行，而不是 `[data-testid=jd-greet-receipt]` 那张卡
（那张卡挂在岗位坐标那一路，本轮没走它）。落点写在 plan §7 第 15 条。
