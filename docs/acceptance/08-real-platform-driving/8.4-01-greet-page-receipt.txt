第三节 · 「不最大化也能执行」在这一发上兑现（8.4-05 的活体半边）
────────────────────────────────────────────────────────────────────────
同一轮里读到的三条几何，构成一条完整因果链：

    发送前：document.documentElement {scrollWidth:1224, clientWidth/innerWidth:863, scrollLeft:0}
            button.btn-send rect {x:1112, y:601, width:62, height:28}   ← 1112 > 863，在画面外
            document.elementFromPoint(1143, 615) = null
    发送后：scrollLeft:361   （361 = 1224 − 863，正是那一屏的横向裁切量）
            button.btn-send rect {x:751, y:601, width:62, height:28}    ← 复读后的新矩形，在 863 视口内
            派发点取的是这份**复读后**的中心，不是 1112 那份

结论：窗口 1200 宽、未最大化、视图停在 863 的界上，这一发仍然真把消息送到了。
旧那句「活体验收必须把窗口带到 ≥1410 宽」从此作废——1410 是 `1224（站点最小布局）+ 185（app 左轨）` 的和，
是动作层的缺口被误记成操作系统窗口的要求。知识包 `chatSendButton` 那条描述已按本节改写。
仍然保留的另一条：`document.visibilityState==='hidden'` 时 CDP 输入不落页（§9 的 2.1-12），
**那是"用户必须在场把窗口带到前台"这条义务，与宽度无关**；本轮两条读数都是在这一句成立之后取到的
（发送前实测 `visibility:'visible'`，此前一次为 `hidden`）。

第四节 · 第一次尝试死在哪里（这是本轮真正的缺陷，另立 8.4-06）
────────────────────────────────────────────────────────────────────────
第一次调用同一发，62003ms 后结构化失败：

    { ok:false, code:'WAIT_TIMEOUT', message:'等待「clickable」超时（5000ms 内未满足）',
      details:{ waitedMs:20206, snapshot:{ elementCount:543, bodyText:'…您好，我对贵司这个岗位很感兴趣，方便聊聊吗？\n按Enter键发送…' } } }

那一轮里：**行选中成功了**（快照正文出现「朱梅 / 上海肯德基有限公司 / 经理 / 兼职·昌平兼职长期稳定服务员 / 查看职位」），
**正文也真落页了**（快照正文末尾就是我要发的那句，输入框里挂着它 + 「按Enter键发送」提示），
死在发送键的「等到可点」那一步。根因单独读过：

    button.btn-send {found:true, cls:'btn-v2 btn-sure-v2 btn-send', disabledProp:false, ariaDisabled:null,
                     rect x=1112, innerWidth 863, elementFromPoint(中心)=null, scrollLeft:0}

也就是：`locator-script.ts` 的 `unobstructedOf` 用 `elementFromPoint` 判遮挡，而**命中测试在视口之外回的是 null**，
于是"根本没在画面里"被读成了"被别的元素盖住"，`clickableStable` 的三条（visible+enabled+unobstructed）永远缺一条，
等 20s 超时。这条等待排在定位与滚进画面**之前**，所以 8.4-05 那一步根本没被执行到。
账本读数证明那一次什么都没发：total 4→4、byAction 无 greet、页面上也没有新气泡——**失败的一侧不落账**。
修法（spec 8.4-06）：`unobstructedOf` 把"这一点在视口外"与"被盖住"分开——前者是"还没滚进来"，
交给滚进画面那一步；视口尺寸读不到（0）时不吃这条快捷路径，仍按命中测试保守处理。
