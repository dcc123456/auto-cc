# 三、密钥的落点（spec 7.2-10 的 U 半边）

  没有第二份映射表；

  命中明文的文件列表 = `[]`；
- `SELECT * FROM llm_providers` 那一行 `JSON.stringify` 后 grep 不到明文。

一条取证口径的教训（本片当场撞上）：这条原本写成 `readFileSync(join(userData,'settings.json'))`，
在"只添加提供商、没有保存过任何设置"的场景下直接 **ENOENT** —— `config` 是在第一次 `setPersisted` 时才建那支文件。
所以"某个文件里没有明文"必须写成**扫目录**而不是按固定文件名读，否则判据会在没有该文件的合法形态上碎掉，
而那种形态恰恰是本片新增的路径（池 CRUD 不碰持久层）。

还没到货的另一半：`stat` 复核 0600、`trace()` 与渲染层回包两面，等 7.2-d 的 IPC 形状落地后按 7.1-06 的口径重取。

# 四、删除的原子性（spec 7.2-09 的存储半边）

`deleteProviderRow` 在**同一条事务**里做两次 DELETE（先 `llm_models`、后 `llm_providers`），
COMMIT 失败则 ROLLBACK。
- 为什么不只靠 DDL 里的 `ON DELETE CASCADE`：全仓 grep `PRAGMA foreign_keys` **0 处命中**（`store` 开连接时没设这个
  pragma，`packages/store/src/*.ts` 里没有一行），SQLite 默认 `foreign_keys = OFF`，于是外键约束与 CASCADE 都是
  装饰性的——只写 DDL 就会长出孤儿清单行。DDL 里那句仍然保留，是为了 pragma 一旦开起来两侧行为一致。
  同仓先例：`packages/store/src/migrate.ts:100`、`packages/resume-kb/src/profile-service.ts:557` 都是显式多语句删。
- 读数：删一家有清单有 key 的实例后 `modelRowsOf(...)` 长度 0、`getSecret(providerSecretPath(id))` 回空串、
  `listProviders()` 里不再有此 id；删一个不存在的 id 回 `LLM_PROVIDER_NOT_FOUND` 且池子不变。
- 第三条"引用它的角色绑定回落到未绑定"随 7.2-c 的 `bindRole` 到货：现在配置格里的 `providerId` 记的还是**预设 id**
  （7.1 语义），与实例 id 不是一个命名空间，此刻去撤它只会撤错。这条写在 `deleteProvider` 的注释里。

# 五、7.2-08 号段与回滚的读数

    store.migrations.map(m => m.version) → [31, 32]
    store.upgrade() → applied: [31, 32]
    store.rollback(30) → reverted: [32, 31]
    回滚后 SELECT ... FROM sqlite_master → llm_providers / llm_models 均不存在
    再 upgrade() → 两张表回来

号段依据：AGENTS.md §9 实测 5.3-a 记的本机台账最高 29，30 被 plan §8.3 预留给 3.6 的草稿表（裁定⑨ 只拦不存，
所以 30 当前未启用），本片取 31/32 并在此登记。
"老库只跑新 up"这一条没有造真老库（每个用例从空目录起），它是按两条间接判据证的：
① 新表挂在**从未记过账**的版本号上；② `跨重启仍然算数` 那条用例在同一份 userData 上第二次装载，
实例行与清单行都还在、`upgrade()` 没有重建表——即台账里已记的版本不会被重跑。
另记一条与 `packages/workflow/src/run-store.ts:260` 同源的纪律：`ensureSchema()` 往 `store.migrations` 里
**push 前必须按 version 判重**，插件重启会重新构造本服务，无条件 push 会在共享清单里留下两个 `version: 31`。

# 六、跨重启（"跨重启仍然算数"这条为什么必须有）

角色的绑定要落 SQLite 而不是配置键（§9 实测 5.3-b：配置层只写内存、重启即失）。本片的表因此必须证明
同一目录第二次装载后实例与清单都还在 —— 用例 `跨重启仍然算数` 把第一次 boot 的 `userData` 递给第二次 boot，
读回同样的实例 id 与同样的清单条数。
