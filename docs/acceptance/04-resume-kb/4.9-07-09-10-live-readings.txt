三、4.9-07 抬头四项真的进文档模型（活体那半：三项落地 + 一项如实为空）
================================================================================

活体（同一份真文档，只报形状不报值，§8.5）：
  profile.name    = 4 字（非空）
  contact.phone   = 11 位数字（原文落在工作副本里，按裁定「工作副本存原文」）
  contact.email   = 在（含 @ 与点号）
  contact.location = null ← 这一项**不是抽取缺陷**，见下面的取证

为什么 null 是对的（一次判定性观察，`tmp/probe-city.ts` 走 app 自己那条 `extractSourceText` 通道）：
  这份 PDF 抽出来 201 行，抬头前 8 行的长度是 [6, 6, 22, 19, 22, 34, 29, 14]，
  全文里能对上城市形状的令牌只出现在第 45 / 54 / 66 / 78 / 89 行（「上海」，工作经历里的公司地）
  与第 154 / 155 行（「重庆」，教育/项目段），**抬头那几行一个都没有**。
  `pickLocation` 只扫抬头行（`rawHeaderLines`），所以它回 null 是"抽不出即为空、不编造"（4.9-08 同一条），
  清单因此显示 所在城市 = weak（在，但不合格 → 这一项在文档模型里是空的），并把它算进缺项提示。
  四项的**正向**断言在单测里按 PDF 抬头形状跑（`sections.test.ts` 的 `4.9-b`：
  「李测试｜13800002222｜litest@example.com｜上海市」→ name / phone / email / location 四项逐字对上，
  且不带「市」后缀的「深圳」也认）。所以本行的状态位是 [x]，但城市这一格在真实那份上的结论是"源里没有"，
  不是"抽丢了"——两种写法在界面上长得一样（都显示 weak），靠这一条读数分开。
