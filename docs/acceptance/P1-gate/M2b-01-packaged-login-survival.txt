-- 3. 登录态写入 → 干净退出 → 重启读回（同一条 UI 路径，非注入） --
第一轮（PID 2329）：`harness click --text 诊断` → `harness click --selector '[data-session-id="fixture"] [data-action="open"]'`
两次都返回「已点击 <button>（原生鼠标事件）」，内核视图被 `persist:fixture` 分区加载到
`http://127.0.0.1:10233/`（本地 fixture 站点，未碰真实招聘平台，符合 §7.2）。
在 fixture 页求值写入标记，返回：
  marker = p1-04-2026-09-29T16:58:02.965Z
  lsKeys = ["p1-04-marker"]，cookieCount = 0
  bridgeExposed = "undefined"，ipcRendererExposed = "undefined"，preloadGlobals = []
  （外部视图不挂 preload，这三条正是 §8.1 的底线在打包版上成立）
退出方式：CDP `Browser.close`（`tmp/m2b-close.mjs`），端口随后释放 —— leveldb 靠正常关闭流程落盘，
不用 taskkill 强杀，避免把「没落盘」误当成「没持久化」。
第二轮（PID 2374，同一 --user-data-dir 重新启动）：同样两次真实点击重开 fixture 视图，读回：
  lsMarker  = "p1-04-2026-09-29T16:58:02.965Z"   ← 与第一轮逐字相同
  idbMarker = "p1-04-2026-09-29T16:58:02.965Z"   ← IndexedDB 同样跨重启
  origin = http://127.0.0.1:10233，isSecureContext = true，readyState = complete
localStorage 与 IndexedDB 两条存储都活过一次进程重启，且是在**打包产物**上发生的。

-- 4. 顺手复验了 1.6-08 留给打包态的那半条 --
同一轮取 `devtools.status()`：`isPackaged=true`、`isCdpEnabled=false`、`cdpPort=null`、`targetCount=2`，
而 `curl http://127.0.0.1:10222/json/version` 同时返回
`{"Browser":"Chrome/152.0.7977.130", … UA 含 auto-cc/0.1.0}`。
两个读数不矛盾，且必须写清楚它们的差别：**app 自己不会开 CDP**（打包闸门 `resolveCdpPort(…, true) → null`，
产物不带这个开关），但由启动者**从外部追加** `--remote-debugging-port` 时，Chromium 仍会照命令行开出端口 ——
这是所有 Chromium 产品的固有行为，不是本项目的闸门漏了。本轮正是靠外部追加的开关才观测到第 3 节的过程；
1.7-06 早先记录过同样的组合（isCdpEnabled=false + 端口可用），本次是在 1.11 之后的新产物上复现。

「全新机器只装 app（无 Node / 无系统 Chrome）即可运行」：PASS（剥离 PATH + 包内 file:// 资源 + 窗口可见
`windowVisible=true`、`kernelViewVisible=true`、内核视图摆位 451x737）。
