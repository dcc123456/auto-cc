plan §4.6「前置」原文：两次 accept + 一次重排落在 resume-0185fba4a2cc 之后

诚实交代一处过程损耗：第一次复算是在另一支探针里跑的，那支探针在打印阶段抛了

所以**那一次的 created/updated/removed 三个计数器没能留下来**。本节因此改从两个可复现的角度取证：
行级 createdAt≠updatedAt（复算改写过的行会留下痕迹，与计数器同等信息量）+ 重跑一次 sync 证幂等收敛。
不拿"应该是 2 条"冒充实测读数。

2. 收敛：同一 docId 再同步一次是 0/0/0，不是"每次改配置就重写一遍"
────────────────────────────────────────────────────────────────────
kb.profile.sync('resume-0185fba4a2cc') 的第二轮读数（本次探针当场跑的）：

  { "docId": "resume-0185fba4a2cc", "created": 0, "updated": 0, "removed": 0 }

三个零各自说明一件事：没有新增实体（内容没变）、没有重写实体（索引与实体已对齐）、
没有清理实体（4.5 的 accept 是改写现有行而不是删旧建新）。
这条是 §9「热改配置会重建下游插件」那类失效的反证：复算不是一次性动作，
但重复执行它不产生 churn，所以后面每一片随时可以再喊一次。

4. 这一片实际做了什么（不写代码就没人信的"前置"要落成动作）
────────────────────────────────────────────────────────────────────
复算走的是公开入口 kb.profile.sync（白名单里第 1371 行那条），它内部同时重算
kb_entities 与 FTS/kb_chunks 派生表（reindexSectionChunks）。没有手搓 SQL 去 UPDATE 索引，
