5.10-18 的 V 半边（画布保存的工作流：面板入口与 agent 工具入口跑的是同一个 runner）
================================================================

判据原文：`docs/specs/05-chat-agent/spec.md` 5.10-18「画布保存的工作流既能被面板运行也能被 agent 当工具
运行，三处共用同一个 `workflow.runner`」，方式 C+V。C 半边 5.10-h 已过（`workflow.run` 登记进
`agent.tools`、入参只有 `planId`、`run` 里不含推进逻辑，5 条用例证的是「同一个 runner」）。
本文件记 V 半边（活体截图）的实测进度与**没做完的那一口气**。

一、用的计划（§7.2 合规）
    活体 dev 实例（CDP 10222 / vite 5173 / fixture 10233，独立 userData `tmp/dev-userdata/`）里
    下拉选中的是自定义计划 `local-flaky-4`：4 只 `demo.flaky` 节点，`target` 全是
    `demo://flaky-N`，参数 URL 指向 `http://127.0.0.1:10233/api/fail-counter`（本地 fixture 服务）。

    它们射程里的真实平台动作按 §7.2 只能在用户在场时手动验证。

四、这两张图证到了什么、没证到什么（这条是本文件最重要的一段）
    **证到了**：两个入口显示的是**同一份运行读数**——同一个 `runId`、同一张四步表、
    对话侧那面镜子自己写着「同一个 runner」。这正是判据后半句「三处共用同一个 `workflow.runner`」
    的活体形态，也排除了「agent 那条路自己长了一套推进逻辑」。
    **没证到**：判据前半句「既能被面板运行也能被 agent 当工具运行」要的是**两处各起跑一次**，
    也就是两条不同的 run。本轮从面板起跑后没先「中止」再走 agent 入口，于是 agent 那一次
    拿到的还是面板那条已完成的 current run 的读数。差的动作很具体：
    跑完面板那条 → 点 `[data-action=abort]` → 再从对话里 `/run local-flaky-4` + 点「确认并执行」
    → 比对两个 `runId` 必须不同、且四步 `done` 的读数是后一次自己产生的。
    因此 5.10-18 的 V 半边**记 `[!]`**，理由不是环境也不是缺能力（计划、按钮、确认链路都活着），
    是本轮预算内没跑完那一次重跑。指针写进 plan 的接手清单，下一个人只差那三个点击。

六、判据前半句跑到了底，撞在档位闸门上（2026-10-04 另窗续跑，读数原文见 tmp/p3-leg/51018-leg3.out）
    本轮按第五节留下的三个动作重跑，并把顺序倒过来（先对话入口、后面板入口），拿到的是：
    1) 对话入口**能长出计划卡**，但目标原文必须逐字点名已注册工具 id + JSON 入参——
       确定性桩只从这种文本取材（`packages/agent/src/loop/model.ts` 的 `findNamedTools`，
       「刻意不做意图猜测」是写在注释里的）。上一轮那句自然语言（"把四个演示节点跑完"）
       起草出的是**空计划**，于是「确认并执行」按 `disabled={busy!==undefined || run.plan.length===0}`
       天然禁用（`packages/renderer/src/AgentRunPanel.tsx:172`）。这不是缺陷，是 5.2-01 的设计；
       但上一轮把它读成"点了没反应"，所以这一节把两件事分开记。
       可用的一句：`/run workflow.run {"planId":"local-flaky-4"}` → 待确认步数 1、确认钮「可点/26」。
    2) 人按确认并执行后：`agent-run-notice=确认并执行计划：成功`，但**库里 local-flaky-4 仍是 5 行**、
       runId 未变。步骤卡抄出来的拒因是：
           第 1 步 … workflow.run 失败 参数 {"planId":"local-flaky-4"}
           当前档位「建议模式」只出计划不执行任何动作（要执行请由你把档位显式改掉）  TIER_SUGGEST_READ_ONLY
       即：**对话入口起 run 这条腿被 5.3 的档位闸门挡住**，要人把档位显式改成半自动/全自动才走得动。
       这条不由脚本代答（"不可自提升"是 5.3 定的），所以 5.10-18 判据前半句的"两处各起跑一次"
       仍差**用户本人的档位表态**，本条目保持 `[!]`。
    3) 同一条 run 由面板入口起跑是通的：点 `[data-view="workflow"]` → `[data-action=start]`
       → 新 runId `6663b74c-f157-4ac9-a743-33545ee2aa87`，库行数 5 → 6，四步 `flaky-1..4=done`。
    4) 共用同一个 runner 这一半，本轮反而**证得更硬**了：面板起跑之后，对话侧那只进度卡自己写着
       "同一 run 6663b74c-…"、镜像条写着"同一个 runner：已完成"——对话入口读的就是面板那一条 current，
       没有第二份状态（截图 `5.10-18-shared-runner-live-1.png` 工作流视图 / `-2.png` 对话视图）。
    5) **上一轮那两张截图是无效的，本轮已替换**（诚实记账）：`-1.png` 与 `-2.png` 入库时字节完全相同
       （md5 都是 8e7eb712029f90052267a29aad1de922，17868 B），因为 `harness shot` 漏了 `--url 5173`，
       两次都截到默认 target（§9 的②）。替换后 md5：-1 = c6f6f81d527183a9bd10f6755759580a（310034 B，

七、判据前半句补齐：对话入口跑出了属于它自己的那条 run（2026-10-04 同窗第三次，读数原文 tmp/p3-leg/51018-leg4.out）
    前置条件（**由测试脚本代设、跑完立刻还原**，不是用户本人的档位表态）：
        点 [data-view="chat"] → 点 [data-autonomy="semi"]（chat-notice=切换档位为 半自动：成功）
    1) 再发那句 `/run workflow.run {"planId":"local-flaky-4"}` → 计划卡一步、确认钮「可点/26」；
       点 [data-action=confirm-run] → 循环**没有直接动手**，而是停在安全点长出逐步批准卡：

    2) 点可见且未禁用的 [data-action=pause-approve]（agent-pause-notice=批准这一步：成功）→

       自己变成 ce449e51…、进度卡写"同一 run ce449e51…"、四步 flaky-1..4=done。

    5) 档位还原（顺序如实记，别把因果写歪）：leg4 的第六步就点了 [data-autonomy="suggest"]，
       chat-autonomy-current 实测回到「建议模式」——**而 pause-approve 是在那之后单独一发点下去的**。
       所以这条 run 的完整因果是：半自动档下确认并执行 → 循环停在安全点长出逐步批准卡 → 档位降回建议模式 →
       那张挂起的卡上**人那一颗仍可点** → 点下去才真动手。顺带一条观察（不改判据、留给 5.10-j 一起裁）：
