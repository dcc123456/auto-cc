# 10.12 在场会话：QA 探针与证据模板（今晚备，明早按序跑）

目标：明早一次 40 分钟的在场会话里，把剩下 8 条判据取成**可逐条核对的读数**，而不是「看起来对」。
每条写死三样：**读什么**（具体命令/字段/选择器）、**判据**（什么算过）、**失败即停**（什么情况立刻停）。
统一环境：`c15c449` 起（开发重打后如有新提交，以当日 HEAD 为准，并记下 sha）；CDP 端口按 QA 自己的号段；
真站只由**用户本人**操作登录/验证码/最后确认那一笔；我们只读、只取证、不代做。

三条全局红线（任一触发就整轮停，不重试、不绕过）：

1. 出现验证码 / 风控页 → 停，存页面原文与截图，不改 UA、不重试、不刷新；
2. 四方对账任一笔对不上 → 停后续外发，先对账；
3. 越权面出现（授权范围外的外发、助手在未登记来源上写动作未被拦）→ 停并上报。

## 1. 登录三态与「接下来」（`10.11-02` / `10.11-06`）

**读什么**
- `window.autoCC.sessions.status()` 每行取 `id / partition / auth / expiresAt / cookieNames.length`；
- Home 三块：`[data-testid=home-status-unattended]`、`home-status-run`、`journey.unattended.view()`；
- 阻断条数量：`document.querySelectorAll('[data-testid^=home-blocker]').length`；
- 主行动：页首那颗 `[data-action]` 的 `textContent` 与 `disabled`；
- 「接下来」六条：`[data-testid=home-next]` 下的行，逐条 `textContent` + 落点 `data-action`。

**判据**
- 三态只出现一种，且与事实一致：`active`（BOSS 有效会话）/ `expired`（过期）/ `unknown`（判不准，**不发** `session/expired`）；
- 已登录时阻断条 **0**、主行动唯一且可点；未登录时阻断条 ≥1 且文案指向登录；
- 「接下来」六条顺序固定、每条落点存在（点得动）。

**失败即停**：`auth` 与页面实际状态矛盾（页面已登录但 `auth=expired` 之类）→ 停，记两边原文。

**证据**：`docs/acceptance/10-job-journey/10.11-02-qa-login-states-readings.txt`（含脱敏后的 auth 行，不带 cookie 值）。

## 2. 前台焦点环（`10.11-13`）

**读什么**
- 窗口必须在前台（`document.hasFocus() === true`，先读一次确认）；
- 依次 Tab 过 6 个可聚焦元素，每次读 `document.activeElement` 的 `data-action` 与 `matches(':focus-visible')`；
- 取该元素的 `outline-color / outline-width / box-shadow`（焦点环是不是真的画出来了）。

**判据**：`:focus-visible` 为真且可见的焦点环存在（`outline-width ≥ 1px` 或 `box-shadow` 非 none）；
Tab 顺序自然（不自造 tabindex 跳跃）；`Esc` 回到胶囊（`[data-action=assistant-capsule]`）。

**失败即停**：窗口抢不到前台（`hasFocus()` 为 false）→ 这一条记 `[!]` 并说明「需前台窗口」，**不拿后台读数冒充**。

**证据**：`10.11-13-qa-focus-ring-readings.txt`。

## 3. 200% 系统缩放（`10.11-23`）

**读什么**
- `window.devicePixelRatio`（200% 时应为 2）；
- 三档视口下 `document.documentElement.scrollWidth <= clientWidth`；
- Home 三块与岗位卡的 `getBoundingClientRect()` 是否互相重叠（两两交集判据）；
- 三张截图（100% 前 / 200% 后 / 收窄后），`md5 -q` 互异。

**判据**：`devicePixelRatio=2` 下无横向溢出、无裁切、无重叠；截图三张互异。

**失败即停**：系统缩放改不了（需要用户手动改设置）→ 记 `[!]`，**不用 `Emulation.setDeviceMetricsOverride` 冒充**（那改的是页面视口，不是系统缩放）。

**证据**：`10.11-23-qa-zoom200-readings.txt` + `10.11-23-qa-zoom200-{before,after,narrow}.png`。

## 4. `site-default` 未确认被拒 vs 确认后账本只增 1（`10.11-25` / `10.11-26`）

**读什么**（三只口，读的都是真相不是界面文案）
- `usage.ledger.recentAttempts(20)`：每行的四元组 `platform+target+action+resumeVersion`、`status`、账本 id、页面回执；
- `usage.ledger.summary()`：`today`、`byAction`、`recent`、`recentDenials`（被拒的不进 totaL，只进这里）；
- `outbound.authorization.current()`：授权单的 `targets` 与 `status`。

**判据**
- 未确认的 `site-default`：**被拒**（`recentDenials` 出现一条，带结构化原因），且 `summary.today` **不变**；
- 用户确认后同一条再发：成功一次，`summary.today` **只增 1**（不是 2）；
- 同日第二次确认同一笔：**被拒**（去重按四元组），账本**不增**。

**失败即停**：出现任何「页面回执成功但账本没动」或「账本增了但四元组没有对应行」→ 停，先对账。

**证据**：`10.11-25-qa-site-default-readings.txt`（含三条的 `recentDenials` 原文与 `today` 前后值）。

## 5. 优雅退出后 cookie 落盘（`10.11-30` 的 ⑧⑨）

**读什么**
- 退出前：`sessions.status()` 的 `cookieNames` 逐平台 + 主分区 cookie 表行数（只读 `<userData>/Partitions/*/Cookies` 的 `COUNT(*)`，**不导 cookie 值**）；
- 用**正常退出**（托盘退出/`app.quit()`，不是关窗强杀），等进程退净；
- 重启后：再读同样的两份；确认 `fixture`/`zhipin` 分区在、`persist:web` 标记不在、旧目录仍留。

**判据**：重启前后**同一分区的 cookie 行数不减少**；`auth` 重启后仍 `active`；分区目录结构没有被迁移清掉。

**失败即停**：重启后 cookie 清零 → 停，这是「登录态丢失」，比任何功能缺陷都严重。

**证据**：`10.11-30-qa-cookie-persist-readings.txt`（只写行数与分区名，不写 cookie 名以外的任何值）。

## 6. 真实输入法组字（`10.11-32` 的组字项）

**失败即停**：组字期间列表清空 → 记录当时的 `value` 与采样时间线，停这一条（后面继续）。

## 8. 真实链路（本轮主目标，`10.7` 全 `[x]`/`[!]`）

**读什么**：四方逐笔（列名已按真实 schema 核对过，**不是猜的**）——
1. **页面回执**：`browser.page.snapshot()` 的对话页文本 + 投递确认后的页面状态；
2. **账本**：`usage.ledger.summary()`（`today`/`byAction`/`recent`/`recentDenials`）+ `usage.ledger.recentAttempts(20)`；
3. **投递记录**：只读 SQLite `delivery_records`，真实列是 **`ledger_id, platform, job_id, snapshot_id, ts, conversation_target`**
   （**没有** `action` / `resume_version`）；
4. **四元组**：`outbound_attempts` 表——真实列 **`id, platform, target_id, action, resume_version, workflow_run_id, status, ledger_id, receipt_id, reason, updated_at, confirmed_at, evidence_summary`**。
   它和 `delivery_records` 用 **`ledger_id`** 关联，`usage_ledger`（`id, action, target_id, workflow_run_id, ts, source, remote_ref`）是那本账。

**对账表的正确连法（给 PM 的表也用这个）**：
`usage_ledger.id` ←→ `outbound_attempts.ledger_id`（四元组 + 状态 + 回执 id）←→ `delivery_records.ledger_id`（投递凭据 + `snapshot_id`）。
一行一笔 = 一个 `ledger_id`；页面回执用 `receipt_id` / `remote_ref` 对，**不要**拿 `delivery_records` 去对 action/version（它没有这两列）。

**判据**
- 同一条外发在四方里是**同一笔**（时间、目标、动作、简历版本一致）；
- 账本增量 == 页面回执成功次数 == 投递记录新增行数（逐笔 1:1）；
- 同日重复发同一四元组 → 被拒且四方都不增。

**失败即停**：任一笔四方不一致 → 停外发、先对账、把三份读数原样贴出。

**证据**：`10.12-onsite-4way-recon.txt`（PM 的对账表逐行填）+ 脱敏截图。

## 附二：**行键用 `ledger_id` 会丢「失败笔」**（明早对账表必须避开）

实测 `outbound_attempts` 4 行里，`ledger_id` **全是 null**（0/4 有账本号）——因为它们都是被拒/未决的 `unknown`。
这不是脏数据，而是结构决定的：**只有真正发出的那一笔才会先落账本拿到 `ledger_id`**；被闸门拒掉、`WAIT_TIMEOUT`、
`site-default` 未确认这些**根本不会产生账本行**（它们进的是 `usage_denials`，不是 `usage_ledger`）。

所以对账表的行键**不能只用 `ledger_id`**：

- 若行键 = `ledger_id`：所有「失败笔」都没有键，而 PM 的 §1 又要求「失败笔也占一行、结论写『未发生』」——**失败笔会被挤掉**，
  而失败笔恰恰是最需要留证的那一类（它证明「没发生」，也证明闸门真的拦住了）。
- 建议口径：**行键用四元组**（`platform|target_id|action|resume_version`，空版本归一成 `unversioned`），
  `ledger_id` 作为**列**（成功笔填账本号，失败笔填「无」并另给 `status/reason` 与 `usage_denials` 里的那条原因）。
  这样一笔一行、失败笔在位、成功笔还能用 `ledger_id` 连到 `delivery_records`。

判据不变：成功笔必须满足「页面回执 ⇔ 账本恰增 1 ⇔ deliver 恰增 1 条投递记录」；
失败笔必须满足「四方都不增 + 有一条结构化原因」。
