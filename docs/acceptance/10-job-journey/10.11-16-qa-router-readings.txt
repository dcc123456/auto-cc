## 发现

### H（P1）：`draft_plan` 结构上出不来计划卡——`agent.loop.propose` 是 async，端口按同步取

`packages/agent/src/session.ts` 的 `routePorts().propose`：
`const run = loop.propose(goal); return Promise.resolve({ runId: run.runId, steps: run.plan.length });`
`agent.loop.propose` 是 async（`loop.test.ts` 全部 `await loop.propose(...)`），`run` 是 Promise → `run.plan` 为 `undefined` → `.length` 抛 `TypeError`。活体复现：`route_refused: ROUTE_FAILED`；而桥口直调同一个计划器给的是结构化错误 `AGENT_PLANNER_UNAVAILABLE：模型通道未配置，缺 baseUrl / model / apiKey：先在「信任」工作台里配齐对话通道`——**真正的原因被吞成 `ROUTE_FAILED`**，既不是「不允许」也不给出口。即使配齐模型，按这段代码也仍会抛 TypeError，计划卡永远出不来。

### I（P1）：`explain` 的两个读数都是假的——`kb.search` 是 async、`trackingCurrent` 是硬编码

- `routePorts().kbSearch`：`const result = kb.search(query); … result.rows?.length ?? 0`；而 `packages/resume-kb/src/profile-service.ts:1561` 是 `async search(query): Promise<KbSearchResult>` → `result.rows` 恒为 `undefined` → **命中数恒为 0**，库里有没有行都一样。
- `routePorts().trackingCurrent`：`() => Promise.resolve({ jobId: null, state: null })` —— **写死 null**，没有读任何追踪口（设计里写的是 `journey.tracking.current`）。
- 两条合起来：`explain` 永远说「命中 0 条、当前岗位 —」，不可能兑现判据要求的「可回指的库行」。这同时是 17 第 4 条「编读数」的结构性缺口（它不是编一个数，而是把读不到画成 0/—）。

### J（P2）：`reminder` 不带暂停原因，且把英文枚举甩进中文句子

seeded 的 `pause_reason`（「页面出现验证码，本轮暂停等人确认」）在回执里**一个字都没有**；`runStatus`/`authorization` 直接渲染成 `idle`/`paused`。判据 16⑥ 要求「能读到暂停原因与待办」——待办（2）有，原因没有。修法建议：`reminder` 的 params 补 `pauseReason`（授权单/执行器各自的原文），文案里状态走语言包（`home.runState.*` 已有）。

### G（P2）：`unknown` 回执没走「没听懂 + 示例」，落回开发骨架文本；`route_unknown` 文案零引用

`session.ts:1133` 在 `reading.intent === 'unknown'` 时 `return false`，于是走 `fakeReplyFor()` 的骨架句：里面写着「这是对话骨架的本地确定性回复」「按 2.8-10 经额度闸门与账本」「想演示工具卡片，把消息以 /tool 开头再发一次」——用户看到的是开发说明与 spec 编号。而语言包里 `assistant.notice.route_unknown`（「没听懂这句。你可以这样说：…」）**全仓零代码引用**（`grep -rn route_unknown packages --include=*.ts` 只命中注释与 locale）。PM 裁的「没听懂」与「听懂了但不允许」两种回执，目前只有后者生效。
