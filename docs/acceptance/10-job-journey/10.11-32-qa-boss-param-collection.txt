## 缺的两个维度：行业 / 融资 —— 被一个 P1 阻断

**复现步骤（可复现两次）**：
1. 打开 BOSS 搜索页（`query=前端`），页面正常、`shell.getStatus()` 正常；
2. 点「公司行业」这一栏的下拉头（`.current-select` 里含「公司行业」的那个 div）；
3. → `/json/list` 里 zhipin 的页面 target **消失**；再调 `shell.getStatus()` / `sessions.status()` 都抛：

```
{ code: "UNKNOWN", message: "Cannot read properties of undefined (reading 'isDestroyed')" }
```

地址栏也随之失效（`shell.getStatus` 取不到，右栏渲染不出来）。第一次出现是在我读页面之后（未点击时也可能被触发），第二次是明确的「点行业下拉头 → 视图消失 → 状态调用抛错」。

**判定：P1 —— 内核视图一旦被销毁（或销毁后未清理引用），`shell`/`sessions` 的读接口抛原生 TypeError，整个右栏与地址栏瘫掉。**
不是「行业这栏读不到」的问题，是**视图没了之后服务没有兜住**：正确行为应是「视图不存在」的读数（`kernelViewVisible:false` + url 空），而不是 `isDestroyed` 的空引用异常。

## 更正 + 关键读数：那条栈其实写出来了，但栈**指不出调用方**

上一条我写「日志里页面被销毁 0 条」——**那是错的**，我只看了 stdout。`ctx.logger` 落盘在
`~/Library/Logs/auto-cc/auto-cc.log`，里面确实有这两行（本机时间 12:07:08 / `8a79e85` 构建）：

```
WARN [shell-service] 内核视图的页面被销毁｜Error: kernel-view-destroyed
    at WebContents.<anonymous> (/private/tmp/qa-11/tree/packages/main/dist/main.cjs:142905:59)
    at WebContents.emit (node:events:514:28)
WARN [shell-service] 内核视图已失效（页面销毁或进程退出）：清掉视图记位，下一次导航会重开一个
```

**判断**：这段栈只有两帧，且都落在**我们自己的 `destroyed` 监听器里**（`new Error()` 是在监听器内部构造的，栈顶必然是监听器自身 + `EventEmitter.emit`）。所以它**不能点名是谁销毁的 webContents**——这一点对开发很关键：如果想抓调用方，必须把打点放在**销毁动作的调用点**（包住 `webContents.close()/destroy()`，或在 `removeChildView`/`close` 之前记 `new Error().stack`），而不是放在 `destroyed` 事件里。

另：整份日志里**没有** `render-process-gone` 行，再次排除渲染进程崩溃。

## 销毁现场判定（`64061ec` 的调用点栈尾迹）——结论：**不是我们重建，是外部/站点侧杀的**

`shell.getStatus().kernelViewGoneStack` 原文（12:22:51–12:23:10，`ud-onsite4`，真站搜索页）：

```
销毁栈: stackBrief ← goneScene ← WebContents.<anonymous> ← WebContents.emit
before:
 12:22:51.443 createKernelView partition=(placeholder)
 12:22:51.445 new kernel view assigned
 12:23:10.438 mountKernelSite partition=persist:browser   ← ensureBrowser
 12:23:10.438 createKernelView partition=persist:browser
 12:23:10.438 closing previous kernel view ← createKernelView ← mountKernelSite ← ensureBrowser
 12:23:10.439 new kernel view assigned
```

**判读**（按开发给的三种）：
- 最后一次 `closing previous kernel view` 只出现在 12:23:10.438 那一次**我们自己的建视图**（栈点名 `ensureBrowser → mountKernelSite → createKernelView`），之后 12:23:10.439 `new kernel view assigned`；
- 真正销毁发生在**之后很久**，尾迹里**没有任何新的 `closing`、也没有 `mount`**——所以**不是我们重建**；
- 也不是 `reapDeadKernelView` 先于 `closing` 的那种；是**外部/站点侧把 webContents 杀了**（`window.close()` 一类）。

按开发自己的判读表，这属于「**外部/站点侧杀的**」那一档 → 需要重新裁「禁止页面自关」还是「接受并恢复」。

## 建议（给裁定参考）

1. **禁止页面自关**：在 `dom-ready` 注入 `window.close = () => {}`（不挂 preload、不改安全底线），或捕获 `contents.on('close')` 阻止；风险是站点行为可能依赖自关（例如城市选择本来靠“关旧页开新页”）。
2. **接受并恢复**：`destroyed` 后自动重建视图并回原 URL + 一条可见提示；代价是每次点击可能有可见闪断，且要处理恢复循环。
3. 无论选哪条，都要保住「不是我们重建」这条区分：尾迹里已能分开（`closing` 有调用点栈 vs 没有），这套读数可以继续用。
