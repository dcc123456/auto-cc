## 二、三条动作各一次

| 动作 | 点击后读数 | 账本 |
| --- | --- | --- |
| **批准** | 按钮消失、run 继续跑到第 1 步；该步因**缺参数**进入「补信息」卡（`agent-pause-supply` 输入框在），**没有自动补参、也没有外发** | `ledger 13 / attempts 7 / deliveries 0`（零增） |

- 「批准后是否只出现一次外发尝试」这一条**没验到意义**：批准后卡在「缺信息」，闸门链继续挡着，所以是 0 次而不是 1 次；
  要验「恰一次」，得给一步带全参数的外发（现有 stub 只按点名的工具 id 出步，不产参数）。

## 五、D2 精确化：**不是「慢」，是界面路径的「拒绝」根本没生效**

上一节只能写「8 秒未落定」。这次改用**库里的 run 行**做 60 秒轮询（400ms 一次），并且先确认点的是新 run 的按钮：

| 项 | 读数 |
| --- | --- |
| 新 run（界面 `/plan` 起） | `864f5215-f8c2-4b23-8d94-9473ea735fb6`，`status:"running"` |
| 点「拒绝」 | `{clicked:true, text:"拒绝"}`（可见、且点到了） |
| 60 秒里 run 行 | **`status` 一直 `running`、`stop_reason` 一直 `null`、`updated_at` 从 `1795496332679` 一动不动** |
| 账本 | `ledger 13 / attempts 7 / deliveries 0`（零增） |

**这不是「落定慢」，是这次点击对 run 没有任何影响。** 与开发报的「桥接口起的 run，`stop-run` 是空操作」正好互补：

| 起 run 的入口 | 「拒绝」 | 「叫停」 | 「批准」 |
| --- | --- | --- | --- |
| 桥接 `agent.loop.propose` | **有效**（两条落 `PAUSE_DENIED`：`cfff78c1…`、`6603cd86…`） | **空操作**（开发已报） | 全自动档不渲染 |
| 界面 `/plan` | **无效**（本条 60 秒零变化） | 8 秒未落定（本轮 `deny-stop.mjs`） | semi 档渲染、可点（点了进入「补信息」卡） |

所以 D2 的修法不是「等久一点」，而是**把两条入口的 runId/待决单绑定统一**——同一条 run 无论从哪个入口起，
三只审批键都必须打到同一张待决单上。建议给开发一条可复跑的判据：**同一 runId 下，界面起与桥接起各连跑三次，
三只键都必须 5 秒内落定**。

## 六、更正上一节：不是「通道差异」，是**拒绝常被忽略、生效也慢到 86–118 秒**

上一节我写下「界面路径的拒绝完全无效」的推论，**这一节用库里的全量 run 行把它推翻**（我自己的错，先纠）：

| run | 档位 | `stop_reason` | 从创建到落定 |
| --- | --- | --- | --- |
| `864f5215` | semi | **`PAUSE_TIMEOUT`** | **120s** |
| `da2ec288` | semi | **`PAUSE_TIMEOUT`** | **120s** |
| `f18e5994` | semi | **`PAUSE_TIMEOUT`** | **150s** |
| `0b839707` | semi | `PAUSE_DENIED` | **86s** |
| `e293ce55` | semi | `PAUSE_DENIED` | **118s** |

按档位聚合：`auto` → `PAUSE_DENIED` 2 / `PAUSE_TIMEOUT` 3；`semi` → `PAUSE_DENIED` 2 / `PAUSE_TIMEOUT` 3。

**所以真实形态是两条，而不是我说的「某条入口失效一半」**：

1. **拒绝被忽略的比例很高**：两种档位都是 **2 拒绝 : 3 超时**——我点「拒绝」的那几条里，有一部分最终以
   `PAUSE_TIMEOUT` 收尾，也就是点等于没点，靠 120 秒超时兜底。这才是 D2 的形态。
2. **即便拒绝被认，落定也慢得离谱**：两条 `PAUSE_DENIED` 分别用了 **86 秒 / 118 秒**，**没有一条在 5 秒内落定**。
   这与「拒绝后 5 秒内必须落定」的判据差距是数量级的，不是「偶尔慢一点」。

**给开发的判据（可直接复跑）**：同一档位连跑 3 次「拒绝」与 3 次「叫停」，要求 **6/6 在 5 秒内落定**，
且 `stop_reason` 与所点动作一致（拒绝 → `PAUSE_DENIED`，叫停 → `stopped`/`stopping`），零外发。
按本次读数，现有实现是 **0/5 达标**（最快的 86 秒），修复前后差别会一眼看出来。

**顺带一条**：`agent_run.autonomy` 是**创建时定格**的（库里那 8 条各自记着 auto/semi），所以「切档位后老 run 仍按旧档位走」是设计行为、
不是缺陷；但**老 run 上没有批准键时也没有补救出口**，这正是 D1 要裁决的那半条。
