10.12-08 审批门禁三处缺陷（D1/D2/D3）的复验与修法（2026-11-24，开发侧）

**D1「全自动档没有批准出口」——口径要更正：那不是确认单，是补充信息单**
- 两张卡是两种东西，界面标签就不一样：确认单的否定键是「**拒绝**」（`agent.pause.deny`），
  补充信息单的否定键是「**放弃**」（`agent.pause.giveUp`），另外还有一颗「提交」与一个补充输入框
  （`data-testid="agent-pause-elicitation"` / `agent-pause-supply-input`）。
- QA 报的是「放弃」，所以那张是**补充信息单**：全自动档按 2026-10-26 裁定**不问批准**（一次性明示之后逐步放行），
  卡住它的是入参缺字段——`outbound.greet.perform` 的入参是
  `{ request: { platform, jobId?, conversationTarget?, text } }`（`platform` 与 `text` 必填），
  桩按 goal 里那段 JSON 给入参，goal 只写了工具 id 时入参是 `{}`，于是开的是「这一步还缺信息」。
- 结论：**没有可批的事**（不是缺批准键），也不该「立即拒绝」（缺的是信息，不是被拒）。
  真要改的是文案侧——那张卡已经写明「这一步还缺信息 / 还缺或不合契约的字段」，超时那句也写明
  「到点无人表态就按未批准收掉，绝不默认放行」。这条建议按口径问题收口，不算缺陷。

**D2 拒绝后偶发停在 `running`——已加结构性兜底，复验两次都在 10 毫秒内落定**
- 修法：`packages/agent/src/loop/loop.ts` 新增 `executeToSettlement(scope)`，`confirm` 与 `resume` 都改走它。
  `execute` 的每条正常出口本来就调 `finish`，但它自己也可能抛（库写失败、上下文被重建、意料之外的断言）——
  抛出去就会留下一条永远 `running` 的 run。现在：**抛也只落 `failed`**（`AppError` 用它的码，
  其余记 `STEP_UNSUCCESSFUL`），并且只在 `scopes` 里还有它时才收（不把已 `completed` 的改写掉）。
- 活体复验（半自动档，同一份 fixture 装配，点 `pause-deny`）：两条 run 分别 **7ms / 4ms** 落到
  `failed` / `PAUSE_DENIED`，`agent.pause.pending()` 归 0，抬头「确认单已按你的表态收掉（第 1 轮）拒绝这一步：成功」。

**D3 确认调用阻塞两分钟——界面这一侧改成不等，主进程语义保持不变**
- 修法：`packages/renderer/src/useAgentRun.ts` 的 `confirm()` 不再 `await` 主进程那一口，只把调用抛出去，
  状态一律走 `agent/run-progress`。理由写进注释：主进程这条口的语义是「确认并跑完整条循环」，
  碰到确认单会等到人表态或超时；界面等它就会把「按一下」画成「忙到超时」，而人此刻要做的正是在卡片上表态。
- 活体：点「确认并执行」到确认单可见 **8～10 毫秒**（改造前要等整条循环，最长 120 秒）。
- **为什么不改主进程那一口的返回值**：`agent.loop.confirm` 的返回值是「跑完之后的读数」，全仓 **69 处**调用点
  （其中 65 处在 `loop.test.ts`）都按这个语义写。把它改成「立即返回 running」要重写这 65 条用例的等待方式，
  换来的只是程序内调用者的语义变化，而用户能感到的阻塞已经在渲染层消掉。这一条请 PMO 判是否还要动主进程契约。

**截图**：`10.12-08-approval-card-deny.png`（确认单本体：批准 / 拒绝两颗键 + 收单后的那句「拒绝这一步：成功」）。

## 补：暂停单号挂到按钮与 band 上（2026-11-24，治「点错卡」的根）

`pause-approve` / `pause-deny` 现在各自带 `data-pause-request-id="<单号>"`；band 容器带
`data-pause-request-ids="<按开单顺序的空格分隔清单>"`（**多张单时不给单数属性**——写一张就会撒谎；
每张卡自己另有单数标记，投递确认单用它自己的 `approvalId`）。

活体读数（同一时刻只有一张待决单，`agent.pause.pending()[0].requestId = 79b223a8-…`）：

| 位置 | 读到 |
| --- | --- |
| band `data-pause-request-ids` | `79b223a8-e161-4f7b-b270-f58cc0553524` |
| `pause-approve` `data-pause-request-id` | 同上 |
| `pause-deny` `data-pause-request-id` | 同上 |

三处与 `pending()[0].requestId` **逐字相同**——脚本与人从此都能先核单号再点，不必靠「哪只可见」猜。

## 补：补信息卡改成按工具 schema 声明的结构化字段（R13-8，P1）

**为什么不能让人填 JSON**：QA 连填两种形状都报 `Unrecognized key: "jobId"`——形状只能靠报错反推，
真实使用中等于审批链在此断掉。JSON 只能是交换格式，不能是界面形态。

**做法**
- `ToolSupplyField`（`packages/core/src/events.ts`）：`{ path, labelKey, kind: 'text'|'textarea'|'select', optional?, options?, optionsFrom? }`。
  由**工具登记方**声明，不从 zod 内部结构内省（`_def` 不是稳定 API）；声明只描述画法与组装路径，不参与校验。
- `agent.tools.list()` 把它带进 `ToolDescriptorView.supply`（渲染层只读这一份）。
- `outbound.greet.perform` 声明三格：`request.platform`（下拉，取值现问 `platform.registry.list`）、
  `request.jobId`（文本、可选）、`request.text`（文本域）。
- 界面（`AgentPauseCards` 的 `ElicitationCard`）：有声明就按格子画，`assembleSupply()` 按点路径**拼出嵌套对象**，
  提交时 `JSON.stringify` 交回（`{request:{…}}` 这层由代码拼）；可选项留空即整格不写；没声明的工具退回旧文本域。

**活体（半自动 + 桩，`/plan outbound.greet.perform` → 确认 → 批准）**

| 读点 | 读数 |
| --- | --- |
| 卡片形态 | `structured:true`、`legacyTextarea:false`；三格 `select` / `input` / `textarea`，平台选项 `["", "boss"]` |
| 提交 | `pending` 1 → **0**；卡片消失 |
| 入参（库里的观察原文） | `入参经人补充 1 轮，实际使用：{"request":{"platform":"boss","jobId":"1","text":"你好，看到贵司在招前端，想聊聊"}}` |
| 这一步的结局 | `failed` / `TOOL_FAILED`：「平台 boss 还没有一份自动化风险确认记录，先确认承担该风险」——**闸门在拦，不是形状不对** |

也就是说：**人只填了三格值，`{request:{…}}` 是代码拼的**，提交后入参一次通过工具自己的 schema，
run 正常推进到执行（再被风险确认闸门挡住，零外发）。（这一格的证据是 DOM 与库里的观察原文；没有另存截图，卡面读数见上表。）

## 补：批准链端到端「各恰增 1」自测（本机仿站）

路径：`/plan outbound.greet.perform` → 确认 → 批准 → 补信息卡三格 → 提交（全走界面，桩只出步、不产参数）。

| 读点 | 读数 |
| --- | --- |
| 岗位 | 库里第一条：`boss / 1001`（`jd.capture.run` 打本机仿站抓的） |
| 三格 | 平台下拉选项 `["", "boss"]`、岗位 id 输入、文案文本域；填 `boss / 1001 / 你好，看到贵司在招前端，想聊聊` |
| 待决单 | 1 → **0**（提交后卡片收掉） |
| `usage_ledger` | 1 → **2**（新增行 `action=greet`、`target_id=1001`、`source=manual:1001`） |
| `outbound_attempts` | 0 → **1**（`boss/1001/greet`、`status=succeeded`、`ledger_id=2`） |
| 步行 | `ok`：「已向 boss 的 1001 发出打招呼（账本第 2 行 · 内容来源 manual）｜入参经人补充 1 轮，实际使用：{"request":{"platform":"boss","jobId":"1001","text":"…"}}」 |
| run | `completed` / `COMPLETED` |

这就是 `10.12-08` 剩下那条判据：**账本与 attempts 各恰增 1、且 `attempts.ledger_id` 指向新增那一行**。
钉住的点：入参是**代码按格子组装**出来的嵌套对象，一次通过 schema；用户全程没写 JSON。
