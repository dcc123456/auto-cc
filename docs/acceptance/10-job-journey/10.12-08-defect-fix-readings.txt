10.12-08 审批门禁三处缺陷（D1/D2/D3）的复验与修法（2026-11-24，开发侧）

**D1「全自动档没有批准出口」——口径要更正：那不是确认单，是补充信息单**
- 两张卡是两种东西，界面标签就不一样：确认单的否定键是「**拒绝**」（`agent.pause.deny`），
  补充信息单的否定键是「**放弃**」（`agent.pause.giveUp`），另外还有一颗「提交」与一个补充输入框
  （`data-testid="agent-pause-elicitation"` / `agent-pause-supply-input`）。
- QA 报的是「放弃」，所以那张是**补充信息单**：全自动档按 2026-10-26 裁定**不问批准**（一次性明示之后逐步放行），
  卡住它的是入参缺字段——`outbound.greet.perform` 的入参是
  `{ request: { platform, jobId?, conversationTarget?, text } }`（`platform` 与 `text` 必填），
  桩按 goal 里那段 JSON 给入参，goal 只写了工具 id 时入参是 `{}`，于是开的是「这一步还缺信息」。
- 结论：**没有可批的事**（不是缺批准键），也不该「立即拒绝」（缺的是信息，不是被拒）。
  真要改的是文案侧——那张卡已经写明「这一步还缺信息 / 还缺或不合契约的字段」，超时那句也写明
  「到点无人表态就按未批准收掉，绝不默认放行」。这条建议按口径问题收口，不算缺陷。

**D2 拒绝后偶发停在 `running`——已加结构性兜底，复验两次都在 10 毫秒内落定**
- 修法：`packages/agent/src/loop/loop.ts` 新增 `executeToSettlement(scope)`，`confirm` 与 `resume` 都改走它。
  `execute` 的每条正常出口本来就调 `finish`，但它自己也可能抛（库写失败、上下文被重建、意料之外的断言）——
  抛出去就会留下一条永远 `running` 的 run。现在：**抛也只落 `failed`**（`AppError` 用它的码，
  其余记 `STEP_UNSUCCESSFUL`），并且只在 `scopes` 里还有它时才收（不把已 `completed` 的改写掉）。
- 活体复验（半自动档，同一份 fixture 装配，点 `pause-deny`）：两条 run 分别 **7ms / 4ms** 落到
  `failed` / `PAUSE_DENIED`，`agent.pause.pending()` 归 0，抬头「确认单已按你的表态收掉（第 1 轮）拒绝这一步：成功」。

**D3 确认调用阻塞两分钟——界面这一侧改成不等，主进程语义保持不变**
- 修法：`packages/renderer/src/useAgentRun.ts` 的 `confirm()` 不再 `await` 主进程那一口，只把调用抛出去，
  状态一律走 `agent/run-progress`。理由写进注释：主进程这条口的语义是「确认并跑完整条循环」，
  碰到确认单会等到人表态或超时；界面等它就会把「按一下」画成「忙到超时」，而人此刻要做的正是在卡片上表态。
- 活体：点「确认并执行」到确认单可见 **8～10 毫秒**（改造前要等整条循环，最长 120 秒）。
- **为什么不改主进程那一口的返回值**：`agent.loop.confirm` 的返回值是「跑完之后的读数」，全仓 **69 处**调用点
  （其中 65 处在 `loop.test.ts`）都按这个语义写。把它改成「立即返回 running」要重写这 65 条用例的等待方式，
  换来的只是程序内调用者的语义变化，而用户能感到的阻塞已经在渲染层消掉。这一条请 PMO 判是否还要动主进程契约。
