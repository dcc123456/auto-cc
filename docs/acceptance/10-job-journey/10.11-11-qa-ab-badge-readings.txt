## B：按停止后 ≤1s 状态不再 `running`

同实例，执行器在岗间节流睡眠中（`throttle.minGapMs=45000 / maxGapMs=150000`）时按停止：

```
{ "stopReturned": "stopping", "statusAfterStop": "stopping", "stopMs": 0, "readMs": 1, "badge": null }
```

（`stopMs` = `stop()` 往返、`readMs` = 紧接的 `view()` 往返，均毫秒；`stop()` 返回值本身已是 `stopping`。）

收尾时间线（每 5s 轮询一次）：

```
{ "transitions": [ { "at": 0, "status": "stopping" }, { "at": 75, "status": "stopped" } ],
  "final": { "status": "stopped", "pending": ["1001","1002"], "failed": ["KB_SOURCE_MISSING"] } }
```

即：按停止 **0ms 后**状态已是 `stopping`（不再是 `running`），循环在下一个检查点（本例为岗间睡眠结束，75s）把状态落到 `stopped`；期间 `pending` 未变、`failed` 未增，账本仍 0 笔。**B 判通过。**

## 发现 C（P2，新）：角标不跟随执行器状态变化刷新，`stopped` 那一格在长开窗口里永远不亮

`packages/renderer/src/ChatPanel.tsx` 的执行器读数 effect 依赖 `[bridge, agentRun.run, agentPause.pending]`——只有 **agent run / 逐条批准卡** 变化或组件重挂（面板/窗口重载）时才重读 `journey.unattended.view`。没有推送、也没有在 `stopping→stopped` 时触发重读。
实测：停止后 75s 已经 `status: "stopped"`、`pending: 2`（直接读桥），角标仍 `null`；`location.reload()` 一次后立刻 `needs 2`。
后果：用户开着窗口、无人值守在后台被停止/收尾之后，**「需要你」这一格不会出现**，除非恰好有别的事件把 ChatPanel 的 effect 撞一次。与 10.11-22「不新增轮询」并不冲突——缺的是一条推送（unattended 状态变化事件）或让 Home 状态行的既有读数顺带报一次。
影响面：10.11-11 的第三类来源（执行器待办）在活体上只能靠刷新看见；SEMantica 对（A）已对，可见性未达。
