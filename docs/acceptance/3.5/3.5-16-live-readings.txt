夹具：`tmp/35-15-mixed.pdf`（一片 595×842pt 的纸，米色底 #f4ead6，三行：sans 13pt / serif 15pt / mono 12pt，墨色 #1f2937）
现场：PDF 编辑档 → 第 1 页 → 点中 serif 那一行（原文「Typography debugging legacy stacks」）→ 就地改挂出

本片要证的三件事，逐件给数：

③ 字号 / 字族 / 墨色三样都从片 2 的行数据来，琥珀边框只在 focus 时现。

----------------------------------------------------------------------
1. 计算样式：那一只框彻底透明（`tmp/35-16-read.js`）
----------------------------------------------------------------------
`[data-testid=pdf-edit-inline-wrap]`（包裹节点）
  background-color : rgba(0, 0, 0, 0)      ← 改造前是 oklab(0.999994 … / 0.95)，即 `bg-white/95`
  color            : rgb(15, 23, 42)
  font-size        : 10.03px
  font-family      : serif
`[data-action=pdf-edit-inline-text]`（输入框本体）
  background-color : rgba(0, 0, 0, 0)
  border-top-color : rgba(0, 0, 0, 0)      ← 非 focus 时无边框
  font-size / font-family / color 同上（`text-inherit` 生效）

10.03px 这一条是算术核对：该行 15pt × 纸面 CSS 宽 398px ÷ 页宽 595pt = 10.03px，
即输入框的字是**按被盖住那一行的字号**长的，不是面板层的又一个写死值。

----------------------------------------------------------------------
2. 变量出处：三条样式变量写在纸的包裹节点上，输入框靠继承吃到（`tmp/35-16-final.js`）
----------------------------------------------------------------------
holder（`wrapRef`，即挂三只框几何变量的那一个节点）自己的 inline style：
  --pdf-edit-size : 10.03px
  --pdf-edit-font : serif
  --pdf-edit-ink  : #0f172a
  --pdf-edit-left : 8.403361344537815%
（`getPropertyValue` 只在**写变量的那一格**读得到；输入框上读回空串，但 computed 值对得上，
  说明这一条走的是继承，符合 §5.2「动态几何/样式不进多颗节点」的既有口径。）
现场自证：那一只节点（`[data-testid=pdf-edit-paper] div.relative`）的 `style` 属性原文里，
三只框的几何与这一格的样式**并排住在同一格**上——
  --pdf-hover-* / --pdf-rubber-* / --pdf-edit-{left,top,width,height} 之后紧跟着
  --pdf-edit-size: 10.03px; --pdf-edit-font: serif; --pdf-edit-ink: #0f172a;

`--pdf-edit-ink` 拿到的是 #0f172a（深墨）而不是回落的那一支 #f8fafc（反白）——
这条本身就是「底色量到了」的旁证：量不到时 `colorsOfOverlay` 走墨黑垫底 + 新字反白，
只有从位图上真量到米色纸，才会给出深色墨。

4. 琥珀边框：这一腿只能读到规则，读不到画面（诚实的 [!]）
----------------------------------------------------------------------
窗口 `document.visibilityState === 'hidden'` 时，Chromium 不给 `:focus` 匹配：
  document.activeElement === input : true
  input.matches(':focus')          : false
  document.hasFocus()              : false
于是"敲字时边框变琥珀"这一条在无人值守的活体上取不到像素证据。改取两条替代读数：
  a) 规则确实发出来了（读注入的 `<style>` 原文，81003 字符，2 个 style 标签）：
     `.focus\:border-amber:focus { border-color: var(--color-amber); }`
     且输入框的 class 串里带着 `focus:border-amber`；
  b) 非 focus 那一半是量得到的：同一格同时挂上 `border-amber`（不加 focus 前缀）后
     computed border-top-color 仍是 rgba(0, 0, 0, 0) —— 基态的 `border-transparent` 压得住它，
     所以"平时看不见这只框"这一条成立；focus 那一态由 a) 的更高特异度（0,2,0 > 0,1,0）接管。
⇒ 这一腿标 `[!]`：要人把窗口带到前台敲一次字，看琥珀边框长不长出来。

6. 一条环境事实（写下来免得下一轮又当成产品缺陷找）
----------------------------------------------------------------------
窗口 hidden 时 pdf.js 的那一趟 `render()` 挂在时间轴上：1500ms 里 rAF 只走了 1 帧，
表现是「状态行已经回 ready、位图却整张白」（`nonWhite 0 / 9241`），且没有任何 rejection/error 事件。
`harness shot`（CDP `Page.captureScreenshot`）逼一帧之后渲染才跑完：
  state 从「画了 -1 毫秒」→「画了 49 毫秒」，位图从全白 → `nonWhite 9241 / 9241`（米色纸 + 墨字）。
⇒ 这条与 §9 的「hidden 时 CSS 动画时间轴不推进」是同一族，只是被挡的对象换成了 pdf.js 的分帧渲染。
⇒ 由此得一条 harness 用法：量画布像素前先拍一张 shot 逼帧，再看 `画了 N 毫秒` 的 N 是否 ≥0。
