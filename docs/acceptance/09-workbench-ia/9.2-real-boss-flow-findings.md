## 二、搜岗与详情（已修两处）

1. **limit 未生效（已修）**
   - 第一次跑 `limit=5`：`stored=12`、`containers=12`、`skipped=12`，界面显示「已入库 12/5 条」。
   - 原因：列表读取把整页卡片全部 upsert 完才检查 `collected.size >= target`。一页返回 12 张卡，于是 5 条目标被整页吞掉。
   - 修复：在 `jd-capture.ts` 的卡片循环内、处理完当前卡后立即 `break`；新增一页 3 卡 + limit 2 的单测（期望入库 2）。
2. **独立详情页正文读空（已修）**
   - 12 条全部 `skipped: 详情页读不到岗位职责正文`，库里 `hasDetail=false`、`descriptionLength=0`。
   - 真实独立详情页的形状：根容器 `div.job-detail`，职位描述正文 `div.job-sec-text`；
     旧知识包把 `div.job-banner`（顶部状态条）当根，正文候选只有 `p.desc`（只存在于列表右侧同页面板）。
   - 修复：`boss.json` 的 `detailRoot` 增加 `div.job-detail`（替换掉 `div.job-banner` 作为形状 B 根），
     `detailDescription` 增加 `div.job-sec-text`；DOM 读数见 `9.2-real-boss-detail-dom.txt`。
   - 复测：limit=1 时 `stored=1`、`hasDetail=true`、正文 253 字，`skipped=[]`。
3. **首次抓取撞上会话首页仍在加载**
   - 刚 `sessions.open('boss')` 后立刻 `capture.run`，返回 `UNKNOWN (-3) loading 'https://www.zhipin.com/shanghai/?seoRefer=index'`。
   - 等 `page.snapshot().readyState === 'complete'` 后重跑即成功。
   - 建议：`openSearch` 前先等到当前页 `readyState=complete`，或对 `(-3) loading` 做一次短重试。

## 三、打招呼（应用内仍未走通）

1. **jdId 契约错位（已修）**
   - 第一次点「打招呼」：`OUTBOUND_JD_UNREGISTERED：岗位 15 在库里没有记录`。
   - 原因：`JobLabPanel` 与 `ScriptPanel` 把库内自增 `row.id` 当成 `script.jdId`；服务端 `hasJob()` 按平台 `job_id` 查库。
   - 修复：两处都改传 `row.jobId` / `target.jobId`。
2. **真实 BOSS 的打招呼入口不在现有适配器路径里（未修）**
   - 修复 jdId 后重试仍失败：`WAIT_TIMEOUT：等待「clickable」超时（5000ms 内未满足）`。
   - 真实路径：
     - 岗位详情页 `a.btn.btn-startchat`（文本「立即沟通」，rect 150×45，visible/enabled/unobstructed）
     - 点击后**不跳页**，同页长出 `div.startchat-content` 内联聊天面板：
       `textarea.input-area`（422×74） + `div.send-message`（空内容时 class 含 `disable`）
     - 现有知识包/适配器却是：导航 `/web/geek/chat`，等 `div#chat-input.chat-input`。
       该页在未选中会话时根本没有输入框，所以 5 秒后超时。
   - 本轮手动用 `browser.act.click` + `HitAddress` 点了 `a.btn.btn-startchat`（定位分只有 10，低于 70，
     但传 hitAddress 后 CDP 点击成功）。点完之后页面文本出现
     **「已发送 您好，可以和您聊聊吗？」**——这是 BOSS 自己点「立即沟通」发出的默认问候，
     **不是本应用的 `greet.perform` 发出的**；应用账本里只有 `search:1`，没有对应的 greet 行。
   - 这意味着两件事：
     ① 应用内自动打招呼在真实 BOSS 上仍不可用；
     ② 人手在页面上点「立即沟通」会发出站点的默认问候，而应用无法把这笔记进自己的账本。

## 五、额度与账本读数

- `entitlement.gate.check`：search / greet / deliver 全部 `allowed=true`、`remaining=null`。
- `cordis.yml` 的 `entitlement.mode = unlimited`；`dailyLimits` 虽然写了 search 40 / greet 20 / deliver 10，但当前模式不执行。
  AGENTS.md §8.3 要求「频控、日上限、人类化节流是必需项」——发货前建议切到 `daily`，或至少把 `unlimited` 作为显式开发档提示。
- 抓取结束时 `CaptureRunView.ledgerRowsBefore/After = 0/0`，但随后账本里能看到 `search:1`。
  两次读数不是同一时刻：抓取自己的 before/after 读在闸门任务内部，而 search 行在任务成功后由闸门写入。
  界面上「抓取前/后账本 0 行」容易被读成「这一轮什么都没记」，建议改成「本轮 search 已入账」或在任务收尾后再读一次。

## 六、优化建议（按优先级）

1. **P0 真实 BOSS 打招呼**：在知识包增加 `chat.startButton`（`a.btn.btn-startchat`）与内联面板
   `textarea.input-area` / `div.send-message` 的定位；适配器在只有 `jobId` 时先打开岗位详情、点「立即沟通」、
   再在内联面板输入与发送。保留 `/web/geek/chat` + `conversationTarget` 作为已有会话的另一条路。
2. **P0 真实 BOSS 投递**：补「附件简历」菜单 → 文件控件 → 确认发送的整条定位链；在拿到真实 DOM 证据前不要登记猜测选择器。
3. **P1 抓取导航竞态**：`openSearch` 前等 `readyState=complete`，或对 `(-3) loading` 重试一次。
4. **P1 额度**：把 `mode` 切到 `daily`（或把 unlimited 明确标成开发档），确保日上限真的生效。
5. **P2 账实一致**：手动在页面上点「立即沟通」产生的消息无法被应用记账；至少要在界面上说明
   「这条消息不是应用发出的」，或提供一次「同步会话/补记」入口。
6. **P2 账本读数**：抓取结局里的 before/after 与真实入账时刻错位，建议在 `gate.perform` 完成后重读一次。
